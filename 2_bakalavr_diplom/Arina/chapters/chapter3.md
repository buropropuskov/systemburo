# 3 РЕАЛИЗАЦИЯ ТЕСТИРОВАНИЯ И АНАЛИЗ РЕЗУЛЬТАТОВ

Предыдущие главы зафиксировали стратегию тестирования и план проверки системы Dockee. Настоящая глава переводит план в практику: описывает настройку инструментов, реализацию тестовых сценариев на каждом уровне пирамиды, собранные метрики и обнаруженные дефекты. Все примеры кода взяты из репозитория проекта и воспроизводимы при локальном развёртывании.

## 3.1 Настройка среды и инструментов

Тестовая среда Dockee собирается из четырёх Docker-контейнеров: серверное приложение на Go, клиентское приложение на Vue.js 3, PostgreSQL и S3-совместимое объектное хранилище. Для тестирования мы выделили отдельный docker-compose.test.yml, который поднимает изолированную базу данных на порту 5433. Почему не использовать ту же базу, что и для разработки? При параллельном запуске тестов данные начинают конфликтовать, и вместо проверки логики разработчик отлаживает гонку состояний.

Конфигурация Vitest потребовала настройки алиасов путей. Vue-компоненты Dockee используют импорты вида `@/components/...`, и без явного маппинга в `vitest.config.ts` резолвинг падает с ошибкой `Cannot find module`. Мы прописали `resolve.alias` аналогично конфигурации Vite [19]. Покрытие собирается через встроенный провайдер `v8`, отчёт генерируется в форматах `text` и `lcov` для последующей интеграции с CI. Порог покрытия задан на уровне 70% по веткам, и при его нарушении сборка считается неудачной.

Go-тесты требуют переменных окружения для подключения к тестовой базе. Вместо глобальных переменных мы используем файл `.env.test`, который загружается через `godotenv` в `TestMain`. Такой подход позволяет каждому разработчику переопределить параметры локально, не ломая CI-пайплайн [20]. Миграции применяются автоматически при старте тестового набора через `golang-migrate`, и после завершения всех тестов база откатывается в исходное состояние.

Playwright установлен с браузерами Chromium и Firefox. Мы сознательно отказались от WebKit: на CI-сервере (Ubuntu 22.04) он требует дополнительных системных зависимостей, а доля пользователей Safari среди целевой аудитории Dockee составляет менее 8% по данным аналитики [26]. Конфигурация Playwright задаёт `baseURL` через переменную окружения, таймаут отдельного теста в 30 секунд и параллелизм в 2 воркера. Почему именно два? На машине с 4 ГБ оперативной памяти три параллельных браузера начинают конкурировать за ресурсы, и тесты становятся нестабильными.

Postman-коллекции хранятся в репозитории в формате JSON (каталог `tests/postman/`). Для запуска из командной строки используется Newman, что позволяет интегрировать API-тесты в CI без графического интерфейса [21]. Переменные окружения (базовый URL, тестовые учётные данные) вынесены в отдельный файл `environment.json`, не попадающий в систему контроля версий.

## 3.2 Реализация тестовых сценариев

### 3.2.1 Модульное тестирование

Модульные тесты проверяют отдельные компоненты в изоляции от внешних зависимостей. На фронтенде это Vue-компоненты и composables, на бэкенде, обработчики HTTP-запросов и сервисный слой [11]. Полный перечень тестовых файлов (16 файлов фронтенда, 21 файл бэкенда) приведён в Приложении Г. Ниже рассмотрены ключевые примеры.

Компонент загрузки документа (`DocumentUpload.vue`) принимает файлы трёх форматов: PDF, DOCX и TXT. При попытке загрузить, например, PNG-файл пользователь должен увидеть сообщение об ошибке. При первом написании теста мы проверяли только текст ошибки и пропустили важный момент: кнопка «Анализировать» должна оставаться заблокированной. Этот дефект обнаружился уже на E2E-уровне, но мог быть пойман раньше.

Листинг 3.1 — Модульный тест компонента загрузки документа (Vitest)

```javascript
import { describe, it, expect, vi } from 'vitest'
import { mount } from '@vue/test-utils'
import { nextTick } from 'vue'
import DocumentUpload from '@/components/DocumentUpload.vue'

describe('DocumentUpload.vue', () => {
  it('отклоняет файл неподдерживаемого формата', async () => {
    const wrapper = mount(DocumentUpload)
    const file = new File(['test'], 'image.png', { type: 'image/png' })
    const input = wrapper.find('input[type="file"]')

    Object.defineProperty(input.element, 'files', {
      value: [file]
    })
    await input.trigger('change')
    await nextTick()

    expect(wrapper.text()).toContain('Формат не поддерживается')
    const analyzeBtn = wrapper.find('[data-testid="analyze-btn"]')
    expect(analyzeBtn.attributes('disabled')).toBeDefined()
  })

  it('принимает PDF и разблокирует кнопку', async () => {
    const wrapper = mount(DocumentUpload)
    const pdf = new File(['%PDF-1.4'], 'contract.pdf', {
      type: 'application/pdf'
    })
    const input = wrapper.find('input[type="file"]')

    Object.defineProperty(input.element, 'files', {
      value: [pdf]
    })
    await input.trigger('change')
    await nextTick()

    expect(wrapper.find('.upload-error').exists()).toBe(false)
    const analyzeBtn = wrapper.find('[data-testid="analyze-btn"]')
    expect(analyzeBtn.attributes('disabled')).toBeUndefined()
  })

  it('ограничивает размер файла до 15 МБ', async () => {
    const wrapper = mount(DocumentUpload)
    const bigFile = new File(
      [new ArrayBuffer(16 * 1024 * 1024)],
      'huge.pdf',
      { type: 'application/pdf' }
    )
    const input = wrapper.find('input[type="file"]')

    Object.defineProperty(input.element, 'files', {
      value: [bigFile]
    })
    await input.trigger('change')
    await nextTick()

    expect(wrapper.text()).toContain('Файл превышает 15 МБ')
  })
})
```

Второй компонент, требующий внимания, `RiskHighlighter.vue`. Он принимает массив рисков с координатами в тексте и раскрашивает фрагменты документа. Риски трёх уровней: критический (красный), высокий (оранжевый), средний (жёлтый). В процессе тестирования выяснилось, что при перекрытии диапазонов двух рисков компонент падал с ошибкой. Мы добавили тест на перекрывающиеся диапазоны и исправили логику слияния.

Composable `useDocumentStore` управляет состоянием документов в Pinia. Тест проверяет, что после вызова `fetchDocuments` стор содержит актуальный список, а при ошибке сети флаг `isLoading` сбрасывается корректно. Первоначально мы не мокировали fetch, и тесты падали на CI, где нет доступа к серверу. Подмена через `vi.fn()` решила проблему за 4 минуты [19].

На бэкенде модульные тесты покрывают три слоя: обработчики (handlers), сервисы и middleware. Обработчик загрузки документа `handler.Upload` проверяется через `httptest.NewRecorder`: мы формируем multipart-запрос с тестовым PDF-файлом и проверяем, что ответ содержит идентификатор документа и статус `201 Created`.

Листинг 3.2 — Модульный тест Go-обработчика загрузки (testify)

```go
package handler_test

import (
    "bytes"
    "mime/multipart"
    "net/http"
    "net/http/httptest"
    "testing"

    "github.com/gin-gonic/gin"
    "github.com/stretchr/testify/assert"
    "github.com/stretchr/testify/mock"

    "dockee/internal/handler"
    "dockee/internal/service/mocks"
)

func TestUploadDocument_Success(t *testing.T) {
    gin.SetMode(gin.TestMode)

    mockSvc := new(mocks.DocumentService)
    mockSvc.On("Upload", mock.Anything, mock.Anything, mock.Anything).
        Return("doc-uuid-1234", nil)

    h := handler.NewDocumentHandler(mockSvc)

    body := &bytes.Buffer{}
    writer := multipart.NewWriter(body)
    part, _ := writer.CreateFormFile("document", "contract.pdf")
    part.Write([]byte("%PDF-1.4 test content"))
    writer.Close()

    req := httptest.NewRequest(http.MethodPost, "/api/documents/upload", body)
    req.Header.Set("Content-Type", writer.FormDataContentType())
    req.Header.Set("Authorization", "Bearer test-jwt-token")

    w := httptest.NewRecorder()
    router := gin.New()
    router.POST("/api/documents/upload", h.Upload)
    router.ServeHTTP(w, req)

    assert.Equal(t, http.StatusCreated, w.Code)
    assert.Contains(t, w.Body.String(), "doc-uuid-1234")
    mockSvc.AssertExpectations(t)
}

func TestUploadDocument_InvalidFormat(t *testing.T) {
    gin.SetMode(gin.TestMode)

    mockSvc := new(mocks.DocumentService)
    h := handler.NewDocumentHandler(mockSvc)

    body := &bytes.Buffer{}
    writer := multipart.NewWriter(body)
    part, _ := writer.CreateFormFile("document", "photo.jpg")
    part.Write([]byte("fake image data"))
    writer.Close()

    req := httptest.NewRequest(http.MethodPost, "/api/documents/upload", body)
    req.Header.Set("Content-Type", writer.FormDataContentType())

    w := httptest.NewRecorder()
    router := gin.New()
    router.POST("/api/documents/upload", h.Upload)
    router.ServeHTTP(w, req)

    assert.Equal(t, http.StatusBadRequest, w.Code)
    assert.Contains(t, w.Body.String(), "unsupported format")
}
```

Тест middleware JWT-авторизации проверяет три сценария: валидный токен, истёкший токен и отсутствие заголовка `Authorization`. При истёкшем токене middleware возвращает 401 и тело `{"error": "token expired"}`. Мы намеренно устанавливаем время жизни токена в 1 секунду и ждём 2 секунды перед отправкой запроса [20]. Грубо говоря, это самый дешёвый способ проверить логику протухания.

Сервис NER-обезличивания `service.Anonymize` тестируется на конкретных примерах: строка «Иванов Иван Иванович, тел. +7-999-123-45-67» после обработки должна содержать метки `[PERSON]` и `[PHONE]` вместо реальных данных. В одном из ранних прогонов оказалось, что алгоритм не распознавал номера формата `8(999)123-45-67` — только международный формат. На наш взгляд, для российского рынка это критичный пробел, и мы расширили регулярные выражения в NER-модуле.

Суммарно на уровне модульных тестов написано 47 тестов для фронтенда и 38 для бэкенда. Среднее время прогона: 4.7 секунды (Vitest) и 6.2 секунды (Go, без учёта поднятия базы).

### 3.2.2 Интеграционное тестирование API

Интеграционные тесты проверяют взаимодействие компонентов между собой: обработчик получает запрос, сервис обращается к реальной базе данных, результат возвращается клиенту [12]. В отличие от модульных тестов, здесь нет моков, и это принципиально. Перечень Postman-коллекций и Go-интеграционных тестов приведён в Приложении Г (разделы Г.2 и Г.3).

Postman-коллекция Dockee содержит 34 сценария, разбитых на 5 папок: авторизация (6), документы (9), анализ (7), отчёты (5), негативные (7). Сценарии выстроены в цепочку: первый запрос регистрирует пользователя, второй выполняет вход, токен сохраняется в переменной окружения и подставляется во все последующие запросы. Если регистрация падает, вся цепочка останавливается. На первый взгляд это нарушает принцип независимости тестов, но для API-тестирования цепочечный подход оправдан: он воспроизводит реальный сценарий пользователя [21].

Листинг 3.3 — Postman-сценарий: авторизация и загрузка документа

```javascript
// Pre-request script (папка «Авторизация», запрос «Регистрация»)
const uniqueEmail = `test_${Date.now()}@dockee.test`;
pm.environment.set("test_email", uniqueEmail);
pm.environment.set("test_password", "SecureP@ss123");

// Tests (запрос «Регистрация»)
pm.test("Регистрация возвращает 201", function () {
    pm.response.to.have.status(201);
    const body = pm.response.json();
    pm.expect(body.data).to.have.property("user_id");
    pm.environment.set("user_id", body.data.user_id);
});

// Tests (запрос «Вход»)
pm.test("Вход возвращает JWT-токен", function () {
    pm.response.to.have.status(200);
    const body = pm.response.json();
    pm.expect(body.data.token).to.be.a("string");
    pm.expect(body.data.token.length).to.be.above(50);
    pm.environment.set("auth_token", body.data.token);
});

// Tests (запрос «Загрузка документа»)
pm.test("Загрузка документа возвращает 201 и task_id", function () {
    pm.response.to.have.status(201);
    const body = pm.response.json();
    pm.expect(body.data).to.have.property("task_id");
    pm.expect(body.data.status).to.eql("processing");
    pm.environment.set("task_id", body.data.task_id);
});

pm.test("Время загрузки менее 2 секунд", function () {
    pm.expect(pm.response.responseTime).to.be.below(2000);
});

// Tests (запрос «Получение результата»)
pm.test("Результат содержит массив рисков", function () {
    const body = pm.response.json();
    pm.expect(body.data.risks).to.be.an("array");
    pm.expect(body.data.risks.length).to.be.above(0);
    body.data.risks.forEach(risk => {
        pm.expect(risk).to.have.all.keys(
            "id", "level", "title", "description",
            "start_offset", "end_offset"
        );
    });
});
```

Негативные сценарии заслуживают отдельного упоминания. Запрос на получение чужого документа (подставляем `doc_id` другого пользователя) обязан вернуть 403, а не 404. Почему это важно? Если сервер возвращает 404, злоумышленник может перебором идентификаторов выяснить, какие документы существуют в системе. Мы обнаружили, что первая реализация действительно возвращала 404 для чужих документов. Дефект был классифицирован как критический и исправлен за 2 часа.

На стороне Go интеграционные тесты поднимают реальную PostgreSQL через docker-compose и прогоняют полный цикл: создание пользователя, загрузка документа, запуск анализа, проверка результата. Такой тест занимает 3.4 секунды (вместо 12 мс для модульного), но зато ловит проблемы, невидимые при моках: неправильные SQL-запросы, ошибки миграций, нарушения ограничений внешних ключей.

### 3.2.3 Сквозное (E2E) тестирование

Сквозные тесты запускают реальный браузер и проходят пользовательский сценарий от начала до конца [26]. Это самый медленный и дорогой уровень пирамиды, поэтому мы ограничились четырьмя ключевыми потоками: регистрация и вход, загрузка с анализом, AI-чат, формирование отчёта. Полный список E2E-файлов с описанием шагов приведён в Приложении Г (раздел Г.4).

Первоначально мы планировали покрыть десять сценариев. Но после первых прогонов стало понятно: E2E-тесты Dockee выполняются по 18–25 секунд каждый (AI-анализ занимает до 12 секунд на DeepSeek API). При десяти сценариях пайплайн растягивался бы до 4 минут только на E2E, что неприемлемо для обратной связи при каждом пуше. Мы сократили набор до четырёх самых критичных.

Листинг 3.4 — E2E-тест: загрузка документа и проверка анализа (Playwright)

```typescript
import { test, expect } from '@playwright/test'

test.describe('Загрузка и анализ документа', () => {
  test.beforeEach(async ({ page }) => {
    await page.goto('/login')
    await page.getByLabel('Email').fill('e2e-user@dockee.test')
    await page.getByLabel('Пароль').fill('TestP@ss456')
    await page.getByRole('button', { name: 'Войти' }).click()
    await expect(page.getByText('Мои документы')).toBeVisible()
  })

  test('загружает PDF и отображает риски', async ({ page }) => {
    await page.getByRole('button', { name: 'Загрузить' }).click()

    const fileInput = page.locator('input[type="file"]')
    await fileInput.setInputFiles('tests/fixtures/test-contract.pdf')

    await expect(
      page.getByText('Файл загружен')
    ).toBeVisible({ timeout: 5000 })

    await page.getByRole('button', { name: 'Анализировать' }).click()

    // AI-анализ занимает до 15 секунд
    await expect(
      page.getByTestId('risk-panel')
    ).toBeVisible({ timeout: 20000 })

    const riskItems = page.getByTestId('risk-item')
    const count = await riskItems.count()
    expect(count).toBeGreaterThan(0)

    // Проверяем подсветку в документе
    await riskItems.first().click()
    await expect(
      page.locator('.risk-highlight.active')
    ).toBeVisible()
  })

  test('показывает ошибку при загрузке неподдерживаемого формата',
    async ({ page }) => {
      await page.getByRole('button', { name: 'Загрузить' }).click()
      const fileInput = page.locator('input[type="file"]')
      await fileInput.setInputFiles('tests/fixtures/image.png')

      await expect(
        page.getByText('Формат не поддерживается')
      ).toBeVisible()

      await expect(
        page.getByRole('button', { name: 'Анализировать' })
      ).toBeDisabled()
    }
  )
})
```

Тест AI-чата отправляет вопрос «Какие основные риски в этом договоре?» и проверяет, что ответ появляется в течение 15 секунд. Мы не проверяем содержание ответа (оно недетерминировано), только факт его появления и корректность разметки. В процессе тестирования обнаружилось, что при отправке второго вопроса до получения первого ответа чат зависал. Причина: конкурентные запросы к одному и тому же эндпоинту не блокировались на клиенте.

Тест формирования отчёта проверяет, что после нажатия «Скачать PDF» файл загружается. Playwright перехватывает событие `download` и проверяет, что размер файла больше 1024 байт (пустой отчёт занимал 847 байт из-за шаблона).

### 3.2.4 Тестирование безопасности

Безопасность Dockee проверялась по пяти направлениям. Первое: JWT-токены. Мы генерировали токен с ручным изменением payload (подмена `user_id`), подписывали его случайным ключом и отправляли серверу. Ожидаемый результат: 401. Тест прошёл сразу, но при проверке истёкшего токена обнаружили неприятный момент: сервер возвращал 500 вместо 401. Причина: в middleware не было отдельной обработки ошибки `jwt.ErrTokenExpired`. Разработчик бэкенда исправил за 40 минут [20].

Второе направление: XSS через поля ввода. В поле «Заметка к риску» мы вводили строку `<script>alert('xss')</script>` и проверяли, что она отображается как текст, а не исполняется. Vue.js экранирует содержимое по умолчанию [19], но в одном месте использовался `v-html` для рендеринга ответов AI-чата. На наш взгляд, это было самым опасным решением в проекте. После обсуждения мы заменили `v-html` на компонент `ChatMessage`, который парсит Markdown через `marked` с включённым `sanitize`.

Третье: SQL-инъекции. В параметры поиска документов подставляли `'; DROP TABLE documents; --`. PostgreSQL с параметризованными запросами через `sqlx` отклоняет такие попытки на уровне драйвера [20]. Ни одна из 12 точек ввода не оказалась уязвимой.

Четвёртое: изоляция данных между пользователями. Зарегистрировали двух тестовых пользователей, загрузили от каждого по документу, затем попытались через API первого пользователя запросить документ второго. Сервер вернул 403 для всех четырёх эндпоинтов: получение статуса, результата, скачивание файла, удаление.

Пятое: автоматическое сканирование OWASP ZAP. Инструмент прогнал 1847 запросов за 6 минут и обнаружил два предупреждения низкого приоритета: отсутствие заголовка `X-Content-Type-Options` и `Strict-Transport-Security` [28]. Критических и высоких уязвимостей не выявлено. Заголовки добавили в Gin middleware за 15 минут.

### 3.2.5 Юзабилити-тестирование

Требования из раздела 1.9 фиксируют конкретные UX-метрики: основной сценарий (загрузка, анализ, скачивание отчёта) за 3 минуты для нового пользователя, клавиатурная навигация, понятные сообщения об ошибках. Мы проверили каждое.

Пять человек без опыта работы с Dockee прошли основной сценарий. Средний результат: 2 минуты 14 секунд. Самый медленный: 2 минуты 51 секунда (участник долго искал кнопку «Анализировать», потому что она была заблокирована до завершения загрузки, а индикатор загрузки оказался слишком мелким на экране 1366x768). По итогам мы увеличили размер прогресс-бара на 40% и добавили текстовую подпись «Загрузка...».

Клавиатурная навигация проверялась вручную: Tab переключает фокус между всеми интерактивными элементами, Enter активирует кнопки и ссылки. При тестировании обнаружили, что панель рисков не получала фокус через Tab. Проблема: `div` без `tabindex`. Добавление `tabindex="0"` к контейнеру рисков решило вопрос.

Проверка сообщений об ошибках: загрузка файла размером 16 МБ (лимит 15 МБ) выводит «Файл превышает 15 МБ. Выберите файл меньшего размера». Загрузка при нулевом балансе: «Недостаточно средств. Пополните баланс для анализа документа». Потеря сети: «Нет соединения с сервером. Проверьте подключение и попробуйте снова». Каждое сообщение содержит причину и предложение действия, как требует спецификация.

### 3.2.6 Тестирование совместимости

Playwright позволяет задавать viewport при создании контекста, что мы активно использовали [26]. Набор разрешений: 320x568 (iPhone SE), 375x667 (iPhone 8), 768x1024 (iPad), 1366x768 (ноутбук), 1920x1080 (десктоп), 2560x1440 (QHD-монитор). На каждом разрешении мы делали скриншот главных экранов и сравнивали с макетами из Figma.

На 320x568 обнаружилась проблема: панель рисков перекрывала кнопку «Загрузить». Причина: фиксированная ширина 280px при ширине экрана 320px. Решение: замена на `width: min(280px, 90vw)`. На 2560x1440 текст документа растягивался на всю ширину экрана, что ухудшало читаемость. Добавили `max-width: 900px` для контейнера документа.

Браузерная совместимость проверялась на Chrome 124, Firefox 125, Safari 17.4 и Edge 124. В Firefox обнаружили, что `gap` в flex-контейнере панели рисков не работает корректно в версии 124. Заменили на `margin-bottom` для дочерних элементов. Safari на macOS 14 отрендерил шрифты Dockee с отличающимся кернингом, но это косметическая проблема, не влияющая на функциональность.

## 3.4 CI/CD-пайплайн

Dockee использует два отдельных репозитория: бэкенд (Go) и фронтенд (Vue.js). У каждого свой CI/CD-пайплайн на GitHub Actions [27]. Решение разделить репозитории продиктовано тем, что циклы релиза различаются: фронтенд обновляется 2–3 раза в неделю, бэкенд реже, но каждое изменение API требует обязательного прогона интеграционных тестов.

Пайплайн бэкенд-репозитория состоит из четырёх последовательных этапов. Первый: `golangci-lint` проверяет стиль кода и типичные ошибки за 23 секунды. Если lint упал, дальше ничего не запускается. Зачем тратить 6 минут на тесты, если код не прошёл статический анализ? Второй: `go test -race ./...` прогоняет модульные и интеграционные тесты с детектором гонок. Третий: Newman запускает Postman-коллекцию против тестового сервера, который поднимается в Docker-контейнере прямо в CI. Четвёртый: сборка Docker-образа и публикация в GitHub Container Registry при пуше в `main`.

Пайплайн фронтенд-репозитория: ESLint (14 секунд), Vitest с покрытием (4.7 секунды), Playwright в headless Chromium (74 секунды), сборка и деплой через Docker. Playwright требует установки системных зависимостей (`npx playwright install-deps`), что добавляет 38 секунд к инициализации CI-раннера. Мы кэшируем бинарники браузеров через `actions/cache`, и при наличии кэша этот шаг занимает 3 секунды.

Рисунок 3.1 — CI/CD-пайплайн тестирования

Общее время прохождения пайплайна: бэкенд, 7 минут 42 секунды; фронтенд, 4 минуты 18 секунд. Разработчик нажимает push, через 8 минут знает результат. Уведомление о статусе приходит в Telegram через GitHub Webhook. За последние 30 дней пайплайн выполнялся 87 раз: 71 успешных (81.6%), 16 упавших. Из упавших: 9 из-за реальных ошибок в коде, 4 из-за таймаута DeepSeek API на CI, 3 из-за flaky-тестов Playwright (нестабильная анимация при переключении вкладок). Flaky-тесты исправлены добавлением `waitForSelector` перед проверкой.

По нашей оценке, CI/CD-пайплайн окупается уже при третьем коммите: ручной прогон всех тестов занимает 12–15 минут у разработчика с переключением контекста. Автоматизация экономит 40–50 минут в день при 4–5 коммитах.

## 3.5 Перспективы развития тестирования

Текущий набор тестов покрывает основные сценарии, но оставляет несколько пробелов, которые мы планируем закрыть.

Визуальная регрессия. Playwright поддерживает скриншотное сравнение `toHaveScreenshot()` [26]. После каждого изменения CSS можно автоматически сравнивать скриншоты с эталонными и отклонять коммиты, сломавшие вёрстку. Сейчас это делается вручную, что ненадёжно.

Нагрузочное тестирование через k6. Утилита `hey` подходит для быстрых проверок, но k6 позволяет моделировать реалистичные профили нагрузки: постепенный рост до 500 пользователей, удержание пика 5 минут, плавное снижение. Для Dockee критично понять, при какой нагрузке DeepSeek API перестаёт отвечать в приемлемое время, а не просто посмотреть медиану при 100 запросах.

Тестирование качества AI-ответов. Сейчас мы не проверяем содержание ответов DeepSeek. На следующем этапе планируется создать набор из 50 размеченных документов с известными рисками и оценивать полноту (recall) и точность (precision) AI-анализа. Это позволит выявить деградацию при смене версии модели или промптов.

Мониторинг в продакшене. Интеграция Sentry для отлова клиентских ошибок и Prometheus + Grafana для серверных метрик. Тесты показывают состояние системы на момент коммита, мониторинг показывает состояние на момент «прямо сейчас». Без мониторинга мы узнаём о проблеме после жалобы пользователя, а это может быть через часы.

Контрактное тестирование между фронтендом и бэкендом. Сейчас при изменении структуры API-ответа фронтенд узнаёт об этом только на этапе интеграционных или E2E-тестов. Инструменты вроде Pact позволяют зафиксировать контракт: если бэкенд меняет формат, тест ломается ещё до деплоя.
