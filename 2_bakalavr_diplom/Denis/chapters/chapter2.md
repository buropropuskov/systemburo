# 2 МОДЕЛИРОВАНИЕ ПРЕДМЕТНОЙ ОБЛАСТИ СИСТЕМЫ ОЦЕНИВАНИЯ СТУДЕНТОВ

## 2.1 Характеристика процесса оценивания в LMS Moodle

Moodle сегодня работает более чем на 200 000 площадках в 240 странах [1]. Платформа стала де-факто стандартом для вузов СНГ, и МИРЭА здесь не исключение. Через неё проходят курсовые работы, лабораторные, эссе, контрольные домашние задания. Именно на этом фоне возникает задача, которой посвящена наша работа.

Понедельник, 9:00. Преподаватель открывает Moodle и видит 28 файлов DOCX, сданных вчера вечером к 23:59. Группа ЭФБО-06-22, задание «Эссе по архитектуре корпоративных приложений». Что делает преподаватель? Он открывает первый файл, быстро пробегает глазами. Открывает второй. Кажется, абзац про микросервисы где-то уже встречался. Возвращается к первому, сверяет. Похоже, но не дословно. Открывает третий. И так пока позволяет терпение.

Посчитаем честно. Для группы из 25 студентов число уникальных пар равно C(25,2) = 300. Для группы 30 человек уже 435. Медианное время беглого визуального сравнения двух работ объёмом 1-2 страницы, по данным Коваленко, составляет около 1,5 минуты [7]. Умножаем: 300 × 1,5 = 450 минут, или 7,5 часов непрерывного внимания на одно задание у одной группы. Три параллельные группы, два-три задания в неделю, и уже 900+ пар отделяют преподавателя от выходных.

По опыту автора, в реальной практике таких проверок не бывает. Преподаватель сравнивает выборочно, по интуиции: «Этот абзац у Петрова подозрительно похож на формулировку Сидоровой». Систематика исчезает, субъективность растёт. Рыбаков указывает, что отсутствие инструмента попарного сравнения в LMS — одна из системных причин низкой ценности самостоятельной работы в электронной среде [18].

Мы выделили три болевые точки. Первая — трудозатраты, которые при честной проверке делают задачу нерешаемой. Вторая — субъективность: нашёл или не нашёл совпадение зависит от усталости. Третья — невоспроизводимость: преподаватель не документирует факт сравнения, и его решение нельзя обосновать перед апелляционной комиссией.

## 2.2 Акторы системы и их цели

Выделение ролей мы выполнили по методике Грекула: сначала ответственные за бизнес-процесс, затем конечные пользователи, затем технический персонал [19]. Получилось три роли.

### 2.2.1 Преподаватель

Основной актор. Ради него плагин создаётся, его рабочий день плагин освобождает. Цели:

- настроить задание с включённой проверкой самостоятельности одним чекбоксом, без обращения к администратору;
- после срока сдачи получить автоматический отчёт о попарной схожести работ группы;
- раскрыть подозрительную пару и увидеть выделенные фрагменты совпадающего текста рядом, в двух колонках;
- принять обоснованное решение об оценке, опираясь на зафиксированные цифры, а не на впечатление.

### 2.2.2 Студент

Для студента плагин прозрачен: дополнительных действий от него не требуется. Цели:

- загрузить файл-ответ через стандартный элемент «Задание» Moodle;
- опционально увидеть индикатор «проверено на самостоятельность» в личном кабинете, если преподаватель открыл эту настройку;
- получить оценку в обычные сроки.

Прозрачность — принципиальное требование. Если студенту придётся что-то дополнительно подтверждать, плагин столкнётся с сопротивлением и превратится в формальность.

### 2.2.3 Администратор Moodle

Техническая роль. Цели:

- установить плагин за 5 минут: распаковать ZIP в `mod/assign/feedback/samost`, выполнить `upgrade.php`, активировать в настройках задания;
- задать пороги срабатывания по умолчанию (высокий 60%, низкий 20%) и параметры очереди;
- просматривать агрегированную статистику по кафедре или факультету для отчётности.

По опыту автора, именно короткая инструкция установки определяет, появится ли плагин на других кафедрах после первого внедрения. Moodle Plugin Types описывает стандартный путь установки плагинов типа assignfeedback [10]; наш плагин следует ему без отклонений.

## 2.3 Бизнес-процессы

### 2.3.1 Процесс «как есть»

Рисунок 2.1 — Диаграмма бизнес-процесса «как есть» (BPMN)

Разберём текущий процесс пошагово:

1. Студент загружает файл-ответ в элемент «Задание» до срока сдачи.
2. По истечении срока Moodle закрывает приём файлов, работы фиксируются в базе.
3. Преподаватель открывает в браузере каждый файл по очереди.
4. Глазом сверяет содержимое с уже просмотренными работами, документирование отсутствует.
5. Принимает субъективное решение: самостоятельно или нет.
6. Выставляет оценку в стандартной форме.

Узкое место — четвёртый шаг. Именно там происходит попарное или, чаще, выборочное сравнение. Решение не документируется и не воспроизводится. Если студент оспорит оценку, преподаватель не сможет предъявить формальное обоснование: «Мне показалось, что ваш абзац про CQRS слишком похож на работу Иванова». Коваленко фиксирует эту проблему как одну из ключевых барьеров доверия к дистанционной оценке [7].

### 2.3.2 Процесс «как будет»

Рисунок 2.2 — Диаграмма бизнес-процесса «как будет» (BPMN)

Ниже приведена предлагаемая последовательность:

1. Студент загружает файл обычным способом, интерфейс Moodle не меняется.
2. По истечении срока сдачи Moodle Cron триггерит плагин.
3. Плагин создаёт задачи в очереди `samost_queue` — по одной записи на каждую уникальную пару работ.
4. Воркер по расписанию извлекает текст, считает шинглы, вычисляет коэффициент Жаккара для каждой пары.
5. Результаты сохраняются в таблицу `samost_results` с процентом схожести и массивом совпадающих фрагментов.
6. Преподаватель заходит на страницу задания и видит цветовую матрицу пар: зелёная зона (до 20%) безопасна, жёлтая (20-60%) требует внимания, красная (выше 60%) почти гарантированно содержит заимствование.
7. Клик на подозрительную ячейку открывает детализацию: две колонки текста с подсветкой совпадающих фрагментов.
8. Преподаватель принимает обоснованное решение и выставляет оценку.

Экономия времени предварительно оценивается так: вместо 7,5 часов ручного сравнения для группы 25 студентов преподаватель тратит 10-15 минут на просмотр красных ячеек и проверку выделенных фрагментов. Фоновая серверная обработка для той же группы укладывается примерно в 15 минут при однопоточном воркере. Получаем коэффициент примерно 30× по времени преподавателя, точные замеры приведём в главе 4.

## 2.4 Карта пользовательских историй

Рисунок 2.3 — Карта пользовательских историй

Карту мы построили по методу Джеффа Паттона: горизонталь — последовательность действий в процессе, вертикаль — приоритеты MoSCoW. Горизонтальный «хребет» содержит пять этапов процесса: настройка, загрузка работ, запуск проверки, просмотр результата, принятие решения. Под каждым этапом — истории, раскрашенные по приоритету.

Таблица 2.1 — Пользовательские истории

| ID | Роль | История | Этап |
|----|------|---------|------|
| US-01 | Администратор | Установить плагин за 5 минут, чтобы не перегружать службу поддержки | Настройка |
| US-02 | Преподаватель | Включить проверку в настройках задания одним чекбоксом | Настройка |
| US-03 | Студент | Загружать файл обычным способом без дополнительных действий | Загрузка |
| US-04 | Преподаватель | Получать уведомление о завершении проверки | Запуск |
| US-05 | Преподаватель | Видеть таблицу пар с цветовой шкалой | Просмотр |
| US-06 | Преподаватель | Раскрывать пару и видеть выделенные фрагменты | Просмотр |
| US-07 | Преподаватель | Экспортировать отчёт в CSV для учёта | Решение |
| US-08 | Администратор | Настраивать пороги срабатывания | Настройка |

Приоритеты распределены так. US-01, US-02, US-03, US-05, US-06 относятся к MVP: без них плагин бесполезен для пользователя. US-04 и US-08 попадают в Should — полезные улучшения, которые можно поставить во вторую итерацию. US-07 — Could: экспорт нужен не каждому преподавателю, но без него система кажется незаконченной в глазах методиста. Такой приоритет соответствует реальному порядку внедрения: сначала MVP для пилотной кафедры, затем расширение.

## 2.5 Диаграмма вариантов использования

Рисунок 2.4 — Диаграмма вариантов использования (UML use case)

Фаулер рекомендует диаграммы use case как самое наглядное средство для фиксации границ системы и взаимодействия акторов с ней [20]. На нашей диаграмме четыре актора: Преподаватель, Студент, Администратор Moodle и системный актор Cron (планировщик Moodle). Восемь основных вариантов использования:

- загрузить работу (Студент);
- настроить задание с включённой проверкой самостоятельности (Преподаватель);
- запустить проверку вручную (Преподаватель);
- запустить проверку по расписанию (Cron);
- просмотреть отчёт о попарной схожести (Преподаватель);
- раскрыть детализацию пары (Преподаватель);
- настроить плагин (Администратор);
- установить или обновить плагин (Администратор).

Связи include раскрывают внутреннюю структуру. Вариант «Запустить проверку» включает три обязательных подварианта: «Извлечь текст из файла», «Вычислить отпечатки (шинглы)», «Сохранить результаты в `samost_results`». Связь extend фиксирует опциональное расширение: «Просмотреть отчёт» может быть расширен вариантом «Экспортировать в CSV», но клиент выбирает это действие по желанию.

Разделение ручного и автоматического запуска в двух отдельных вариантах — сознательное решение. Ручной запуск нужен, когда преподаватель хочет перепроверить группу после загрузки дополнительной работы опоздавшим студентом. Автоматический запуск по Cron — базовый сценарий для массовой эксплуатации. Вариант «Раскрыть детализацию» отделён от «Просмотреть отчёт», потому что это самостоятельное действие с отдельным AJAX-запросом и отдельным шаблоном вывода.

## 2.6 Ключевые сценарии взаимодействия

### Сценарий 1: полный цикл проверки группы 25 студентов

Проследим путь от момента сдачи до готового отчёта.

- Шаг 1. 23:59 воскресенья: последний студент загрузил файл DOCX. В Moodle лежит 25 работ. Действие пользователя → реакция: срок сдачи истёк, приём файлов закрыт.
- Шаг 2. 00:00 понедельника: Moodle Cron вызывает колбэк плагина. Действие → реакция: плагин проверяет, что задание настроено на проверку самостоятельности, и создаёт 300 записей в `samost_queue`.
- Шаг 3. 00:01: плагин запускает извлечение текста из файлов средствами PhpWord [21], нормализует пробелы и пунктуацию, сохраняет чистый текст в `samost_texts`.
- Шаг 4. 00:02: воркер читает очередь и последовательно обрабатывает пары. Для каждой пары строит множество шинглов длины 4, вычисляет коэффициент Жаккара.
- Шаг 5. 00:15: очередь опустела, 300 результатов записаны. Триггер на таблице обновляет агрегированные метрики задания.
- Шаг 6. 07:30: плагин отправляет преподавателю уведомление Moodle «Проверка группы ЭФБО-06-22 завершена, 7 пар в красной зоне».
- Шаг 7. 09:00: преподаватель открывает страницу задания и видит цветовую матрицу. Действие → реакция: 293 ячейки зелёные или жёлтые, 7 красных выделены рамкой.
- Шаг 8. 09:10: беглый просмотр семи подозрительных пар занимает около 10 минут. Преподаватель выставляет 25 оценок и закрывает задание.

### Сценарий 2: раскрытие подозрительной пары

- Шаг 1. Преподаватель кликает на красную ячейку «Иванов × Петров, 78%». Действие → реакция: JavaScript отправляет AJAX-запрос `/mod/assign/feedback/samost/details.php?pair_id=142`.
- Шаг 2. Сервер PHP извлекает из `samost_results` запись с массивом совпадающих фрагментов: смещения, длина, хеш шингла.
- Шаг 3. Возврат JSON с двумя текстами и списком `{offset, length}` для каждой работы.
- Шаг 4. Mustache-шаблон [22] рендерит две колонки, подсвечивая совпадающие фрагменты жёлтым фоном.
- Шаг 5. Преподаватель видит, что совпадают три подряд идущих абзаца про CQRS и Event Sourcing. Действие → реакция: нажатие «Отметить как плагиат», в журнал оценок пишется комментарий с ID пары.

## Выводы по главе 2

В этой главе решена задача 2 — проведено моделирование предметной области системы оценивания студентов.

Проанализирован текущий процесс ручной проверки: для группы 25 студентов одно задание требует до 7,5 часов внимания преподавателя при честном попарном сравнении, а в реальной практике систематика заменяется выборочной проверкой, теряющей воспроизводимость.

Выделены три актора — преподаватель, студент, администратор Moodle — с конкретными целями и зонами ответственности. Построены BPMN-диаграммы процессов «как есть» и «как будет», зафиксирована предварительная оценка экономии времени преподавателя примерно в 30 раз.

Сформирована карта из восьми пользовательских историй, распределённых по пяти этапам процесса и трём уровням приоритетов MoSCoW. Диаграмма вариантов использования покрывает все сценарии взаимодействия четырёх акторов с системой, включая связи include и extend. Два ключевых сценария расписаны пошагово.

Полученные модели служат входными данными для проектирования архитектуры плагина, схемы хранения и пользовательского интерфейса в главе 3.
