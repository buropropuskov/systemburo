# 3 ПРОЕКТИРОВАНИЕ ПЛАГИНА И ИНТЕГРАЦИЯ В MOODLE

## 3.1 Выбор архитектурного подхода

Вторая глава завершилась перечнем функциональных и нефункциональных требований. Дальше возникает развилка: как именно реализовать модуль проверки самостоятельности внутри инфраструктуры вуза? На наш взгляд, вариантов ровно три.

Первый — микросервис с REST-API. Отдельный контейнер поднимает PHP-сервис, Moodle обращается к нему по HTTP, обменивается JSON. Красиво с точки зрения разделения ответственности, но данные студентов покидают контур LMS. Для вуза, хранящего персональные данные по ФЗ-152, это дополнительный контур защиты, дополнительный SLA, дополнительный аудит. Второй вариант — внешний скрипт, запускаемый cron и работающий с файлами Moodle напрямую. Проще первого, но ломает модель прав доступа: скрипт обходит систему ролей, а значит, обходит и аудит действий. Третий — нативный плагин типа `plagiarism` в Moodle Plugin API [10]. Данные не покидают процесс LMS, используются штатная ORM, штатная очередь задач, штатная система прав.

Мы выбрали третий путь. Heller в руководстве по расширению Moodle формулирует принцип прямо: «расширение через Plugin API сохраняет совместимость с будущими версиями платформы» [23]. Moodle поддерживает 15 типов плагинов [10], и тип `plagiarism` существует именно для нашего сценария: внешняя проверка отправленных работ с возвратом оценки схожести [11]. Пересобирать ядро не нужно, обновления LMS не ломают плагин.

Архитектурная основа — слоистая модель, которую описал Мартин в «Чистой архитектуре»: зависимости направлены внутрь, бизнес-логика изолирована от UI и БД [24]. Для выбора алгоритма по типу файла применён паттерн Strategy [25]: интерфейс «сравнить два документа» имеет несколько реализаций — шинглы для текста, Winnowing для кода. Для реакции на загрузку студенческой работы — паттерн Observer [25]: Moodle публикует событие `file_uploaded`, плагин его слушает и ставит задачу в очередь.

## 3.2 Архитектура плагина

Плагин разделён на три слоя. Графически структура показана на Рисунке 3.1.

**Рисунок 3.1 -- Архитектура плагина (слоистая)**

Верхний слой — интерфейс. Шаблонизатор Mustache [22] рендерит страницы отчёта и попарного сравнения, Bootstrap 5 [26] отвечает за сетку и базовые компоненты, AJAX-запросы подгружают тяжёлые фрагменты (совпадающие куски текста) по требованию. Физически слой представлен файлами `report.php`, `pair.php` и поддиректорией `tabs/`, где хранятся частичные шаблоны вкладок отчёта. Преподаватель взаимодействует только с этим слоем.

Средний слой — обработка данных. Сюда входят извлечение текста из бинарных форматов, нормализация содержимого, постановка задач в очередь. Ключевые классы: `classes/text_extractor.php` занимается декодированием DOCX, PDF и XLSX; `classes/file_types.php` определяет тип файла по расширению и MIME; `classes/task/process_queue.php` реализует scheduled-task Moodle и поштучно разбирает очередь. Слой обработки изолирован от UI: он не знает ни о Mustache, ни о Bootstrap, он просто получает `fileid` и возвращает очищенный текст.

Нижний слой — анализ. Единственный существенный класс, `classes/analyser.php`, содержит реализацию обоих алгоритмов сравнения. На вход получает два очищенных текста, на выход выдаёт коэффициенты схожести и список совпадающих фрагментов. Слой анализа не знает, откуда пришли тексты и куда уйдут результаты; это чистая алгоритмическая функция.

Путь запроса таков: преподаватель открывает страницу отчёта, UI дёргает Moodle Plugin API (реализованный в `lib.php`), тот обращается к слою обработки за новыми файлами, слой обработки передаёт извлечённый текст в слой анализа, результаты сохраняются в собственные таблицы плагина через штатную Moodle DB API [16]. Обратный путь короче: UI читает готовые результаты прямо из таблицы `plagiarism_samost_results`. За счёт такого разделения очередь и анализ работают в фоне (cron), а преподаватель видит свежие данные без задержек.

## 3.3 Интеграция с Moodle Plugin API

Plugin API — это набор точек расширения, куда платформа сама вызывает код плагина в нужные моменты [10]. Для типа `plagiarism` базовый контракт описан в абстрактном классе `plagiarism_plugin` [11]: плагин обязан унаследоваться от него и переопределить ключевые методы. Перечень использованных нами точек собран в Таблице 3.1.

**Таблица 3.1 -- Используемые точки расширения Moodle Plugin API**

| Точка расширения | Назначение | Файл плагина |
|------------------|------------|--------------|
| `plagiarism_plugin::get_file_results()` | Возврат результата по конкретному файлу | `lib.php` |
| `plagiarism_plugin::get_links()` | Вставка кнопки «Отчёт» в интерфейс проверки | `lib.php` |
| Event observer `file_uploaded` | Реакция на загрузку студенческой работы | `lib.php`, `db/events.php` |
| `scheduled_task` | Фоновая обработка очереди по расписанию | `classes/task/process_queue.php`, `db/tasks.php` |
| `admin_setting_*` | Форма глобальных настроек плагина | `classes/form/admin_settings.php`, `settings.php` |
| `capability` | Права доступа (`plagiarism/samost:viewreport`) | `db/access.php` |
| `get_string` | Локализация строк интерфейса | `lang/ru/`, `lang/en/` |

Семь точек покрывают весь жизненный цикл работы: от конфигурации через событие загрузки и фоновой обработки до показа результатов преподавателю. Event observer через `db/events.php` регистрируется у ядра Moodle декларативно — достаточно описать массив `$observers` с именем события и callback-методом, платформа сама подпишет обработчик [11]. Scheduled-task работает аналогично: класс-наследник `\core\task\scheduled_task` регистрируется через `db/tasks.php` и получает вызовы с указанной периодичностью (мы поставили раз в минуту), причём Moodle гарантирует, что одновременно выполняется только один экземпляр задачи.

Плагин следует Moodle Coding Style [16]: префикс всех функций и классов — `plagiarism_samost_`, имена файлов в нижнем регистре, методы классов в `snake_case`, классы — в `lowercase_with_underscores` (это отличие от PSR-подобного `PascalCase`, но такова конвенция Moodle). Строки интерфейса вынесены в `lang/`, прямых SQL-запросов нет — только DB API [16].

**Таблица 3.2 -- Собственные таблицы плагина**

Связи с ядром Moodle ссылаются на три стандартные сущности: `mdl_user` (пользователи), `mdl_assign` через поле `cm` (course module id — уникальный идентификатор экземпляра модуля задания) и `mdl_files` через `fileid` (физические файлы вложений). Каскадного удаления на уровне СУБД мы не ставим: Moodle использует DB API, который не всегда прокидывает `ON DELETE CASCADE` одинаково в PostgreSQL и MySQL. Очистка происходит через hook `plagiarism_samost_uninstall()` и при удалении курса.

Почему таблиц именно пять? Кеш извлечённого текста (`plagiarism_samost_files`) заведён отдельно не ради красоты, а ради экономии времени: извлечение PDF весом 10 МБ занимает 5–8 секунд [28], и повторять эту операцию при каждом попарном сравнении бессмысленно. Кеш индексирован по паре `(cm, userid)` и по `fileid`; обновляется только при замене файла. Очередь вынесена в отдельную таблицу по причине, знакомой всем, кто имел дело с фоновыми задачами: если откатить транзакцию, в которой сидят и бизнес-данные, и запись очереди, теряются соседние задачи [16]. Таблица результатов хранит попарные коэффициенты — как текстовой схожести, так и схожести кода, — что позволяет быстро строить матрицу N×N в отчёте без повторного запуска анализа.

Отдельно стоит таблица обратной связи `plagiarism_samost_feedback`: когда преподаватель оставляет комментарий к паре работ, он сохраняется вместе со «снимком» схожести на момент комментария (поля `snap_similarity_code`, `snap_similarity_text`). Это снимает проблему «комментарий остался, а схожесть после перезапуска изменилась».

## 3.5 Алгоритмы сравнения

### 3.5.1 Шинглы и коэффициент Жаккара для текста

Для естественного языка мы применяем шинглы и коэффициент Жаккара. Метод опубликован Бродером в 1997 году [8], выдержал двадцать восемь лет критики и остаётся базовой линией в задачах поиска почти-дубликатов. Формула проста:

$$J(A, B) = \frac{|A \cap B|}{|A \cup B|}$$

где A и B — множества шинглов (хешированных фрагментов) двух документов. Значение J лежит в отрезке от нуля (документы не пересекаются) до единицы (идентичны). Проценты в интерфейсе мы получаем умножением на сто.

Пайплайн содержит пять шагов. Шаг первый — нормализация: текст приводится к нижнему регистру, удаляются знаки препинания, множественные пробелы сжимаются до одного, выполняется нормализация переносов. Шаг второй — разбиение на k-шинглы. При k=4 из фразы «кот сидел на крыше дома» получаются два шингла: «кот сидел на крыше» и «сидел на крыше дома». Шаг третий — хеширование каждого шингла (CRC32 достаточно, коллизии при объёмах курсовой работы пренебрежимы). Шаг четвёртый — формирование множеств хешей A и B. Шаг пятый — вычисление J(A, B) по формуле.

Почему k=4? При k=2 половина шинглов состоит из общеупотребительных сочетаний вроде «в том», «на что», «и к»; они одинаково встречаются у всех авторов и создают фоновую схожесть 30–40 %. При k=7 алгоритм перестаёт ловить переформулировки: студент поменял местами два слова, и шингл уже другой. Бродер в [8] экспериментально обосновал значения k в диапазоне 3–5 для текстов на естественном языке; Gomaa и Fahmy в обзоре подходов к измерению схожести подтвердили эти значения на современных корпусах [6]. Мы остановились на k=4, установив это по умолчанию, но оставили настраиваемым через `admin_setting` — преподаватель может поднять до 7 для коротких эссе или опустить до 3 для технических отчётов с обилием формул.

### 3.5.2 Winnowing для исходного кода

Исходный код — совсем другая структура. Переменные переименовываются без потери смысла, комментарии удаляются, форматирование меняется. Шинглы на коде дают бесполезный результат: студент заменил `int i` на `int counter`, и схожесть упала с 90 % до 20 %. Для кода мы применяем Winnowing — алгоритм Schleimer, Wilkerson и Aiken, предложенный в 2003 году и лежащий в основе известной системы MOSS [9], [4].

Алгоритм состоит из шести шагов. Шаг первый — токенизация: идентификаторы заменяются на обобщённую метку `__ID__`, строковые литералы на `__STR__`, числовые на `__NUM__`. Переименование переменных после этого не влияет на результат — они все стали одинаковыми. Шаг второй — построение k-грамм: последовательностей из k токенов подряд. Шаг третий — rolling hash: для каждой k-граммы считается хеш, причём алгоритм Рабина–Карпа позволяет получить хеш следующей k-граммы из предыдущего за O(1). Шаг четвёртый — скользящее окно ширины w: в каждой позиции окна выбирается минимальный хеш, при совпадении минимумов — правый (это условие обеспечивает инвариантность к вставкам в начале файла, как доказано в [9]). Шаг пятый — множество выбранных минимумов становится отпечатком документа. Шаг шестой — пересечение отпечатков по формуле Жаккара, как для текста.

Параметры k=5 и w=4 взяты из оригинальной работы [9]. Авторы математически доказали, что при таких значениях гарантируется обнаружение любого совпадения длиной не менее k+w-1=8 токенов, а средняя плотность отпечатка составляет 2/(w+1) ≈ 0,4. На практике это означает: отпечаток файла в 500 токенов содержит примерно 200 хешей — достаточно для точного сравнения, но в два с половиной раза меньше исходного объёма.

### 3.5.3 Сопоставление алгоритмов и типов файлов

Выбор конкретного алгоритма определяется расширением и MIME-типом загруженного файла. Стратегия выбора собрана в Таблице 3.3.

**Таблица 3.3 -- Соответствие алгоритмов и типов файлов**

| Тип файла | Алгоритм | Обоснование |
|-----------|----------|-------------|
| DOCX, PDF, TXT, ODT | Шинглы + Жаккар | Естественный язык, важна фразовая структура |
| Python, Java, C++, PHP (исходный код) | Winnowing | Токенизация устойчива к переименованиям |
| XLSX | Шинглы на строковом представлении | Таблица сводится к тексту с разделителями |

Класс `classes/file_types.php` инкапсулирует это решение, а `classes/analyser.php` выступает контекстом паттерна Strategy [25]. Добавить новый формат (например, LaTeX) значит дописать одну ветку в `file_types.php` — остальной код не меняется. Подход с обобщённой семантикой через латентный семантический анализ [29] мы сознательно оставили за рамками: он требует обучающего корпуса на языке предметной области и вычислительно тяжелее в десятки раз.

## 3.6 Обработка форматов файлов

Перед запуском алгоритма сравнения плагину нужен чистый текст. Студенческие работы приходят в DOCX, PDF, реже XLSX; исходный код — в текстовых файлах разных расширений. Используемые библиотеки собраны в Таблице 3.4.

**Таблица 3.4 -- Библиотеки извлечения текста**

| Формат | Библиотека | Лицензия | Применение |
|--------|-----------|----------|------------|
| DOCX | PhpOffice\PhpWord [21] | LGPL 3.0 | Парсинг XML-структуры архива |
| PDF | Smalot\PdfParser [28] | LGPL 3.0 | Извлечение текстового слоя |
| XLSX | PhpOffice\PhpSpreadsheet [30] | LGPL 3.0 | Чтение ячеек листов |
| Исходный код | Встроенные средства PHP 8.1 [31] | — | Прямое чтение через `file_get_contents` |

Все три библиотеки распространяются по LGPL 3.0 и совместимы с лицензией GPL v3, под которой распространяется Moodle [10]. Смысл лицензионной совместимости: никаких юридических препятствий для вуза при разворачивании плагина. Подключаются библиотеки через Composer, вендоринг лежит в директории `vendor/` — этот подход стандартен для современных плагинов Moodle.

Для исходного кода собственной нормализации больше, чем кажется. Мы удаляем однострочные комментарии (`//` в C-подобных языках, `#` в Python), многострочные (`/* ... */` и `""" ... """`), сжимаем пробельные символы, приводим переводы строк к LF. Без этих шагов студент получает формальную схожесть 40 % только из-за того, что у одного файл с CRLF (Windows), а у другого — с LF (Linux). Следует признать, что нормализация комментариев — компромисс: осмысленные комментарии на русском содержат фразовые совпадения, ценные для обнаружения заимствований. Однако на практике код списывают вместе с комментариями переведёнными или выкинутыми, и потеря этого сигнала не критична.

## 3.7 UI-сценарий и страница отчёта

UI-часть плагина скромна, но продумана. Макет страницы отчёта показан на Рисунке 3.3.

**Рисунок 3.3 -- Макет страницы отчёта**

Элементов на странице шесть. Первый — заголовок вида «Проверка самостоятельности — [имя задания]», чтобы преподаватель не запутался, открыв несколько вкладок с разными заданиями. Второй — блок метрик: всего проверено пар, сколько из них с высокой схожестью (более 60 %), сколько со средней (от 20 до 60 %), средняя схожесть по всем парам. Метрики рассчитываются один SQL-запросом прямо из `plagiarism_samost_results` — индекс по `cm` делает операцию моментальной. Третий — матрица N×N, где N — число сданных работ, а ячейка окрашена по шкале: зелёный до 20 %, жёлтый от 20 до 60 %, красный выше 60 %. Четвёртый — попарное сравнение по клику на ячейку: AJAX-запрос к `pair.php` возвращает две панели с подсвеченными совпадающими фрагментами, модалка открывается без перезагрузки страницы. Пятый — кнопки действий: «Скачать CSV», «Пометить как проверено», «Перезапустить проверку». Шестой — форма обратной связи, сохраняемая в `plagiarism_samost_feedback`.

Технологический выбор для фронтенда минималистичен: Mustache как штатный шаблонизатор Moodle [22], Bootstrap 5 для сетки и типографики [26], ванильный JavaScript (без jQuery и тяжёлых фреймворков) для AJAX через встроенный в Moodle модуль `core/ajax`. Такой набор совместим с любым уровнем кастомизации темы LMS и не тянет за собой сборку Webpack.
