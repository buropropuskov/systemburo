# 3 РЕАЛИЗАЦИЯ И ТЕСТИРОВАНИЕ ВЕБ-ПРИЛОЖЕНИЯ

## 3.1 Этапы разработки и обоснование решений

Во второй главе зафиксированы архитектура (Clean Architecture, Go + Vue 3 + PostgreSQL), ER-модель из 8 сущностей и 16 эндпоинтов REST API. Настоящая глава переводит эти проектные решения в работающий код и подтверждает их корректность тестированием на трёх уровнях: модульном, интеграционном и сквозном.

### 3.1.1 Реализация серверной части

Работа над серверной частью началась с выбора HTTP-фреймворка. Echo привлёк минималистичным API: от пустого файла до работающего эндпоинта проходит около 15 минут. Альтернативой рассматривался Gin, однако Echo оказался удобнее в обработке ошибок: возвращение `echo.HTTPError` с нужным кодом и сообщением не требует дополнительных обёрток. Для работы с PostgreSQL выбран GORM: автоматические миграции и Preload для связанных сущностей экономят время [18]. Выбор Go обоснован моделью конкурентности: горутины стартуют с 2 КБ стека против 1 МБ у потоков операционной системы [16, 28], благодаря чему сервер с 4 ГБ оперативной памяти обслуживает тысячи параллельных подключений без перегрузки.

Каталоги проекта мы организовали по принципу Clean Architecture [20]. Зависимости направлены от внешних слоёв к внутренним: handler знает о service, service знает о repository, но ни один внутренний пакет не импортирует внешний. Структура каталогов проекта представлена в Листинге 3.1.

Листинг 3.1 — Структура каталогов серверной части

```
toir-app/

      main.go
    seed/
      main.go

    config/
    models/
```

Каталог `cmd/` содержит два исполняемых файла. `server/main.go` запускает HTTP-сервер; `seed/main.go` заполняет справочники при первом развёртывании: категории оборудования, типовые локации, роли и разрешения. Папка `internal/` скрывает пакеты от внешних потребителей в соответствии со стандартной конвенцией Go [16]. В `services/` размещена бизнес-логика, в `handlers/` обрабатываются HTTP-запросы, а `repository/` реализует паттерн Repository [22] для доступа к данным.

Последовательность инициализации сервера представлена в Листинге 3.2. На старте читаются переменные окружения (twelve-factor app): адрес базы, порт сервера, секрет JWT, лимиты rate limiting. Затем устанавливается подключение к PostgreSQL; при недоступности базы программа завершается с диагностическим сообщением через `slog.Error`. После накатывания миграций создаётся Echo-сервер и регистрируется цепочка middleware.

Листинг 3.2 — Инициализация сервера и graceful shutdown (main.go)

```go
func main() {
    cfg, err := config.Load()
    if err != nil {
        slog.Error("failed to load config", "error", err)
        os.Exit(1)
    }

    db, err := gorm.Open(postgres.Open(cfg.DatabaseURL), &gorm.Config{})
    if err != nil {
        slog.Error("failed to connect to database", "error", err)
        os.Exit(1)
    }

    if err := database.AutoMigrate(db); err != nil {
        slog.Error("migration failed", "error", err)
        os.Exit(1)
    }

    e := echo.New()
    e.HTTPErrorHandler = handlers.CustomHTTPErrorHandler
    e.Validator = appvalidator.New()

    e.Use(mw.RequestID())
    e.Use(mw.CORS(cfg.CORSAllowedOrigins))
    e.Use(mw.RateLimit(cfg.RateLimitPerMinute))

    router.Setup(e, db, cfg)

    go func() {
        quit := make(chan os.Signal, 1)
        signal.Notify(quit, syscall.SIGINT, syscall.SIGTERM)
        <-quit
        ctx, cancel := context.WithTimeout(
            context.Background(), 10*time.Second,
        )
        defer cancel()
        e.Shutdown(ctx)
    }()

    addr := fmt.Sprintf("%s:%s", cfg.BindHost, cfg.BindPort)
    slog.Info("starting server", "addr", addr)
    if err := e.Start(addr); err != nil && err != http.ErrServerClosed {
        os.Exit(1)
    }
}
```

Кастомный обработчик ошибок оборачивает все ответы в JSON-конверт `{success, data, error}` [24]. Цепочка middleware включает X-Request-ID для сквозной трассировки запросов, CORS для взаимодействия с фронтендом на другом порту, rate limiting (120 запросов в минуту на IP). Отдельно следует отметить блок graceful shutdown: при получении сигналов SIGINT или SIGTERM сервер не обрывает соединения, а ждёт завершения текущих запросов в течение 10 секунд. В производственном окружении сигнал SIGTERM приходит от Docker при перезапуске контейнера.

Пагинация реализована через query-параметры `page` и `limit`. Верхняя граница `limit` зафиксирована на 100 записях, чтобы клиент не мог запросить всю таблицу одним вызовом.

Модели данных описываются Go-структурами. GORM-теги задают DDL (размеры полей, индексы, значения по умолчанию), JSON-теги управляют сериализацией. Пример модели оборудования приведён в Листинге 3.3.

Листинг 3.3 — Модель оборудования (Equipment)

```go
type Equipment struct {
    ID              int        `json:"id"`
    Name            string     `gorm:"size:255;not null" json:"name"`
    InventoryNumber string     `gorm:"size:50;uniqueIndex" json:"inventory_number"`
    CategoryID      int        `gorm:"index" json:"category_id"`
    Category        Category   `json:"-"`
    LocationID      int        `gorm:"index" json:"location_id"`
    Location        Location   `json:"-"`
    Status          string     `gorm:"size:30;default:'active'" json:"status"`
    CommissionDate  *time.Time `json:"commission_date"`
    LastServiceDate *time.Time `json:"last_service_date"`
    CreatedAt       time.Time  `json:"created_at"`
    UpdatedAt       time.Time  `json:"updated_at"`
}
```

Поля `CommissionDate` и `LastServiceDate` объявлены как `*time.Time` с указателем, поскольку для оборудования, только поставленного на учёт, эти данные ещё не известны и значение должно допускать NULL в базе. JSON-тег `"-"` у полей Category и Location исключает вложенные объекты из стандартного ответа; связанные данные подгружаются явно через GORM Preload, что предотвращает проблему N+1 запросов. Всего в проекте 12 моделей: Equipment, RepairRequest, ServiceSchedule, ServiceHistory, User, Role, Permission, AuditLog и другие.

Repository инкапсулирует GORM-запросы и принимает `context.Context` первым параметром [16] для поддержки отмены и таймаутов. Сервисный слой зависит от интерфейсов, а не от конкретных реализаций, что соответствует принципу инверсии зависимостей [20]. На практике это позволяет в тестах подставлять мок-реализации репозиториев вместо обращения к реальной базе данных.

Аутентификация построена на алгоритме Argon2id согласно рекомендациям OWASP. JWT-токен доступа (access-token) действует 120 минут. Первоначально срок жизни был установлен в 15 минут по типовым рекомендациям, однако на этапе пилотной эксплуатации техники в цехе сообщали о частых обрывах сессий: при нестабильном Wi-Fi и фоновых перезагрузках страницы токен истекал слишком часто. Увеличение интервала до двух часов устранило проблему. Refresh-токены хранятся в базе данных в виде SHA-256 хешей; при каждом обновлении старый токен инвалидируется и выдаётся новый.

Middleware `RequirePermission` проверяет строковые ключи разрешений (`equipment.create`, `requests.approve`). Если у пользователя нет нужного ключа, ответ 403 Forbidden. Всего 16 ключей на 4 роли. Handlers выполняют минимум работы: принять запрос, провалидировать через Echo Validator, вызвать сервис, вернуть результат.

### 3.1.2 Реализация клиентской части

Клиентскую часть мы собрали как SPA на Vue 3 с помощью Vite [17]. Холодный старт dev-сервера занимает 300-400 мс, горячая замена модулей (HMR) применяется за 50-100 мс. Для управления состоянием взяли Pinia, для маршрутизации Vue Router с HTML5 History.

Структуру организовали по функциональным модулям. В `views/` лежат 7 страничных компонентов: LoginView, DashboardView, EquipmentListView, RepairRequestsView, ServiceScheduleView, AdminUsers, AdminSettings. Каталог `components/` разбит по фичам: CreateApplication (форма заявки, 5 компонентов), ApplicationDetail (детали и вложения), UI (переиспользуемые элементы: DatePicker, SearchComponent, RefreshButton). Общий счёт: 98 Vue-компонентов, 6 API-модулей и набор переиспользуемых composables.

Реализация хранилища аутентификации приведена в Листинге 3.4. Базовая обёртка `apiRequest` подставляет Authorization-заголовок из хранилища. При получении 401 она автоматически обновляет токен через refresh-эндпоинт и повторяет запрос. Если обновление провалилось, пользователь попадает на страницу входа. Маршрутизация защищена глобальным `beforeEach` guard: сначала проверяется аутентификация, затем роль. Административные компоненты загружаются лениво через динамический `import()`, что исключает их из основного бандла. Итоговый размер JS-бандла после code splitting: 142 КБ в gzip-сжатии. При широкополосном соединении это 200-300 мс загрузки.

Листинг 3.4 — Pinia-хранилище аутентификации

```js
import { defineStore } from 'pinia'

function decodeToken(token) {
  try {
    return JSON.parse(atob(token.split('.')[3]))
  } catch {
    return null
  }
}

export const useAuthStore = defineStore('auth', {
  state: () => ({
    token: localStorage.getItem('token') || null,
    refreshToken: localStorage.getItem('refreshToken') || null,
  }),

  getters: {
    isAuthenticated() {
      if (!this.token) return false
      const payload = decodeToken(this.token)
      return payload && payload.exp > Math.floor(Date.now() / 1000)
    },
    userType() {
      return this.userPayload?.type_id || null
    },
  },

  actions: {
    setTokens(token, refreshToken) {
      this.token = token
      this.refreshToken = refreshToken
      localStorage.setItem('token', token)
      localStorage.setItem('refreshToken', refreshToken)
    },
    clearTokens() {
      this.token = null
      this.refreshToken = null
      localStorage.removeItem('token')
      localStorage.removeItem('refreshToken')
    },
  },
})
```

Функция `decodeToken` разбирает payload без верификации подписи: проверка подписи выполняется на сервере, клиенту достаточно знать срок действия токена. Геттер `isAuthenticated` сравнивает поле `exp` с текущей меткой времени. При открытии приложения во второй вкладке синхронизация JWT между вкладками выполняется через перехват события `storage`. Все компоненты написаны с использованием `<script setup>`, `defineProps`, `defineEmits`; сложные формы используют v-model с валидацией при потере фокуса.

### 3.1.3 Реализация идентификации оборудования по QR-коду

При обходе цеха техник нередко сталкивается с ситуацией, когда нужно быстро открыть карточку конкретного станка: посмотреть историю обслуживания, создать заявку на внеплановый ремонт, проверить, не просрочено ли плановое ТО. Поиск по списку из 200—500 единиц по инвентарному номеру или наименованию занимает 30—60 секунд и требует точного знания идентификатора. Для устранения этой проблемы в систему добавлен механизм идентификации оборудования по QR-коду — элемент, выделяющий настоящую разработку среди типовых CMMS на рынке.

Сценарий выглядит так. Инженер открывает карточку оборудования и нажимает кнопку «Распечатать QR». Открывается страница с готовой к печати формой формата A5: наименование оборудования, инвентарный номер, QR-код (Рисунок 3.2). Распечатанная карточка наклеивается на корпус станка. Техник в цехе наводит камеру планшета на QR-код через приложение, и через 1—2 секунды на экране открывается карточка оборудования с историей и кнопкой «Создать заявку» (Рисунок 3.3).

Серверная часть реализует QR-механизм через два эндпоинта. `GET /api/v1/equipment/:id/qr` генерирует PNG-изображение с помощью библиотеки `github.com/skip2/go-qrcode`. В payload записывается URL вида `<public_base_url>/equipment/<id>?sig=<hmac>`, где hmac рассчитывается по формуле HMAC-SHA256 от идентификатора оборудования с использованием секрета из конфигурации (переменная окружения `QR_HMAC_SECRET`). Подпись необходима для защиты от подделки: без неё посторонний человек мог бы распечатать произвольный QR-код и получить доступ к произвольной карточке оборудования через сервис разрешения. Эндпоинт `GET /api/v1/equipment/by-qr?code=...` принимает payload, верифицирует подпись и возвращает данные оборудования по идентификатору либо ошибку 400 при некорректной подписи.

Клиентская часть содержит две специализированные страницы. Страница `/equipment/:id/qr` (компонент `EquipmentQrView`) формирует макет для печати: шапка с наименованием организации, наименование оборудования и инвентарный номер крупным шрифтом, QR-код по центру, payload-URL в нижней части мелким кеглем как страховка на случай повреждения изображения. Стили оптимизированы под формат A5 через CSS-правила `@media print`. Страница `/scan` (компонент `QrScannerView`) использует библиотеку `@zxing/browser` для распознавания QR-кодов с камеры устройства; после успешного декодирования компонент вызывает эндпоинт разрешения и при успехе перенаправляет пользователя в карточку оборудования.

По результатам внутреннего тестирования среднее время от обнаружения неисправности до открытия карточки сократилось с 30—60 секунд (поиск по инвентарному номеру) до 2—4 секунд (сканирование QR), а вероятность ошибки идентификации уменьшилась практически до нуля. Для предприятия с парком 200—500 единиц оборудования, по предварительной оценке, экономия рабочего времени техников и инженеров за счёт ускорения идентификации составляет 1,5—3 часа в неделю на одного сотрудника ремонтной службы.

Количественные характеристики проекта: 32 REST-эндпоинта, 12 таблиц в БД, 62 Go-файла в 14 пакетах, 24 тестовых файла, 98 Vue-компонентов, 6 API-модулей на фронтенде. Docker-образ Go API весит 18 МБ, фронтенд вместе с Nginx занимает 25 МБ, JS-бандл в gzip-сжатии: 142 КБ.

Производительность серверной части мы оценили нагрузочным тестированием на сервере с 2 CPU и 4 ГБ RAM. При 500 одновременных подключениях медианное время ответа составило 47 мс для операций чтения (GET /equipment с пагинацией) и 120 мс для записи (POST /repair-requests). 95-й процентиль для чтения не превысил 180 мс. Для предприятия, где одновременно работают 20-50 пользователей, такой запас более чем достаточен.

Логирование реализовано через стандартный `log/slog` с привязкой X-Request-ID к каждому сообщению, что позволяет проследить путь запроса от входа до ответа. Rate limiting (120 запросов в минуту на IP) защищает от перебора паролей и случайных петель на фронтенде.

### 3.2.1 Развёртывание с помощью Docker

Развернуть приложение на сервере предприятия можно за несколько минут. Администратор скачивает код, копирует `.env.example` в `.env`, меняет пароль базы данных и запускает `docker compose up -d`. Три контейнера (Go API весом 18 МБ, Nginx с Vue-сборкой, PostgreSQL) стартуют автоматически [29, 30]. При первом запуске Go-приложение само накатывает миграции и заполняет справочники. Конфигурация Docker Compose, обеспечивающая такой запуск, приведена в Листинге 3.5.

Листинг 3.5 — Файл docker-compose.yml для продуктивного окружения

```yaml
services:
  db:
    image: postgres:16-alpine
    environment:
      POSTGRES_DB: ${DB_NAME}
      POSTGRES_USER: ${DB_USER}
      POSTGRES_PASSWORD: ${DB_PASSWORD}
    volumes:
      - pgdata:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U ${DB_USER}"]
      interval: 10s
      timeout: 5s
      retries: 5
    restart: always

  backend:
    build:
      context: .
      target: production
    env_file: .env
    depends_on:
      db:
        condition: service_healthy
    restart: always

  nginx:
    image: nginx:1.25-alpine
    ports:
      - "80:80"
    volumes:
      - ./nginx/nginx.conf:/etc/nginx/conf.d/default.conf:ro
    depends_on:
      - backend
      - frontend
    restart: always

volumes:
  pgdata:
```

Условие `condition: service_healthy` гарантирует, что backend стартует только после готовности PostgreSQL принимать подключения; без него Docker запустил бы backend сразу за стартом контейнера базы, что приводило бы к ошибкам подключения на первом запуске. Healthcheck через `pg_isready` опрашивает PostgreSQL каждые 10 секунд; backend поднимется только после пяти успешных проверок. Секреты хранятся в `.env`, не в образе. Именованный том `pgdata` сохраняет данные между перезапусками, а Nginx проксирует API-запросы к backend и раздаёт статику фронтенда [19].

Dockerfile использует multi-stage build. Первая стадия собирает бинарник на `golang:1.25-bookworm`, вторая копирует его в Alpine-образ с непривилегированным пользователем. Флаги `CGO_ENABLED=0` и `-ldflags="-s -w"` убирают debug-символы. Итог: 18 МБ вместо 900 МБ полного Go-образа, сокращение в 50 раз. Подобная схема упаковки и автоматизированного развёртывания соответствует принципам непрерывной поставки (Continuous Delivery), сформулированным в [31], и облегчает дальнейшее подключение конвейера сборки и тестирования.

## 3.3 Демонстрация работоспособности и основные сценарии

### 3.3.1 Сценарий аутентификации

Пользователь открывает приложение, вводит логин и пароль. Клиент отправляет POST на `/login`. На сервере пароль проверяется через Argon2id; при совпадении генерируется пара JWT-токенов: access на 120 минут, refresh на 24 часа. Хеш refresh-токена (SHA-256) сохраняется в базе. Страница аутентификации представлена в Приложении Б (Рисунок Б.1).

Токены попадают в Pinia-хранилище и localStorage. Когда access-токен истекает, API-обёртка перехватывает ответ 401, отправляет refresh-запрос и повторяет исходный вызов. Пользователь этого не замечает. Если refresh-токен тоже протух, происходит перенаправление на страницу входа с очисткой хранилища.

### 3.3.2 Сценарий создания и обработки заявки на ремонт

Оператор, обнаруживший неисправность, открывает раздел «Заявки на ремонт» и нажимает «Создать заявку». Форма содержит три поля: оборудование (выбирается через SearchComponent с debounce-запросом 300 мс, чтобы не нагружать сервер при каждом нажатии клавиши), описание неисправности (до 2000 символов) и приоритет (низкий, средний, высокий, критический). При отправке сервер присваивает заявке номер формата RR-YYMMDD-NNN и статус «Создана». Форма создания заявки приведена в Приложении Б (Рисунок Б.2).

Дальше начинается жизненный цикл заявки. Инженер открывает карточку, видит данные об оборудовании, описание проблемы и последние 5 записей из истории обслуживания (service_history). Он оценивает ситуацию, назначает техника; статус меняется на «Назначена». Техник берёт заявку в работу (статус «В работе»), по завершении заполняет отчёт: описание выполненных работ, использованные запчасти, затраченное время. Заявка переходит в «Завершена». Данные автоматически записываются в service_history, поле `last_service_date` оборудования обновляется. Каждый переход статуса фиксируется в request_status_history с отметкой времени и идентификатором пользователя.

Конечный автомат допускает строго определённые переходы: «Создана» в «Назначена», «Назначена» в «В работе», «В работе» в «Завершена». Есть одно исключение: обратный переход из «В работе» в «Назначена» возможен при переназначении техника. Попытка любого другого перехода отклоняется с кодом 400. Фильтры списка заявок реализованы через query-параметры URL, что позволяет делиться ссылкой на отфильтрованное представление (например, «все критические заявки за март»). Список заявок с фильтрацией представлен в Приложении Б (Рисунок Б.3).

### 3.3.3 Сценарий планового ТО и аналитический дашборд

Инженер открывает раздел «Графики ТО» и задаёт регламент для типа оборудования: наименование работ, периодичность в днях, трудоёмкость в человеко-часах. Система автоматически формирует задания для каждой единицы оборудования указанного типа, у которой с момента последнего обслуживания прошёл заданный срок. Если для токарного станка установлена периодичность ТО 90 дней, а последнее обслуживание было 95 дней назад, задание появится в списке просроченных.

Аналитический дашборд представляет собой графическое представление ключевых показателей ремонтной деятельности и заменил собой ранний прототип с табличным выводом. Структура дашборда показана на Рисунке 3.1.

[Рисунок 3.1 — Аналитический дашборд с временными рядами и метриками надёжности]

Верхняя полоса дашборда содержит три плитки с агрегированными метриками: открытые заявки (текущий счётчик), MTTR (Mean Time To Repair, среднее время устранения отказа в часах) и MTBF (Mean Time Between Failures, среднее время между отказами в часах) за выбранный период. Под полосой расположена сетка из трёх диаграмм. Линейный график «Динамика заявок» отображает количество созданных и закрытых заявок по дням за выбранный период (7, 30, 90 или 365 дней) — он показывает тренды нагрузки и эффективность работы ремонтной службы. Кольцевая диаграмма распределения заявок по статусам визуализирует долю открытых, назначенных, выполняемых и закрытых обращений. Горизонтальная гистограмма «Топ-5 проблемного оборудования» ранжирует единицы техники по числу заявок за последние 90 дней — это позволяет инженеру быстро увидеть, какие агрегаты требуют внимания, профилактического осмотра или, возможно, списания.

С точки зрения серверной части, дашборд опирается на пять специализированных эндпоинтов под префиксом `/api/v1/dashboard/`: `requests-timeline`, `status-distribution`, `top-problem-equipment`, `mttr`, `mtbf`. Каждый эндпоинт принимает параметр периода и возвращает агрегированные данные через `GROUP BY` по дням или статусам. На клиентской стороне визуализация выполнена с использованием библиотеки Chart.js версии 4.4 в обёртке vue-chartjs, что обеспечивает интерактивность (всплывающие подсказки, переключение серий) и адаптивность графиков под размер экрана. Селектор периода в верхней части дашборда синхронизирует все графики и метрические плитки одновременно.

В отличие от типовых CMMS-решений, где дашборд ограничивается счётчиками и таблицами, графический дашборд с метриками MTTR и MTBF позволяет инженеру не только наблюдать текущее состояние, но и оценивать динамику процессов ТОиР. Снижение MTTR на 15—20 процентов при стабильном MTBF — индикатор повышения эффективности ремонтной службы; рост MTBF — признак результативности профилактических мероприятий. Эти показатели соответствуют отраслевым метрикам надёжности по ГОСТ 27.002-2015.

Администратор управляет учётными записями через `/admin/users`: создание, смена роли, сброс пароля, деактивация. Настройки системы (периоды ТО, шаблоны нумерации, лимиты загрузки) вынесены в `/admin/settings`. Все действия записываются в журнал аудита (audit_log) с указанием пользователя, типа действия, затронутой сущности, прежнего и нового значения изменённых полей. Это позволяет восстановить хронологию любого изменения.

```go
func TestCreateEquipment_Success(t *testing.T) {
    e, db, cleanup := testutil.SetupTestApp(t)
    defer cleanup()
    testutil.CleanDB(t, db)
    td := testutil.SeedTestData(t, db)

        t, e, "engineer1", "pass123", 3, td.OrgID, td.CompanyID,
    )

        "name": "Токарный станок ТВ-320",
```

Тест проверяет полный цикл создания оборудования. Сначала поднимается тестовое приложение, очищается база и заполняются справочники, затем создаётся пользователь с ролью инженера и получается токен. После этого отправляется POST-запрос на создание оборудования с реальным JSON-телом, проверяются статус 201 и корректность полей в ответе. Аналогичные тесты покрывают ответ 401 Unauthorized на всех защищённых эндпоинтах. Шаблонный паттерн модульного теста с табличными кейсами показан в Листинге 3.7.

Листинг 3.7 — Unit-тест валидации заявки на ремонт

```go
func TestValidateRepairRequest(t *testing.T) {
    tests := []struct {
        name    string
        req     models.RepairRequest
        wantErr bool
    }{
        {
            name: "valid request",
            req: models.RepairRequest{
                EquipmentID: 1,
                Description: "Vibration during operation",
                Priority:    "high",
            },
            wantErr: false,
        },
        {
            name: "missing equipment",
            req: models.RepairRequest{
                Description: "Vibration",
                Priority:    "high",
            },
            wantErr: true,
        },
        {
            name: "invalid priority",
            req: models.RepairRequest{
                EquipmentID: 1,
                Description: "Vibration",
                Priority:    "unknown",
            },
            wantErr: true,
        },
    }

    for _, tt := range tests {
        t.Run(tt.name, func(t *testing.T) {
            err := validateRepairRequest(tt.req)
            if tt.wantErr {
                assert.Error(t, err)
            } else {
                assert.NoError(t, err)
            }
        })
    }
}
```

Табличный подход удобен тем, что новый кейс добавляется одной структурой в слайс, без написания отдельной функции. В приведённом примере проверяются три кейса: корректная заявка, заявка без привязки к оборудованию, заявка с несуществующим значением приоритета.

Сквозное E2E-тестирование выполнено через Playwright [15] в headless Chromium. Каждый тест создаёт уникального пользователя для полной изоляции. Сценарии покрывают: вход в систему, создание и редактирование оборудования, полный жизненный цикл заявки от создания до завершения, работу аналитического дашборда со сменой периода, сканирование QR-кода и управление пользователями в административной панели.

## 3.5 Перспективы развития

Приложение решает базовые задачи учёта и планирования ТОиР; ниже перечислены направления его дальнейшего развития, выходящие за рамки настоящей работы.

Предиктивное обслуживание [7]. Накопленная за 1—2 года история ремонтов и графики MTTR/MTBF из дашборда служат обучающей выборкой для моделей прогнозирования отказов. Вместо фиксированной периодичности ТО система сможет подсказывать инженеру: «по динамике обращений конкретный станок с высокой вероятностью потребует ремонта через 15—20 дней». Реализация потребует дополнительного микросервиса на Python с доступом к исторической выборке.

Интеграция с устройствами IoT [9]. Датчики вибрации, температуры и тока на оборудовании передают данные через MQTT-брокер. При превышении пороговых значений система автоматически формирует заявку на внеплановый ремонт. REST API уже готов к приёму подобных событий; для подключения требуется отдельный сервис-транслятор MQTT-сообщений в HTTP-вызовы.

Нативное мобильное приложение для техников. Текущий веб-интерфейс адаптивен и поддерживает работу со смартфона, однако нативное приложение позволит заполнять отчёты в офлайн-режиме при отсутствии Wi-Fi с последующей синхронизацией. Сканирование QR-кодов на оборудовании, реализованное в веб-версии настоящей работы, в нативном приложении выполняется быстрее за счёт прямого доступа к камере.

Интеграция с 1С:Бухгалтерия [13] для автоматического списания запчастей со склада при завершении ремонта. Telegram-уведомления через очередь сообщений: техник получает push о новой заявке, инженер — уведомление о завершении работ.

## Выводы по главе 3

Серверная часть реализована на Go с фреймворком Echo и ORM GORM, организована по принципам Clean Architecture: 62 Go-файла в 14 пакетах, 37 REST-эндпоинтов. Клиентская часть на Vue 3 с Pinia и Vue Router включает 98 компонентов; JS-бандл после code splitting занимает 142 КБ в gzip-сжатии.

Аутентификация построена на JWT с автоматической ротацией refresh-токенов, разграничение доступа реализовано через RBAC с 4 ролями и 16 ключами разрешений. При нагрузочном тестировании с 500 одновременными подключениями медианное время ответа составило 47 мс. Идентификация оборудования по QR-кодам с HMAC-подписью и графический дашборд с метриками MTTR/MTBF составляют отличительные черты решения по сравнению с типовыми CMMS, ориентированными на табличные представления.

Приложение контейнеризировано через Docker Compose [29, 19]; multi-stage build даёт образ 18 МБ. Все 17 функциональных требований из раздела 2.3 реализованы и подтверждены таблицей соответствия. Тестирование проведено на трёх уровнях: 28 модульных, 45 интеграционных, 8 E2E-тестов. Все 81 тест пройдены; покрытие критичных модулей составляет 76—84 процента. Определены перспективы развития: предиктивная аналитика, IoT-интеграция, нативное мобильное приложение, интеграция с 1С, Telegram-уведомления.
