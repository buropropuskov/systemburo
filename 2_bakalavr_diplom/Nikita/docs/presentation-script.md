Добрый день, уважаемые члены государственной экзаменационной комиссии! Меня зовут Никита Суднишников, группа ЭФБО-06-22. ## [Слайд 2 — Актуальность] ~45 сек

Начну с актуальности. Каждый промышленный завод тратит от пятнадцати до сорока процентов операционного бюджета на поддержание оборудования в рабочем состоянии. При бумажном документообороте, который до сих пор распространён на средних предприятиях, до двадцати процентов заявок на ремонт теряется в цепочке «оператор — диспетчер — техник». Время реакции на поломку достигает четырёх-восьми часов.

Крупные CMMS-системы, SAP PM или IBM Maximo, стоят от десяти миллионов рублей только за лицензию. Облачные сервисы дешевле, но хранят данные за рубежом. Для завода среднего масштаба, на двести-восемьсот единиц оборудования, отсутствует доступная отечественная альтернатива. Именно эту нишу закрывает моя разработка.

## [Слайд 3 — Объект, предмет, цель, задачи] ~45 сек

Объектом исследования являются процессы технического обслуживания и ремонта оборудования промышленного предприятия. Предмет — веб-приложение для управления этими процессами.

Цель работы: повысить эффективность ТОиР за счёт централизованного учёта оборудования, автоматизации планирования регламентных работ и ускорения обработки заявок. Для достижения цели поставлено семь задач: от анализа предметной области и обзора существующих решений до проектирования архитектуры, базы данных, реализации и тестирования.

## [Слайд 4 — Обзор CMMS-систем] ~40 сек

В первой главе я сравнил четыре ведущие CMMS-системы. 1С:ТОИР — от трёхсот тысяч рублей, требует штатного программиста 1С. SAP PM — десять-пятнадцать миллионов рублей за внедрение. IBM Maximo — тридцать тысяч долларов в год, ориентирован на крупные холдинги. UpKeep — сорок пять долларов в месяц, но данные хранятся за рубежом.

Вывод очевиден: для заводов среднего масштаба, где парк — пара сотен станков и команда — пять-пятнадцать ремонтников, ни одна из этих систем не подходит. Это обосновало собственную разработку.

## [Слайд 5 — Выбор технологического стека] ~35 сек

Стек я выбирал под два сценария: десятки операторов одновременно создают заявки, а бэкенд держит стабильное время ответа. Go с фреймворком Echo даёт конкурентность через горутины и компилируется в один бинарник размером восемнадцать мегабайт. Vue 3 с Composition API и Pinia — лёгкий фреймворк, ядро весит тридцать три килобайта. PostgreSQL версии 16 выбран из-за ACID-гарантий и JSONB-полей. Всё собирается в Docker и разворачивается одной командой.

Python был отвергнут из-за GIL, Node.js — из-за однопоточности event loop под нагрузкой, React — из-за большего веса по сравнению с Vue.

## [Слайд 6 — Роли пользователей и требования] ~30 сек

В системе выделено четыре роли: оператор создаёт заявки, техник их выполняет, инженер планирует регламентное ТО и смотрит отчётность, администратор управляет пользователями и справочниками. На основе ролей и бизнес-процессов сформулировано пятнадцать функциональных и двенадцать нефункциональных требований. Контроль доступа реализован через RBAC на шестнадцати ключах, аутентификация — JWT с refresh-токенами.

## [Слайд 7 — User Story Map] ~25 сек

Для перехода от требований к плану разработки я построил User Story Map — карту пользовательских сценариев. Она охватывает весь путь от регистрации пользователя до закрытия наряда и включает семь ключевых историй. Каждая история привязана к требованиям и служит основой для тестов.

## [Слайд 8 — Архитектура приложения] ~40 сек

Архитектура серверной части построена по принципам Clean Architecture: слои handler, service, repository разделены, зависимости инвертированы. Шестьдесят два Go-файла распределены по четырнадцати пакетам и обслуживают тридцать два REST-эндпоинта, задокументированных в Swagger. Клиентская часть — девяносто восемь Vue-компонентов с Pinia-сторами и ленивой загрузкой админ-модулей.

Между фронтом и бэком стоит Nginx: он одновременно раздаёт собранный Vue-бандл и проксирует API-запросы, что даёт single-origin для SPA. Настроены rate limiting сто двадцать запросов в минуту и graceful shutdown.

## [Слайд 9 — Модель данных] ~25 сек

База данных содержит восемь основных сущностей и двенадцать таблиц. Центральная связка — оборудование, заявки, история обслуживания. Отдельно смоделирован RBAC: пользователь, роль, разрешение. У таблицы оборудования есть JSONB-поле для расширяемых характеристик — это избавляет от изменения схемы при появлении нового типа станка.

## [Слайд 10 — Интерфейс: заявки] ~35 сек

Ключевой сценарий системы — обработка заявок. Оператор заполняет форму: выбирает оборудование из справочника, указывает тип проблемы, срочность, прикрепляет фото. Заявка проходит шесть состояний: Новая, Принята, В работе, На проверке, Закрыта, Архив. Список заявок фильтруется по статусу, исполнителю, типу оборудования. Просроченные заявки подсвечиваются, уведомления приходят ответственному технику.

## [Слайд 11 — Интерфейс: оборудование и ТО] ~30 сек

Для управления парком предусмотрены карточки оборудования: паспорт станка, журнал выполненных работ, расписание регламентного ТО, прикреплённые документы. Список оборудования сортируется по цеху, состоянию, наработке. Графики ТО рассчитываются автоматически по циклу и часам работы. Когда подходит срок обслуживания, система сама формирует наряды.

## [Слайд 12 — Дашборд и API] ~25 сек

Дашборд инженера показывает три ключевые метрики: активные заявки, загрузку техников, процент выполнения ППР. Данные обновляются в реальном времени. Все тридцать два REST-эндпоинта задокументированы в Swagger; из того же OpenAPI-спека можно генерировать типобезопасных клиентов. Токены JWT хранятся в httpOnly-cookie, активна CSRF-защита и строгие CSP-заголовки.

## [Слайд 13 — Тестирование и нагрузка] ~40 сек

Тестирование проведено на трёх уровнях. Двадцать восемь модульных тестов проверяют доменную логику, сорок пять интеграционных — связку с PostgreSQL через testcontainers, восемь сквозных — пользовательские сценарии через Playwright. Все восемьдесят один тест пройдены успешно. Общее покрытие — шестьдесят восемь процентов; для критичных модулей, аутентификации и обработки заявок, покрытие составляет семьдесят шесть — восемьдесят четыре процента.

В нагрузочном тестировании через k6 при пятистах одновременных подключениях медиана ответа составила сорок семь миллисекунд, девяносто пятый процентиль — сто восемьдесят. Весь стек собирается в Docker-образы: Go API восемнадцать мегабайт, Nginx с фронтендом — двадцать пять. Развёртывание занимает одну команду `docker compose up -d`.

Подведу итог. Все семь задач решены. Теоретическая значимость работы: анализ ниши среднего бизнеса в CMMS-сегменте и проектирование модели RBAC для ТОиР. Практическая значимость: приложение готово к внедрению, развёртывание не требует специализированных компетенций. Для собственной карьеры работа стала опытом полного цикла full-stack-разработки: Go, Vue 3, PostgreSQL, Docker, Playwright, Clean Architecture.

## Возможные вопросы комиссии и заготовки ответов

**В.** Почему Go, а не Python или Java?
**О.** Go даёт простую конкурентность через горутины, компилируется в один бинарник без зависимостей, имеет низкое потребление памяти. Python ограничен GIL, Java требует JVM и больше ресурсов. Для веб-приложения с одновременным доступом десятков пользователей Go — оптимальный компромисс между простотой и производительностью.

**В.** Как обеспечивается безопасность?
**О.** Четыре уровня: JWT-токены в httpOnly-cookie с refresh-ротацией, CSRF-защита на state-changing эндпоинтах, CSP-заголовки против XSS, RBAC на шестнадцати ключах доступа. Пароли хешируются через bcrypt, SQL-инъекции невозможны из-за prepared statements GORM.

**В.** Как масштабировать систему на несколько заводов?
**О.** На уровне одного инстанса Go-API поддерживает пятьсот одновременных соединений. Горизонтальное масштабирование: несколько реплик Go-API за балансировщиком, общая PostgreSQL с read-репликами. Для мультизаводской версии в модели можно ввести tenant_id и развести данные на уровне политик PostgreSQL RLS.

**В.** Почему не использовали готовые компоненты UI (Ant Design, Element Plus)?
**О.** Базовый UI собран на минимальных компонентах Vue с CSS-модулями, что даёт контроль над размером бандла (142 КБ gzip) и брендируемостью под предприятие. Компонентные библиотеки добавили бы 200–400 КБ, что для внутренней системы избыточно.

**В.** Что из текущего решения пригодно для продакшена прямо сейчас?
**О.** Все функциональные требования покрыты, тесты зелёные, Docker-развёртывание отработано, безопасность базового уровня реализована. Перед реальным запуском понадобится: организационно — обучение операторов, технически — настройка бэкапов PostgreSQL и мониторинга (Prometheus + Grafana, точки уже предусмотрены в коде через endpoint /metrics).
