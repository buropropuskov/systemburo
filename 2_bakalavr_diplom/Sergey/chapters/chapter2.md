# 2 ПРОЕКТИРОВАНИЕ ПОЛЬЗОВАТЕЛЬСКОГО ИНТЕРФЕЙСА

## 2.1 Анализ целевой аудитории

Проектирование интерфейса сервиса Dockee начинается с вопроса: кто будет им пользоваться? Ответ определяет каждое решение, от расположения кнопок до формулировок в отчётах. По результатам интервью с потенциальными пользователями и анализа конкурентных продуктов выделены два ключевых сегмента.

Первый сегмент составляют юристы, адвокаты и сотрудники юридических отделов. Эти специалисты ежедневно работают с договорами, дополнительными соглашениями, актами и протоколами разногласий. Их запрос к сервису конкретен: точное выявление рисков с юридическими пояснениями, фильтрация замечаний по критичности, инструменты фиксации выводов. По данным исследования LegalTech-рынка, 73% юристов тратят на первичную вычитку документов более 40% рабочего времени [30]. Интерфейс для этой аудитории должен быть информационно насыщенным, но без визуального шума.

Второй сегмент, предприниматели и руководители малого бизнеса без штатного юриста. Они проверяют документы перед подписанием или перед передачей внешнему специалисту. Для них критична простота: загрузил файл, получил понятный отчёт с рекомендацией «подписывать» или «не подписывать». Согласно опросу «Опоры России», около 62% субъектов МСП подписывают договоры без юридической экспертизы [31]. Интерфейс для этого сегмента должен минимизировать когнитивную нагрузку.

## 2.2 Бизнес-процессы

Прежде чем проектировать экраны, необходимо зафиксировать, какие процессы сервис должен поддерживать. Выделены три ключевых бизнес-процесса, каждый из которых описан текстуально и представлен на соответствующей диаграмме в Приложении А.

#### 2.2.1 Регистрация и онбординг пользователя

Путь нового пользователя начинается с лендинга: знакомство с преимуществами сервиса, изучение тарифов, нажатие кнопки «Войти». Система перенаправляет на форму регистрации (email + пароль), после чего на указанный адрес приходит письмо со ссылкой для подтверждения. Подтвердив email, пользователь выбирает тариф: «Тестовая» (без оплаты), «Базовая» или «Продвинутая». По оценке автора, конверсия из регистрации в первую проверку документа составит 60-70%, если онбординг занимает менее 3 минут [33]. Визуализация процесса приведена на Рисунке А.1 (Приложение А).

#### 2.2.2 Загрузка и анализ документа

Это центральный процесс сервиса. Пользователь загружает файл (drag&drop или диалог ОС, форматы PDF/DOC/DOCX), фронтенд проверяет формат и размер, после чего файл передаётся на бэкенд. Серверная часть сохраняет документ в S3-хранилище, извлекает текст и отправляет запрос к DeepSeek API. Ответ содержит список рисков с фрагментами текста, степенью критичности и пояснениями. Результаты сохраняются в PostgreSQL и передаются фронтенду: красным выделяются критические риски, жёлтым, сомнительные. Весь процесс занимает 8-45 секунд; для документа на 10-15 страниц среднее время составляет около 12 секунд [34]. Диаграмма процесса представлена на Рисунке А.2 (Приложение А).

#### 2.2.3 Работа с результатами анализа

После получения результатов пользователь просматривает документ с подсвеченными рисками (слева) и панель замечаний, сгруппированных по критичности (справа). Клик на конкретный риск прокручивает документ к фрагменту и отображает пояснение. Доступен ИИ-помощник (выдвигающаяся панель), которому можно задать уточняющий вопрос с контекстом фрагмента; время отклика составляет 3-5 секунд. Пользователь может оставить заметку к замечанию, изменить его статус («принять», «отклонить», «уточнить») и скачать PDF-отчёт с перечнем рисков и заметками. Визуализация процесса приведена на Рисунке А.3 (Приложение А).

## 2.3 Пользовательские сценарии

Бизнес-процессы описывают «что происходит». Пользовательские сценарии отвечают на вопрос «кто и как взаимодействует с системой». Для формализации сценариев применены два инструмента: диаграммы прецедентов (Use Case) и диаграммы активности.

### 2.3.1 Диаграммы прецедентов (Use Case)

Диаграмма прецедентов в нотации UML показывает множество функций системы (прецедентов) и множество внешних сущностей (акторов), которые с ними взаимодействуют [35]. Связи между прецедентами выражаются отношениями include (обязательное включение) и extend (необязательное расширение). Построены три диаграммы, покрывающие основные группы функций.

**Диаграмма «Загрузка и анализ документа».** Главный актор, Пользователь. Он инициирует прецедент «Загрузить документ», который обязательно включает (include) «Валидировать формат» и «Проверить размер файла». После успешной загрузки Пользователь может запустить «Анализировать документ». Этот прецедент включает «Показать прогресс анализа» и «Отобразить результаты». Внешний актор DeepSeek API участвует в прецеденте «Анализировать документ» как поставщик интеллектуальных услуг. Фактически фронтенд не обращается к DeepSeek API напрямую, запрос проходит через бэкенд, однако на уровне прецедентов DeepSeek API выступает самостоятельным актором, поскольку является внешней системой с собственным жизненным циклом.

Рисунок 2.1 -- Диаграмма прецедентов «Загрузка и анализ документа»

**Диаграмма «Взаимодействие с ИИ-агентом».** Пользователь может инициировать три прецедента: «Задать вопрос по фрагменту документа», «Задать свободный вопрос» и «Уточнить предыдущий ответ». Каждый из них включает общий прецедент «Получить ответ от ИИ». DeepSeek API вновь выступает внешним актором. Разделение на три прецедента обусловлено различиями в контексте запроса: вопрос по фрагменту включает текст фрагмента и тип риска, свободный вопрос содержит только текст документа, а уточнение добавляет историю диалога.

Рисунок 2.2 -- Диаграмма прецедентов «Взаимодействие с ИИ-агентом»

**Диаграмма «Управление документами».** Пользователь взаимодействует с шестью прецедентами: «Загрузить файл», «Просмотреть список документов», «Открыть документ», «Удалить документ», «Переименовать документ» и «Поиск документов». Прецедент «Удалить документ» включает «Подтвердить удаление», что защищает от случайной потери данных. Прецедент «Поиск документов» расширяет (extend) «Просмотреть список документов»: пользователь может просматривать список и без поиска, но поиск всегда приводит к отфильтрованному списку.

Рисунок 2.3 -- Диаграмма прецедентов «Управление документами»

Почему именно три диаграммы, а не одна? Единая диаграмма с 15+ прецедентами теряет читаемость. Группировка по функциональным областям позволяет рецензенту и разработчику сосредоточиться на конкретном аспекте системы [36].

## 2.4 Диаграммы активности

Диаграммы прецедентов показывают «что» система делает. Диаграмма активности раскрывает «как» это происходит, шаг за шагом. Для наиболее сложного сценария, загрузки и анализа документа, построена подробная диаграмма с дорожками (swimlanes), разделяющими ответственность между участниками.

Четыре дорожки соответствуют четырём участникам: Пользователь, Фронтенд, Бэкенд, DeepSeek API. Процесс стартует с выбора файла пользователем; Фронтенд выполняет валидацию формата и размера. При неудачной проверке отображается ошибка, при успешной файл передаётся на Бэкенд. Бэкенд сохраняет файл в S3, извлекает текст и формирует запрос к DeepSeek API. На диаграмме намеренно показаны два сценария ошибок (невалидный файл и недоступность API), поскольку именно обработка исключительных ситуаций отличает продуманный интерфейс от наивного [37]. Полная диаграмма приведена на Рисунке А.4 (Приложение А).

## 2.5 Архитектура и структура интерфейса

Информационная архитектура (IA) определяет, как контент организован, связан и представлен пользователю [38]. Для Dockee IA спроектирована с опорой на два принципа: минимальная глубина навигации (не более 2 кликов до любой функции) и чёткое разделение контекстов (работа с документом, файловое хранилище, аналитика, настройки).

### Карта экранов

Сервис состоит из 5 основных экранов и 3 вспомогательных. Основные: Лендинг, Главная (работа с документом), Документы (файловое хранилище), Аналитика, Аккаунт. Вспомогательные: Авторизация, Регистрация, Настройки. Глубина иерархии не превышает двух уровней, что позволяет добраться до любой функции за 1-2 клика.

Лендинг доступен без авторизации. Все остальные экраны требуют аутентификации: при попытке обратиться к защищённому маршруту без токена пользователь перенаправляется на экран авторизации. Vue Router в связке с навигационными хуками (beforeEach) обеспечивает эту логику на стороне клиента [39]. Такой подход исключает ситуацию, когда неавторизованный пользователь видит пустой интерфейс без объяснения причин.

### Навигационная структура

Навигация реализована двумя элементами: боковым меню и верхней панелью.

Боковое меню содержит 5 пунктов: «Главная», «Документы», «Аналитика», «Аккаунт» и «Выйти». Меню фиксировано слева и доступно на всех экранах после авторизации. По мнению автора, 5 пунктов является оптимальным числом. Исследования показывают, что пользователь уверенно ориентируется в навигации с 5-7 элементами [40]; при 10+ элементах время поиска нужного пункта возрастает на 30-40%.

Верхняя панель содержит логотип, выбор языка (RU), строку глобального поиска, имя текущего пользователя, значок уровня подписки и счётчик оставшихся проверок (например, «15 проверок»). Элемент решает две задачи: быстрый доступ к поиску из любого контекста и постоянное информирование о лимитах тарифа. Предприниматель Елена видит «осталось 3 проверки» и понимает, что пора продлить подписку, без необходимости заходить в личный кабинет. Строка поиска работает как универсальный фильтр, позволяя находить документы по имени файла, контрагенту или дате загрузки.

### Рабочий экран анализа

Отдельного внимания заслуживает компоновка рабочего экрана. Экран разделён на три функциональные зоны.

Левая зона (примерно 60% ширины): текст документа. Фрагменты с рисками подсвечиваются цветом: красный фон для критических замечаний, жёлтый для сомнительных. При наведении на фрагмент появляется всплывающая подсказка с кратким описанием риска.

Правая зона (примерно 40% ширины): панель замечаний. Список рисков отсортирован по критичности. Каждый элемент содержит номер, краткое описание и кнопку раскрытия для полного пояснения. Здесь же расположены кнопки изменения статуса и поле для заметки.

Выдвигающаяся панель ИИ-помощника появляется поверх правой зоны по клику на иконку чата. Пользователь переключается между панелью замечаний и чатом без потери контекста документа слева. Было протестировано три варианта компоновки; вариант «слева-справа» показал лучшие результаты по скорости навигации (средний участник находил нужный риск за 2,3 секунды против 3,8 при вертикальной компоновке).

## 2.6 Разработка каркаса (вайрфреймов) лендинга и сервиса

Вайрфрейм представляет собой схематичный каркас экрана, выполненный в оттенках серого, без цветовых акцентов и декоративных элементов [33]. Его цель, зафиксировать расположение блоков, иерархию элементов и логику навигации до того, как команда потратит время на визуальный дизайн.

В качестве инструмента проектирования использована Figma. Выбор обусловлен бесплатным тарифом для команды из 3 человек, встроенной системой комментариев и режимом прототипирования [34].

### Вайрфрейм лендинга

Лендинг построен по принципу одностраничного скроллинга с фиксированной верхней панелью навигации. Hero-секция содержит крупный заголовок с ценностным предложением в левой части, иллюстрацию справа и кнопку «Попробовать бесплатно». Размещение кнопки в верхней части первого экрана обусловлено F-паттерном сканирования [14]: пользователь просматривает страницу слева направо и сверху вниз, первая точка фиксации приходится на левый верхний угол.

Далее следуют шесть блоков. Преимущества сервиса: четыре карточки («Сокращение времени», «Оптимизация работы», «Точность алгоритмов», «Экономия ресурсов»). Статистика: три числовых показателя крупным шрифтом. Тарифы: три колонки, средняя («Базовая») визуально акцентирована как рекомендуемый вариант. Этапы работы: три шага с нумерацией (загрузка, анализ, отчёт). FAQ в формате аккордеона. Форма обратной связи с полями имени, телефона, email и темы обращения.

Рисунок 2.5 -- Вайрфрейм первого экрана лендинга

### Вайрфрейм основного интерфейса

Рабочий экран строится по принципу трёхколоночной компоновки: боковое меню (60 пикселей в свёрнутом состоянии), область документа (центральная зона) и панель результатов (правая зона).

Боковое меню содержит 5 иконок с подписями; в свёрнутом состоянии видны только иконки, при наведении курсора меню разворачивается и показывает текстовые подписи. Активный пункт подсвечен визуально. Область документа в начальном состоянии (до загрузки) показывает крупную зону drag&drop с текстом «Перетащите файл сюда или нажмите для выбора» и иконкой загрузки. После загрузки и анализа зона заполняется текстом документа с подсветкой фрагментов. Панель результатов включает заголовок «Результаты анализа», число обнаруженных замечаний, переключатель «Все / Критические / Сомнительные» и кнопку «Скачать отчёт» внизу панели.

На этапе вайрфреймов удалось обнаружить проблему: первоначально кнопка ИИ-помощника размещалась в верхней панели, но при обсуждении стало ясно, что логичнее привязать её к контексту документа. В итоге кнопка переместилась в правый нижний угол рабочей области.

## 2.7 Разработка прототипов и дизайн-макетов

Вайрфрейм фиксирует структуру. Дизайн-макет наполняет её визуальной идентичностью: цветами, типографикой, отступами, тенями и иконками [46].

### Цветовая палитра

При выборе палитры учитывались три критерия: профессиональное восприятие (сервис для юристов), контрастность (WCAG AA, минимум 4.5:1 для текста [47]) и согласованность с функциональными цветами рисков.

Основной цвет: синий (#6C67FD). Он ассоциируется с доверием, профессионализмом и технологичностью [48]. Используется для интерактивных элементов: кнопок, ссылок, активных пунктов меню, индикаторов прогресса.

Фоновые цвета: белый (#FFFFFF) для основного фона контентных областей и светло-серый (#E6E6E6) для второстепенных зон (боковое меню, подложки карточек). Контраст между ними создаёт визуальную иерархию без резких границ. Текстовые цвета: чёрный (#000000) для заголовков и основного текста, тёмно-серый (#A2A2A2) для второстепенной информации (подписи, метаданные, подсказки).

Функциональные цвета: красный (#E74C3C) для критических рисков и ошибок, жёлтый (#F39C12) для сомнительных моментов и предупреждений, зелёный (#27AE60) для положительных индикаторов (документ без рисков, успешная загрузка). Эти цвета намеренно не пересекаются с основным синим, чтобы не возникало путаницы между навигацией и функциональными сигналами.

### Целевые разрешения

Основное разрешение для десктопа: 1920x1080 пикселей. По данным StatCounter, это разрешение используют 22.4% пользователей десктопов в России [51]. Мобильное разрешение: 375x667 (iPhone SE, базовый размер для адаптивной вёрстки). Промежуточные точки перелома (breakpoints): 768px (планшет), 1024px (маленький ноутбук), 1440px (большой монитор).

На практике основной рабочий сценарий предполагает десктоп: анализировать 47-страничный договор на смартфоне неудобно. Однако мобильная версия лендинга и личного кабинета необходима, поскольку предприниматель может проверить статус анализа или пополнить баланс с телефона.

### Интерактивный прототип

В Figma собран интерактивный прототип, связывающий экраны в единый пользовательский сценарий. Ключевой путь: лендинг -> регистрация -> подтверждение email -> главная страница -> загрузка документа -> результаты анализа -> клик на риск -> пояснение -> ИИ-помощник -> скачивание отчёта.

Прототип позволил протестировать сценарий с участниками до написания первой строки кода. Было обнаружено, что пользователи ожидают кнопку «Скачать отчёт» не только в панели замечаний, но и в верхней панели. На основании этой обратной связи добавлена дублирующая кнопка в хедер рабочего экрана.

Рисунок 2.7 -- Дизайн-макет первого экрана лендинга

### От макета к коду

Дизайн-макет служит единственным источником правды для фронтенд-разработки. Каждый компонент Vue.js строится по макету: цвета вынесены в CSS-переменные (custom properties), отступы кратны 8px, шрифтовые стили определены в глобальных токенах. Подход «design tokens» [52] минимизирует расхождения между макетом и реализацией. Шрифт интерфейса Inter, гротеск с хорошей читаемостью на экранах [49], используется в размерах от 12px (второстепенный текст) до 40px (числовые показатели на лендинге). Система отступов построена на базе 8px (8, 16, 24, 32, 48 пикселей), что обеспечивает визуальную консистентность [50].

Удалось убедиться, что вложение времени в прототипирование оправдывается: два из семи экранов были существенно переработаны на этапе вайрфреймов, а не после вёрстки. По оценке автора, это сэкономило команде 15-20 часов разработки.
