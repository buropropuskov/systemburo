# Инструкция по сопровождению фронтенда Dockee

Документ описывает регулярные процедуры эксплуатации клиентской части Dockee после запуска в production: мониторинг, релизы, обновления зависимостей, реакция на инциденты. Бэкенд и инфраструктура БД сопровождаются отдельно.

## 1. Мониторинг

### 1.1 Доступность сайта

- **Uptime-пинг**: `https://app.dockee.ru` проверяется каждую минуту сервисом Uptime Kuma (см. `status.dockee.ru`). Алерт в Telegram-канал `#ops-alerts` при двух последовательных неудачах.
- **Health-check nginx**: `/healthz` отдаёт `200 OK` с текстом `ok`. Проверяется load balancer каждые 10 секунд.

### 1.2 Клиентские ошибки

Sentry (проект `dockee-frontend`) собирает JS-ошибки с клиентов. Ключевые метрики на дашборде:

- количество уникальных ошибок в сутки (норма — до 30);
- Crash-Free Sessions Rate (норма — 99.5 %+);
- топ-5 ошибок за неделю.

Триггеры оповещений:

- новая ошибка с частотой ≥ 10 событий за 15 минут;
- падение Crash-Free Sessions Rate ниже 99 %;
- ошибка в файле с версией, не соответствующей текущему релизу (значит, у клиента устаревший bundle — редко, но сигнал).

### 1.3 Производительность

Метрики Core Web Vitals собираются через Web Vitals Library и отправляются в Grafana Cloud. Цели:

| Метрика | Целевое значение | Алерт при |
|---|---|---|
| Largest Contentful Paint (LCP) | < 2,5 с | > 4 с (p75) |
| Interaction to Next Paint (INP) | < 200 мс | > 500 мс (p75) |
| Cumulative Layout Shift (CLS) | < 0,1 | > 0,25 (p75) |
| First Contentful Paint (FCP) | < 1,8 с | > 3 с (p75) |

Еженедельный отчёт по WebVitals автоматически публикуется в `#frontend-weekly`.

### 1.4 Логи nginx

- Access-log: `/var/log/nginx/access.log`, ротация еженедельная через logrotate.
- Error-log: `/var/log/nginx/error.log`, аналогично.
- Счётчик 4xx и 5xx за сутки экспортируется в Prometheus через `nginx-prometheus-exporter`. Алерт при скачке 5xx > 0,5 % за 5 минут.

## 2. Регулярные задачи

### 2.1 Ежедневно (автоматически)

- Uptime-проверка и отчёт по Web Vitals — скриптами.
- Бэкап статики (директория `/var/www/dockee-frontend/`) — rsync на S3, срок хранения 30 дней.
- Проверка срока TLS-сертификатов: certbot renew через systemd-timer.

### 2.2 Еженедельно

- Просмотр дашборда Sentry, триаж новых ошибок.
- Ревью Dependabot-PR (пункт 3.1).
- Анализ аномалий в Web Vitals — какие страницы деградировали.

### 2.3 Ежемесячно

- Обновление минорных версий зависимостей (пункт 3.2).
- Аудит безопасности: `npm audit`, `npx lighthouse-ci`, сканирование CSP.
- Проверка выпущенных TLS-сертификатов (дата обновления, SAN-домены).
- Ревизия прав доступа к deploy-учётке на сервере.

### 2.4 Ежеквартально

- Обновление мажорных версий зависимостей в отдельной ветке (пункт 3.3).
- Нагрузочное тестирование фронтенда с помощью k6.
- Пересмотр политики CSP на актуальность.
- Ротация SSH-ключей deploy-пользователя.

## 3. Обновление зависимостей

### 3.1 Dependabot (автоматически)

В репозитории включён Dependabot для `npm`. Конфигурация `.github/dependabot.yml`:

```yaml
version: 2
updates:
  - package-ecosystem: "npm"
    directory: "/"
    schedule:
      interval: "weekly"
    open-pull-requests-limit: 10
    groups:
      vue-ecosystem:
        patterns: ["vue*", "pinia", "vue-router"]
      build-tools:
        patterns: ["vite*", "@vitejs/*"]
      testing:
        patterns: ["vitest*", "@playwright/*", "@testing-library/*"]
```

PR проверяются CI автоматически. Минорные и патч-обновления мержатся после зелёного билда.

### 3.2 Минорные обновления вручную

```bash
git checkout -b chore/deps-update-YYYY-MM
npm outdated
npm update
npm run test && npm run test:e2e
git commit -am "chore: еженедельное обновление зависимостей"
git push
```

Создаётся PR, после ревью — merge в main.

### 3.3 Мажорные обновления

1. Создать отдельную ветку `chore/vue-3.5-upgrade` (пример для Vue).
2. Обновить по одному пакету, прогоняя тесты после каждого.
3. Проверить сборку (`npm run build`) и размер bundle (`npx vite-bundle-visualizer`).
4. Развернуть на staging-окружении (`staging.dockee.ru`), прогнать полный Playwright-набор.
5. Получить ревью от двух разработчиков.
6. Мержить только после недельного прогона на staging без критичных инцидентов.

## 4. Релизный процесс

### 4.1 Ветка релиза

Используется упрощённый trunk-based flow:

- `main` — всегда готова к релизу.
- Фичи разрабатываются в коротких ветках `feat/*`, `fix/*`, живут не дольше 3 дней.
- PR мержится только после ревью и зелёного CI.

### 4.2 Тег и деплой

```bash
git checkout main
git pull
npm version minor            # 1.0.0 → 1.1.0, создаёт коммит и тег
git push origin main --tags
```

GitHub Actions детектирует push тега `v*` и запускает workflow деплоя (см. deployment.md, раздел 6). Полный цикл от пуша тега до готовой production-сборки — 4–6 минут.

### 4.3 Canary-релиз

Крупные изменения сначала выкатываются на 10 % трафика через feature-flag (`vite-plugin-flags` + внутренняя админка):

1. Флаг выключен — все пользователи видят старую логику.
2. Включить флаг на роль «early-adopter» (около 5 % аудитории).
3. Мониторить Sentry и Web Vitals 24 часа.
4. При отсутствии регрессий — расширение до 100 %.
5. Через неделю — удалить флаг из кода.

### 4.4 Откат

См. `deployment.md`, раздел 8. Решение об откате принимается в течение 10 минут после обнаружения критичной регрессии (Crash-Free Sessions Rate < 99 %, массовые жалобы пользователей, критичная уязвимость).

## 5. Резервное копирование

Фронтенд — статика, содержимое полностью восстанавливается из git и CI. Тем не менее:

- **Статика на сервере**: ежедневный rsync `releases/` в S3-bucket `dockee-frontend-backups`. Срок хранения — 30 дней.
- **Репозиторий**: зеркало из GitHub в Gitea на корпоративный сервер, обновляется ежечасно.
- **CI-артефакты**: сборки каждого тега хранятся в GitHub Packages минимум 90 дней.
- **Секреты CI**: резервируются в 1Password vault `Dockee/CI/Frontend`.

Время восстановления (RTO) из резервной копии: до 30 минут — развернуть последний известный tag из зеркала.

## 6. Реакция на инциденты

### 6.1 Классификация

- **P1** (критичный): сайт недоступен, основной сценарий сломан (регистрация, загрузка, просмотр отчёта). Цель реакции — 15 минут.
- **P2** (высокий): существенная деградация UX, затронуто > 10 % пользователей. Реакция — 1 час.
- **P3** (средний): косметические дефекты, затронуто < 10 %. Реакция — 1 рабочий день.
- **P4** (низкий): улучшения, рефакторинг. По приоритету бэклога.

### 6.2 Протокол для P1 / P2

1. Дежурный получает алерт в Telegram.
2. Открывает канал `#incident-YYYY-MM-DD-short` для текущего инцидента.
3. Подтверждает проблему на production.
4. Принимает решение: откат (первый выбор) или hotfix-ветка.
5. Каждые 15 минут публикует статус в канал и на `status.dockee.ru`.
6. После разрешения — запускается post-mortem (документ в Confluence в течение 48 часов).

### 6.3 Частые сценарии

| Симптом | Быстрая диагностика | Первичное действие |
|---|---|---|
| Белый экран у всех | Консоль браузера, Network: загружается ли `index.html` и bundle | Откат на предыдущий релиз |
| Ошибка 502 от nginx | `systemctl status nginx`, `tail /var/log/nginx/error.log` | Перезапуск nginx, проверка upstream |
| Всплеск 404 на `/assets/*` | Проверить дату последнего деплоя, наличие файлов в `current/assets/` | Перезапустить деплой или откатиться |
| Массовый CORS-error в Sentry | Не деплоился ли бэкенд | Синхронизироваться с командой бэкенда |
| TLS expired | `certbot certificates` | Принудительное обновление `certbot renew --force-renewal` |
| CSP-violation на чужой скрипт | Смотреть отчёты `report-uri` | Проверить код на XSS-уязвимости до послабления CSP |

## 7. Безопасность

### 7.1 Регулярные проверки

- `npm audit` — перед каждым релизом в CI, блокирует деплой при критичных уязвимостях.
- Snyk-сканер — еженедельно, отдельный workflow.
- CSP-отчёты с production пересматриваются раз в две недели.
- Penetration testing — раз в полгода силами внешнего подрядчика.

### 7.2 Обновление секретов

Секреты CI/CD хранятся в GitHub Secrets на уровне environment `production`. Ротация:

- `SSH_PRIVATE_KEY` deploy-пользователя — ежеквартально.
- `VITE_PAYMENT_PUBLIC_KEY` — при смене платёжного провайдера или по требованию безопасности.
- `VITE_SENTRY_DSN` — только при компрометации (DSN публичный, но утечка пишет постороний шум в наш проект).

### 7.3 Управление доступом

- Доступ к deploy-серверу — только по SSH-ключу, паролевая авторизация отключена в `/etc/ssh/sshd_config` (`PasswordAuthentication no`).
- Список разрешённых ключей — в `~/.ssh/authorized_keys` на сервере, синхронизирован с внутренним реестром DevOps.
- `root` SSH-логин запрещён.

## 8. Документирование изменений

- **CHANGELOG.md** в корне репозитория: обновляется при каждом релизе, формат Keep a Changelog.
- **ADR** (Architecture Decision Records) в `docs/adr/`: по одному md-файлу на каждое архитектурное решение.
- **Runbook** инцидентов: `docs/runbooks/*.md`, пополняется после каждого post-mortem.
- Комментарии в коде — только для неочевидных решений (обход багов библиотек, специфические требования браузеров).
