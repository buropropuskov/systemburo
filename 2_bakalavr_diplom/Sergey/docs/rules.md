# Свод правил оформления ВКР Сергея

Единый документ с правилами, по которым собирается `diplom_myakotnykh.docx`. Любая правка должна соответствовать этим правилам. При противоречии с глобальными файлами `~/.claude/CLAUDE.md` и `project/diplom/CLAUDE.md` приоритет — у глобальных правил, а этот файл уточняет их для конкретного диплома.

## 1. Исходные артефакты

- Оригинальный файл от научрука: `diplom_myakotnykh_original.docx` — **не изменять**.
- Рабочий файл для сдачи: `diplom_myakotnykh.docx`.
- Скрипты сборки: `scripts/edit-docx.py`, `scripts/edits_content.py`, `scripts/gen_diagrams.py`, `scripts/gen_plantuml.py`, `scripts/gen_user_story_map.py`.
- Изображения: `images/`.
- Отчёт по изменениям: `CHANGES.md`.

Все скрипты идемпотентны: каждый прогон читает `diplom_myakotnykh_original.docx` и записывает результат в `diplom_myakotnykh.docx`. Повторный запуск даёт идентичный итог.

## 2. Структура документа

Содержание, названия глав и подразделов, а также абзацы оригинала **не меняются**. Допускаются:

- замена нестандартных терминов (см. п. 8);
- перестройка последовательности подразделов главы 2 под этапы проектирования (см. п. 3);
- добавление новых диаграмм и таблиц в соответствии с требованиями;
- короткие обзорные блоки в конец разделов 1.4 и 1.6 (оригинальный текст при этом сохраняется);
- перенос полного перечня требований в Приложение Б, в 1.9 — только обзор основных групп.

Список сокращений (если встречается в старых версиях) удаляется: сокращения расшифровываются при первом упоминании в скобках прямо по тексту. Согласно глобальному `CLAUDE.md`, отдельный раздел «Список используемых сокращений» оставлять не нужно.

## 5. Подписи рисунков, таблиц, листингов

| Объект | Стиль | Выравнивание | Начертание | Разделитель | Пример |
|---|---|---|---|---|---|
| Рисунок | `Normal` 12 пт | по центру | полужирный | тире `–` (en dash) | `Рисунок 2.3 – Диаграмма прецедентов «Управление документами»` |
| Таблица | `Normal` 12 пт | по левому | курсив | тире `–` | `Таблица 2.2 – Сравнение инструментов проектирования` |
| Листинг | `Normal` 12 пт | по левому | курсив | тире `–` | `Листинг 3.1 – Фрагмент Vue-компонента секции лендинга` |

Двойной дефис `--` использовать **нельзя** — только короткое тире `–`. Точка в конце подписи не ставится.

## 6. Порядок «текст → изображение»

Каждый рисунок идёт **после** абзаца, в котором он описан или на который он ссылается. Схема размещения:

```
… текст, описывающий рисунок и ссылающийся на «Рисунок X.Y» …
[изображение]
Рисунок X.Y – Название
… интерпретирующий абзац после рисунка …
```

Перед изображением никогда не идёт подпись и не стоит только пустая строка. Если рисунок иллюстрирует результат выполнения кода — сначала листинг, затем рисунок.

## 7. Стиль диаграмм

**Единая палитра диаграмм**: только три цвета.

| Роль | Цвет |
|---|---|
| Фон | `#FFFFFF` (белый) |
| Контуры, текст, стрелки | `#000000` (чёрный) |
| Акцент (заливка активных узлов, выделение) | `#6C67FD` (синий бренда) |

**Линии и стрелки**: преимущественно прямые (ортогональные), без плавных изгибов. Повороты под 90°. Допустимы диагонали там, где без них диаграмма становится нечитаемой (например, в Use Case связи актор — прецедент).

**Исключения** (не трогаем стиль):

- бизнес-процессы: Рисунки А.1 «Регистрация и онбординг», А.2 «Загрузка и анализ документа», А.3 «Работа с результатами анализа»;
- Рисунок 3.3 «Схема взаимодействия фронтенда и бэкенда».

## 8. Корректность диаграмм по типам

Каждая диаграмма должна соответствовать своему типу:

| Тип | Обязательные элементы |
|---|---|
| Use Case | акторы-«человечки», эллипсы прецедентов, связи include/extend пунктирными стрелками с подписью, рамка системы |
| User flow | прямоугольники шагов, ромбы развилок, чёрные круги начала и конца, подписи веток «да/нет» |
| Диаграмма активности | те же элементы, что и у user flow, но ориентация на внутренние процессы |
| Swimlane | вертикальные/горизонтальные дорожки по ролям, шаги внутри дорожек, стрелки передачи управления |
| Site map | иерархическое дерево страниц от корня, группировка по разделам (публичная / сервис / админка) |
| Sequence | жизненные линии участников, стрелки сообщений между ними, время — сверху вниз |
| Сравнительный график | корректные оси с подписями, легенда, единые единицы измерения |

## 10. Инструменты проектирования (раздел 2.8.1)

Сравнение проводится между тремя инструментами:

- **Figma** — выбран;
- **Adobe Illustrator**;
- **XDesign**.

Критерии сравнения: специализация (UI-интерфейсы vs вектор общего назначения), коллаборация, компонентная система, доступность в РФ, стоимость, экосистема плагинов, экспорт в веб-код.

## 12. Листинги кода

- Шрифт: Courier New 10 пт;
- Краткие фрагменты (15–25 строк) — в тексте главы 3;
- Полные версии — в Приложении В (В.1 — В.8);

- Перед листингом — вводный абзац, после — интерпретирующий.

## 13. Верификация перед сдачей

После прогона `scripts/edit-docx.py`:

1. Открыть итоговый файл в LibreOffice/Word и обновить оглавление (Ctrl+A → F9).
2. Проверить структуру главы 2 по списку из п. 3.
3. Проверить все подписи рисунков/таблиц/листингов на короткое тире `–`.
4. Убедиться, что в цветовой палитре (рисунок 2.9.1 и таблица 2.9.1) указаны ровно пять цветов из п. 9.
5. Убедиться, что в сравнении инструментов (таблица 2.8.1) фигурируют Figma, Adobe Illustrator, XDesign.
6. Пройти по всем вставленным рисункам и убедиться, что каждый идёт после описательного текста.
7. Обновить `CHANGES.md` по итогам прогона.
