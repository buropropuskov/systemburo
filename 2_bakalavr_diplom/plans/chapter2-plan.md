## 2.2 Описание основных бизнес-процессов ТОиР (4-5 стр.)

### Обязательные диаграммы:

#### User Story Map (Рисунок 2.1)
Карта пользовательских историй, показывающая:
- Горизонтальная ось: путь пользователя (регистрация -> учёт оборудования -> подача заявки -> выполнение -> отчётность)
- Вертикальная ось: приоритет функций (must have / should have / could have)
- Роли: Оператор, Техник, Инженер, Администратор

#### Диаграмма вариантов использования / Use Case (Рисунок 2.2)
Акторы и их взаимодействия с системой:
- **Оператор**: создать заявку на ремонт, просмотреть статус заявки
- **Техник**: принять заявку, выполнить работу, внести результаты, запросить запчасти
- **Инженер**: управлять оборудованием, создавать графики ТО, назначать исполнителей, просматривать отчёты
- **Администратор**: управлять пользователями, настраивать систему

#### User Stories (описать текстом, 5-7 ключевых)
Формат: «Как [роль], я хочу [действие], чтобы [ценность]»
- Как оператор, я хочу создать заявку на ремонт оборудования, чтобы техническая служба оперативно узнала о неисправности.
- Как техник, я хочу видеть список назначенных мне заявок с приоритетами, чтобы выполнять работу в правильном порядке.
- Как инженер, я хочу видеть дашборд с ключевыми метриками, чтобы контролировать состояние оборудования.
- Как инженер, я хочу настраивать графики планового ТО, чтобы предотвращать аварийные поломки.
- Как администратор, я хочу управлять учётными записями сотрудников, чтобы контролировать доступ к системе.

### Описание бизнес-процессов текстом:
1. **Процесс подачи и обработки заявки на ремонт**: оператор фиксирует неисправность -> инженер оценивает приоритет -> назначает техника -> техник выполняет -> отмечает завершение -> инженер проверяет
2. **Процесс планового ТО**: инженер задаёт график -> система формирует наряд-задания -> техник выполняет -> результаты в журнале
3. **Процесс учёта оборудования**: регистрация -> присвоение инвентарного номера -> привязка к локации -> история обслуживания

## 2.3 Формирование требований и характеристик (4-5 стр.)

### Нефункциональные требования (Таблица 2.2)
- Время ответа API < 200 мс при 100 одновременных пользователях
- JWT-аутентификация, RBAC
- Развёртывание через Docker Compose
- Поддержка Chrome 90+, Firefox 88+, Safari 14+

### Архитектура системы (Рисунок 2.3)
- Клиент-серверная, REST API, SPA
- Компоненты: Vue 3 SPA -> Nginx -> Go API -> PostgreSQL
- Clean Architecture на бэкенде: handlers -> services -> repositories

### Проектирование БД (Рисунок 2.4 — ER-диаграмма)
- Сущности: users, equipment, repair_requests, maintenance_schedules, work_orders, maintenance_logs, parts, work_order_parts
- Описание ключевых сущностей и связей

### Проектирование API (Таблица 2.3)
- Ключевые эндпоинты REST API с указанием ролей
- Формат JSON envelope: { success, data, error, meta }
