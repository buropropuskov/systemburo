ВВЕДЕНИЕ

Юридическая проверка документов отнимает часы. Один договор аренды может включать в себя 40 страниц, десятки пунктов, ссылки на нормативные акты, скрытые оговорки в приложениях. Юристу нужно без ошибок всё читать, сверять, перечитывать. Если документов несколько десятков в неделю, ошибки становятся вопросом времени, а не вероятности.

Искусственный интеллект способен обрабатывать такой объём за секунды [1]. Алгоритмы находят противоречия, выделяют подозрительные формулировки, сопоставляют с действующим законодательством. Однако без удобного интерфейса результат анализа теряет ценность: пользователь не понимает, почему конкретный пункт помечен как рискованный, не может уточнить детали, не видит контекста. По данным Nielsen Norman Group, 88% пользователей не возвращаются на сайт после неудачного первого опыта [10]. Для юридического сервиса, где каждый клиент принимает решения с финансовыми последствиями, цена неудобного интерфейса измеряется не раздражением, а упущенными рисками.

Рынок LegalTech растёт. К 2025 году его глобальный объём оценивают в 32,21 миллиарда долларов [1]. Российский сегмент, хотя и скромнее (около 15 миллиардов рублей), уже насчитывает несколько заметных решений: Яндекс Нейроюрист, Embedika Contract, Noroots [4]. Каждое из них решает часть задач, но ни одно не предлагает полного цикла: загрузка документа, подсветка рисков прямо в тексте, интерактивный чат с ИИ-агентом, заметки, экспорт отчёта. Именно этот разрыв определяет актуальность настоящей работы.

Стартап Dockee разрабатывается командой из пяти человек. Бэкенд написан на Go с использованием фреймворка Gin и базы данных PostgreSQL. Для анализа документов интегрирован DeepSeek API, обеспечивающий распознавание юридических и финансовых рисков. Персональные данные защищены NER-анонимизацией в соответствии с требованиями Федерального закона N 152-ФЗ. Настоящая работа посвящена фронтенд-части: проектированию и реализации пользовательского интерфейса, через который юристы и предприниматели взаимодействуют с системой.

Целью работы является разработка системы автоматизированного анализа документов, которая позволит выявлять юридические и финансовые риски, несоответствие нормативным требованиям и признаки мошенничества с помощью интегрированного ИИ-агента и средств защиты конфиденциальной информации.

Для достижения поставленной цели сформулированы следующие задачи:

1. Провести анализ предметной области и существующих решений для выявления требований к пользовательскому интерфейсу.

2. Разработать информационную архитектуру и описать пользовательские сценарии.

3. Изучить вопросы безопасности и производительности клиентской части веб-приложений для принятия мер по защите данных и оптимизации.

4. Разработать прототипы и дизайн-макеты пользовательского интерфейса сервиса.

5. Изучить современные методы и инструменты разработки пользовательских интерфейсов, провести их сравнительный анализ и обосновать выбор технологий.

6. Разработать пользовательский интерфейс в соответствии с требованиями и прототипами.

7. Проанализировать результаты и внести правки по итогам обратной связи.

8. Разработать пользовательскую документацию, инструкцию по эксплуатации приложения с описанием развертывания и сопровождения.

Объектом исследования выступает процесс автоматизированного анализа юридических документов. Предмет исследования: пользовательский интерфейс веб-приложения для работы с результатами такого анализа.

1 ИССЛЕДОВАНИЕ ПРЕДМЕТНОЙ ОБЛАСТИ, АНАЛИЗ РЕШЕНИЙ И ВЫЯВЛЕНИЕ ТРЕБОВАНИЙ

1.1 Анализ рынка систем автоматизированного анализа документов

Юридическая отрасль переживает цифровую перестройку. Рынок LegalTech, по данным Grand View Research, достиг отметки в 32 млрд долларов к 2025 году и, согласно прогнозам, вырастет до 78 млрд долларов к 2035 году при среднегодовом темпе роста (CAGR) 9,2% [1]. Движущая сила этого роста не столько в желании юристов «идти в ногу со временем», сколько в экономической необходимости: ручная проверка одного договора занимает от 40 минут до нескольких часов, тогда как автоматизированный анализ укладывается в секунды.

Сегмент Legal AI развивается ещё агрессивнее. Statista оценивает его объём в 2,19 млрд долларов по итогам 2024 года с прогнозом роста до 3,64 млрд долларов к 2030 году (CAGR 10,7%) [2]. Почему этот сегмент опережает общий рынок? Потому что модели обработки естественного языка (NLP) за последние три года научились работать с юридическими текстами на уровне, достаточном для коммерческого применения. Если в 2020 году ИИ мог лишь классифицировать документ по типу, то к 2024 году он способен выделить конкретные риски, указать на противоречия между пунктами и предложить формулировки для исправления.

Облачные технологии стали общепринятым стандартом. По данным American Bar Association, к 2024 году более 70% юридических фирм в США используют облачные инструменты для работы с документами [3]. Переход в облако объясним: юристы работают с клиентами удалённо, доступ к документам нужен с любого устройства, а содержать собственную серверную инфраструктуру для небольшой практики из 5-10 человек нерентабельно.

На рынке автоматизированного анализа документов можно выделить два крупных направления. Первое, сервисы для профессионалов, помогает юристам быстрее проверять договоры, находить риски и формировать отчёты. Второе, инструменты защиты от мошенничества, ориентировано на банки, страховые компании и корпорации, которым нужно выявлять подделки, несоответствия и подозрительные паттерны в потоке входящих документов. Dockee будет находиться на пересечении обоих направлений: сервис должен анализировать юридические документы для профессионалов, но при этом акцентировать внимание на рисках и признаках мошенничества.

Аналитики McKinsey прогнозируют, что к 2030 году около 90% стандартных юридических документов (типовые договоры, NDA, арендные соглашения) будут обрабатываться автоматически [1]. Оставшиеся 10% придутся на нестандартные сделки, где требуется экспертное суждение юриста. Для пользовательского интерфейса это означает следующее: система должна не заменять юриста, а выступать его инструментом, подсвечивая проблемные места и оставляя финальное решение за человеком.

1.2 Развитие в России и анализ отечественных решений

Российский рынок LegalTech формируется по собственной траектории. По оценке РБК, его объём составляет порядка 15 млрд рублей, причём доля отечественных решений превышает 95% [4]. Причина такой автономности проста: российское законодательство имеет свою специфику (Гражданский кодекс, ФЗ-152 о персональных данных, отраслевые регуляции), и зарубежные платформы, обученные на англосаксонском праве, плохо справляются с русскоязычными документами.

ИИ проникает в юридическую практику неравномерно. РБК отмечает, что крупные юридические фирмы уже используют ИИ для рутинных задач: проверки контрагентов, анализа судебной практики, подготовки шаблонных документов [5]. Малые практики и частные юристы, напротив, часто ограничены Excel-таблицами и ручным поиском по базам. Именно для этой аудитории, специалистов без бюджета на корпоративные EAM-системы, создаётся Dockee.

В ходе исследования были изучены три наиболее заметных отечественных решения и сопоставлены их возможности с функциональностью Dockee. Яндекс Нейроюрист работает как чат-бот: пользователь задаёт вопрос текстом, получает ответ. Загрузить договор и получить его разбор по пунктам нельзя. Embedika Contract умеет подсвечивать рисковые фрагменты в тексте, что ближе к поставленной задаче, однако лишён встроенного чата и возможности оставлять заметки к конкретным рискам. Noroots генерирует итоговый отчёт по документу, но интерактивная работа с текстом (навигация по рискам, вопросы к ИИ по выделенному фрагменту) отсутствует.

Что показывает таблица? Ни одно из рассмотренных решений не объединяет все четыре ключевые функции: просмотр документа с подсветкой рисков, интерактивный чат с ИИ, систему заметок и навигацию. Наиболее перспективный подход, который можно реализовать в Dockee, заключается во встраивании результатов анализа непосредственно в документ. Такой подход сокращает когнитивную нагрузку и время проверки.

1.3 Методы и подходы к визуализации результатов анализа

Как показать юристу, что в договоре есть проблема, не заставляя его читать 30 страниц целиком? Вопрос визуализации результатов анализа является ключевым для UX сервиса анализа документов. Nielsen Norman Group подчёркивает, что эффективная визуализация данных снижает время на принятие решения в 2-3 раза по сравнению с текстовым представлением тех же данных [6].

Первый метод – структурированный ответ ИИ в интегрированном чате. После загрузки и анализа документа пользователь получает сводный отчёт в формате чат-сообщения: перечень выявленных рисков, их классификация по степени серьёзности, рекомендации. Далее пользователь может задавать уточняющие вопросы: «Почему пункт 4.3 помечен как рискованный?» или «Какая судебная практика существует по подобным формулировкам?». Чат сохраняет контекст диалога, что позволяет вести последовательный разбор документа.

Второй метод –  цветовая подсветка рисков непосредственно в тексте. Красный маркер обозначает критические риски (ущемление прав, отсутствие обязательных условий, противоречие законодательству). Жёлтый выделяет сомнительные формулировки, которые требуют внимания юриста, но могут быть допустимы в контексте конкретной сделки. Shneiderman в работе по информационной визуализации отмечает, что цветовое кодирование работает эффективнее текстовых пометок, когда категорий не более 5-7 [7]. Для сервиса анализа документов целесообразно ограничиться тремя уровнями (критический, сомнительный, информационный), чтобы не перегружать восприятие.

Третий метод – сводная панель рисков и проблем с группировкой по важности. Боковая панель инспектора отображает все найденные риски в виде карточек, отсортированных по степени критичности. Юрист видит общую картину: 2 критических риска, 5 сомнительных, 3 информационных. По клику на карточку документ прокручивается к соответствующему фрагменту.

Четвёртый метод – рекомендации по исправлению. Каждая карточка риска содержит не только описание проблемы, но и конкретное предложение: «Рекомендуется добавить пункт о порядке расторжения» или «Формулировка допускает двоякое толкование, предлагается заменить на...». Рекомендации генерируются ИИ-агентом и носят вспомогательный характер.

Пятый метод – цветные метки на полосе прокрутки. По аналогии с тем, как IDE подсвечивает ошибки в коде на полосе прокрутки, маркеры рисков размещаются на скроллбаре документа. Юрист, ещё не прочитав документ, видит распределение проблем: если красные точки сконцентрированы в начале, значит, преамбула и определения требуют пристального внимания. Этот метод особенно полезен для длинных документов на 50 и более страниц.

Перечисленные методы работают совместно, дополняя друг друга. Сводная панель даёт общую картину, подсветка в тексте, точную локализацию, чат, глубокое понимание, а метки на скроллбаре, навигационную карту.

1.4 Методы и подходы к организации интерактивного взаимодействия пользователя с ИИ-агентом и результатом

Amershi и соавторы в руководстве по проектированию Human-AI Interaction сформулировали 18 рекомендаций, из которых для данной задачи наиболее релевантны три: система должна объяснять свои решения, допускать корректировку результатов пользователем и обрабатывать неоднозначные ситуации явно, а не молча [8].

Взаимодействие с ИИ-агентом в Dockee может быть организовано по трём каналам. Первый канал – это чат-помощник. Выдвижная панель справа от документа позволяет задавать вопросы. Контекстные вопросы привязаны к выделенному фрагменту текста: пользователь выделяет абзац, нажимает «Спросить ИИ» и получает анализ именно этого фрагмента. Свободные вопросы касаются документа в целом: «Какие существенные условия отсутствуют?», «Соответствует ли договор ФЗ-44?». ИИ-агент на базе DeepSeek API обрабатывает оба типа, сохраняя историю диалога в рамках сессии.

Второй канал – система заметок. Заметки бывают привязанными и общими. Привязанная заметка создаётся из карточки конкретного риска: юрист читает описание проблемы, формулирует своё мнение («Риск незначительный, клиент согласен с условием») и сохраняет. Общие заметки относятся ко всему документу и используются как рабочий блокнот. Shneiderman подчёркивает, что возможность аннотирования результатов анализа критична для систем, где человек принимает окончательное решение на основе рекомендаций машины [9].

Далее – навигация. Её можно организовать четырьмя способами: автоматически генерируемое оглавление документа, полнотекстовый поиск по содержимому, переход от карточки риска к соответствующему фрагменту текста (и обратно) и уже упомянутые цветные метки на полосе прокрутки. Каждый способ решает свою задачу. Оглавление подходит для последовательного чтения. Поиск, для быстрого нахождения конкретного термина. Переход из инспектора, для точечной проверки рисков. Метки на скроллбаре, для общей ориентации в документе.

Зачем столько каналов? По опыту разработки, юристы сильно различаются в стиле работы. Одни читают договор от начала до конца и по ходу задают вопросы. Другие сначала смотрят сводку рисков и разбирают только проблемные места. Третьи ищут конкретные пункты (ответственность, форс-мажор, порядок расторжения). Интерфейс должен поддерживать все три стратегии, не навязывая единственный сценарий.

1.5 Принципы проектирования пользовательского интерфейса

Разработка пользовательского интерфейса для системы анализа документов требует опоры на проверенные принципы проектирования. Прежде чем обсуждать конкретные решения для Dockee, следует определить теоретическую базу.

UX (User Experience) и UI (User Interface) часто употребляются вместе, но описывают разные вещи. UX отвечает на вопрос «как пользователь воспринимает взаимодействие с системой?»: удобно ли загрузить документ, понятно ли, что означает красная подсветка, легко ли найти кнопку экспорта. UI отвечает на вопрос «как система выглядит?»: цветовая палитра, типографика, размеры кнопок, расположение элементов. Norman в книге «Design of Everyday Things» формулирует это так: хороший UX делает систему понятной без инструкции, хороший UI делает её приятной в использовании [13]. Для Dockee приоритет должен отдаваться UX, потому что юрист проводит в системе часы, проверяя десятки страниц. Красивый, но неудобный интерфейс вернёт пользователя к привычному чтению в Word.

User-Centered Design (UCD). Стандарт ISO 9241-210 описывает итеративный процесс проектирования, ставящий потребности пользователя в центр каждого решения [11]. Процесс состоит из четырёх фаз: исследование (кто пользователи, какие задачи решают), концепция (сценарии использования, информационная архитектура), прототипирование (макеты и тестирование на реальных пользователях), тестирование и итерация (корректировка по обратной связи). 

Эвристики Нильсена. Jakob Nielsen сформулировал 10 эвристик юзабилити, которые остаются актуальным инструментом оценки интерфейсов уже более 30 лет [10]. Для проектируемого сервиса можно выделить шесть наиболее релевантных.

Видимость состояния системы: при анализе документа отображается прогресс-бар с этапами («Загрузка», «Извлечение текста», «Анализ ИИ», «Формирование отчёта»). Без обратной связи пользователь через 10 секунд решит, что система зависла. Соответствие реальному миру: карточки рисков используют юридическую терминологию («существенные условия», «контрагент»), а не техническую. Предотвращение ошибок: при удалении документа появляется диалог подтверждения с указанием имени файла; Krug в «Don't Make Me Think» утверждает, что предотвратить ошибку дешевле, чем исправить её последствия [14].

Распознавание вместо запоминания: иконки в боковом меню сопровождаются текстовыми подписями, цветовые маркеры дублируются метками «Критический», «Сомнительный», «Информационный». Помощь и документация: встроенная контекстная справка доступна по иконке «?», при первом входе показываются onboarding-подсказки. Гибкость и эффективность: горячие клавиши (Ctrl+F, Ctrl+E, стрелки для навигации между рисками) позволяют опытному пользователю обходиться без мыши.

Гештальт-принципы восприятия. Принцип близости: карточки рисков одного уровня критичности расположены рядом, образуя визуальную группу. Принцип подобия: все критические риски обозначены красным, все сомнительные, жёлтым. Пользователь считывает уровень опасности по цвету, не читая текст. Принцип замкнутости: каждая карточка имеет чёткие границы, отделяющие её от соседних.

Закон Фиттса: время наведения на цель пропорционально расстоянию и обратно пропорционально размеру. Практический вывод: кнопку «Начать анализ» рекомендуется делать размером не менее 48x48 пикселей, контрастного цвета, и размещать в центре рабочей области.

Закон Хика: время принятия решения растёт логарифмически с увеличением числа вариантов. Для сервиса анализа документов это означает, что на главном экране целесообразно показывать не более 5-6 активных элементов управления, а второстепенные функции можно скрывать в выпадающих меню.

Доступность (WCAG 2.1). Стандарт определяет требования к доступности веб-контента [12]. Уровень AA предписывает контрастность текста не менее 4,5:1. При проектировании юридического сервиса рекомендуется подбирать палитру с запасом: красный маркер на белом фоне должен давать контрастность не менее 5:1, а жёлтые элементы лучше заменить на тёмно-оранжевые (4,8:1). Также целесообразно обеспечить навигацию с клавиатуры и снабдить изображения альтернативными текстами.

1.6 Особенности проектирования лендинга сервиса

Лендинг (landing page) в контексте Dockee выполняет роль ознакомительно-навигационной страницы. Это первый экран, который видит новый пользователь, и от его структуры зависит, поймёт ли человек, как устроен сервис и куда нажимать [15]. За 10-15 секунд посетитель должен разобраться, что делает система, и найти путь к регистрации или авторизации.

Структура лендинга должна быть выстроена по принципу последовательного знакомства. Первый экран должен соодержать заголовок с описанием назначения сервиса и кнопку для перехода к бесплатному пробному периоду. Посетитель не должен скроллить, чтобы понять суть: анализ документов с помощью ИИ. Ниже расположен блок, кратко объясняющий четыре ключевые возможности: сокращение времени проверки, повышение точности, оптимизация процесса, экономия ресурсов. Каждый пункт сопровождается конкретной цифрой.

Блок тарифов показывает три варианта подписки: «Тестовая» (бесплатный период для знакомства с сервисом), «Базовая» и «Продвинутая». Пользователь сразу видит, что входит в каждый пакет, и может выбрать подходящий. Раздел «Как это работает» визуализирует три шага: загрузка документа, анализ ИИ, получение отчёта. Такая схема снижает неопределённость для нового пользователя: он заранее представляет весь процесс.

Для юридического сервиса принципиально важны два аспекта. Первый: наглядная демонстрация интерфейса. Посетитель видит, как выглядит рабочее пространство с подсвеченными рисками, панелью инспектора и чатом ИИ-помощника. Второй: информация о защите данных. Юристы работают с конфиденциальными документами, и сервис должен чётко объяснить меры безопасности: NER-анонимизация персональных данных (ФЗ-152), шифрование при передаче (TLS 1.3).

Блок команды знакомит с разработчиками. FAQ отвечает на типичные вопросы: «Что будет с моими данными?», «Насколько точен анализ?», «Можно ли отменить подписку?». Форма обратной связи позволяет задать вопрос, если пользователь пока не готов к регистрации. Навигация по странице обеспечивается через верхнее меню с якорными ссылками на каждый блок и кнопку «Войти» для перехода к авторизации.

1.7 Безопасность и производительность клиентской части

Клиентская часть веб-приложения находится в потенциально враждебной среде: браузер пользователя доступен для атак, расширений и вредоносных скриптов. Для сервиса, работающего с юридическими документами и персональными данными, безопасность фронтенда не менее важна, чем безопасность сервера.

XSS (Cross-Site Scripting). Межсайтовый скриптинг остаётся в OWASP Top 10 клиентских уязвимостей [17]. Злоумышленник внедряет вредоносный JavaScript-код, который выполняется в браузере жертвы с полномочиями текущей сессии. Выделяют три типа: сохраняемый (stored) XSS, когда скрипт сохраняется на сервере и выполняется у каждого, кто откроет заражённый контент; отражённый (reflected) XSS, когда скрипт передаётся через URL-параметр; XSS на основе DOM, когда скрипт внедряется через манипуляцию DOM-деревом без участия сервера. Для Dockee сохраняемый XSS может быть особенно опасен, поскольку заметки создаются пользователями и отображаются в интерфейсе.

Защита от XSS реализуется на нескольких уровнях: экранирование пользовательского ввода при рендеринге, запрет директивы v-html для пользовательского контента, санитизация данных на стороне сервера.

CSRF (Cross-Site Request Forgery) позволяет выполнять действия от имени авторизованного пользователя без его ведома. Защита: атрибут SameSite=Strict для cookies и CSRF-токены в заголовках POST/PUT/DELETE-запросов.

Clickjacking использует прозрачный iframe поверх легитимной страницы. Защита: HTTP-заголовок X-Frame-Options: DENY.

CSP (Content Security Policy) позволяет указать браузеру, откуда разрешено загружать ресурсы [18]. Для сервиса анализа документов рекомендуется настроить политику строго: разрешить скрипты только с собственного домена и доверенных CDN с nonce-токенами, запретить inline-скрипты. При такой конфигурации даже при наличии XSS-уязвимости внедрённый скрипт не выполнится, если его источник отсутствует в белом списке.

OWASP Top 10 для клиентской части включает также небезопасное хранение данных и утечку информации через консоль [17]. Для защиты токенов авторизации целесообразно использовать httpOnly cookies (недоступны из JavaScript), а пользовательские данные хранить в оперативной памяти state-менеджера.

Для сервиса анализа документов можно использовать следующую стратегию: localStorage подходит для несекретных настроек (язык интерфейса, масштаб, тема). Производительность клиентской части. Google определяет три ключевые метрики Core Web Vitals [19]: LCP (Largest Contentful Paint, цель < 2,5 с), FID (First Input Delay, цель < 100 мс), CLS (Cumulative Layout Shift, цель < 0,1). Маршруты загружаются лениво: начальная загрузка сокращается с ~800 КБ до ~250 КБ. Сжатие статики (gzip/brotli) уменьшает размер данных на 60-80%, кэширование через Cache-Control с хэшами в именах файлов исключает повторное скачивание неизменённых ресурсов.

1.8 Выбор технологий и инструментов для разработки пользовательского интерфейса

Веб-интерфейс любого приложения строится на трёх фундаментальных технологиях. HTML (HyperText Markup Language) задаёт структуру страницы: заголовки, абзацы, формы, кнопки, ссылки. Текущая версия спецификации W3C, HTML5, добавила семантические элементы (header, nav, main, section), которые улучшают доступность и SEO.

CSS (Cascading Style Sheets) отвечает за внешний вид. Блочная модель определяет отступы и размеры элементов. Flexbox и Grid решают задачу раскладки: первый подходит для одномерного выравнивания, второй, для двумерных сеток. Media queries обеспечивают адаптивность интерфейса под разные размеры экранов. Для организации стилей в крупных проектах применяются методологии BEM и CSS Modules, изолирующие стили на уровне компонента.

JavaScript делает интерфейс интерактивным: обработка событий (клик, ввод, прокрутка), манипуляция DOM-деревом, асинхронные запросы к серверу через fetch API. Текущая спецификация ECMAScript 2024 включает модульную систему (import/export), async/await для асинхронного кода и деструктуризацию объектов.

Однако при масштабировании до 10 и более экранов чистый JavaScript становится неуправляемым. Ручное отслеживание состояния приводит к рассинхронизации данных между компонентами. Дублирование шаблонного кода растёт линейно с числом страниц, а тестирование без компонентной архитектуры превращается в проверку всего DOM целиком. Фреймворки решают эти проблемы через компонентный подход, декларативный рендеринг и систему реактивности.

Было рассмотрено три ведущих решения: React, Angular и Vue.js.

React основан на декларативном подходе с использованием JSX. Virtual DOM обеспечивает эффективное обновление интерфейса, сравнивая текущее и предыдущее состояние дерева компонентов. С 2019 года React перешёл на функциональные компоненты с хуками: useState, useEffect, useMemo [22]. Однонаправленный поток данных обеспечивает предсказуемость. Экосистема обширна, но фрагментирована: для маршрутизации нужен React Router, для состояния, Redux или Zustand, для SSR, Next.js.

Рисунок 1.8.1 – Структура React-компонента

Angular представляет собой полноценный фреймворк с обязательным TypeScript, встроенным Dependency Injection и реактивным управлением через RxJS [23]. Angular CLI генерирует компоненты по шаблонам. Хорошо подходит для крупных корпоративных приложений с десятками разработчиков, но кривая обучения значительно круче: TypeScript, RxJS, DI, декораторы, модули, зоны.

Vue.js изначально проектировался как инструмент с низким порогом входа и инкрементальным усложнением. Composition API, введённый в версии 3, группирует связанную логику в одном месте, решая проблему «прыжков» между секциями Options API [21].

Composables (функции с префиксом use) извлекают переиспользуемую логику. Для сервиса анализа документов планируется создать useDocumentAnalysis, useAuth, useChat. Система реактивности Vue 3 построена на ES6 Proxy: ref для примитивов, reactive для объектов, computed с автоматическим кэшированием, watch и watchEffect для побочных эффектов.

Функциональные требования. Стандарт ISO 25010 определяет функциональную пригодность как способность продукта выполнять заявленные функции [27].

Загрузка документов: два способа (кнопка «Загрузить» и drag-and-drop), форматы PDF, DOCX, TXT, лимит 50 МБ. Критерий: файл в списке загруженных за 2 секунды.

Панель инспектора: карточки рисков с группировкой по критичности, кнопка «Перейти к фрагменту». Критерий: прокрутка к фрагменту за 500 мс.

ИИ-помощник: свободные и контекстные вопросы по документу, ответ за 5-10 секунд с сохранением истории диалога.

Система заметок: привязанные (из карточки риска) и общие. Сохранение между сессиями без перезагрузки страницы.

Экспорт отчёта в PDF или DOCX с перечнем рисков, рекомендациями и заметками.

Файловое хранилище с папками, поиском, сортировкой и отображением использованного объёма. Поиск за 300 мс.

Нефункциональные требования. ISO 9241-11 определяет юзабилити через результативность, эффективность и удовлетворённость [28].

2 ПРОЕКТИРОВАНИЕ ПОЛЬЗОВАТЕЛЬСКОГО ИНТЕРФЕЙСА

2.1 Анализ целевой аудитории

Проектирование интерфейса сервиса Dockee начинается с вопроса: кто будет им пользоваться? Ответ определяет каждое решение, от расположения кнопок до формулировок в отчётах. На основе анализа предметной области и типовых сценариев использования можно выделить два основных сегмента потенциальных пользователей сервиса.

Первый сегмент составляют юристы, адвокаты и сотрудники юридических отделов. Эти специалисты ежедневно работают с договорами, дополнительными соглашениями, актами и протоколами разногласий. Их запрос к сервису конкретен: точное выявление рисков с юридическими пояснениями, фильтрация замечаний по критичности, инструменты фиксации выводов. По данным исследования LegalTech-рынка, 73% юристов тратят на первичную вычитку документов более 40% рабочего времени [30]. Интерфейс для этой аудитории должен быть информационно насыщенным, но без визуального шума.

Второй сегмент, предприниматели и руководители малого бизнеса без штатного юриста. Они проверяют документы перед подписанием или перед передачей внешнему специалисту. Для них критична простота: загрузил файл, получил понятный отчёт с рекомендацией «подписывать» или «не подписывать». Согласно опросу «Опоры России», около 62% субъектов МСП подписывают договоры без юридической экспертизы [31]. Интерфейс для этого сегмента должен минимизировать когнитивную нагрузку.

Для конкретизации потребностей каждого сегмента сформированы персоны, представленные в Таблице 2.1.

На практике это означает, что интерфейс должен работать на двух уровнях: детализированная информация для тех, кто хочет углубиться, и сжатая сводка для тех, кому достаточно общей картины.

2.2 Бизнес-процессы

Прежде чем проектировать экраны, необходимо зафиксировать, какие процессы сервис должен поддерживать. Выделены три ключевых бизнес-процесса, каждый из которых описан текстуально и представлен на соответствующей диаграмме в Приложении А.

2.2.1 Регистрация и онбординг пользователя

Путь нового пользователя начинается с лендинга: знакомство с преимуществами сервиса, изучение тарифов, нажатие кнопки «Войти». Система перенаправляет на форму регистрации (email + пароль), после чего на указанный адрес приходит письмо со ссылкой для подтверждения. Подтвердив email, пользователь выбирает тариф: «Тестовая» (без оплаты), «Базовая» или «Продвинутая». Конверсия из регистрации в первую проверку документа составит 60-70%, если онбординг занимает менее 3 минут [33]. Визуализация процесса приведена на Рисунке А.1 (Приложение А).

2.2.2 Загрузка и анализ документа

Это центральный процесс сервиса. Пользователь загружает файл, фронтенд проверяет формат и размер, после чего файл передаётся на бэкенд. Серверная часть сохраняет документ в S3-хранилище, извлекает текст и отправляет запрос к DeepSeek API. Ответ содержит список рисков с фрагментами текста, степенью критичности и пояснениями. Результаты сохраняются в PostgreSQL и передаются фронтенду: красным выделяются критические риски, жёлтым, сомнительные. Весь процесс занимает 8-45 секунд; для документа на 10-15 страниц среднее время составляет около 12 секунд [34]. Диаграмма процесса представлена на Рисунке А.2 (Приложение А).

2.2.3 Работа с результатами анализа

После получения результатов пользователь просматривает документ с подсвеченными рисками (слева) и панель замечаний, сгруппированных по критичности (справа). Клик на конкретный риск прокручивает документ к фрагменту и отображает пояснение. Доступен ИИ-помощник (выдвигающаяся панель), которому можно задать уточняющий вопрос с контекстом фрагмента; время отклика составляет 3-5 секунд. Пользователь может оставить заметку к замечанию, изменить его статус («принять», «отклонить», «уточнить») и скачать PDF-отчёт с перечнем рисков и заметками. Визуализация процесса приведена на Рисунке А.3 (Приложение А).

2.3 Пользовательские сценарии

Бизнес-процессы описывают «что происходит». Пользовательские сценарии отвечают на вопрос «кто и как взаимодействует с системой». Для формализации сценариев применены два инструмента: диаграммы прецедентов (Use Case) и диаграммы активности.

2.3.1 Диаграммы прецедентов (Use Case)

Диаграмма прецедентов в нотации UML показывает множество функций системы (прецедентов) и множество внешних сущностей (акторов), которые с ними взаимодействуют [35]. Связи между прецедентами выражаются отношениями include (обязательное включение) и extend (необязательное расширение). Построены три диаграммы, покрывающие основные группы функций.

Диаграмма «Загрузка и анализ документа». Главный актор, Пользователь. Он инициирует прецедент «Загрузить документ», который обязательно включает (include) «Валидировать формат» и «Проверить размер файла». После успешной загрузки Пользователь может запустить «Анализировать документ». Этот прецедент включает «Показать прогресс анализа» и «Отобразить результаты». Внешний актор DeepSeek API участвует в прецеденте «Анализировать документ» как поставщик интеллектуальных услуг. Фактически фронтенд не обращается к DeepSeek API напрямую, запрос проходит через бэкенд, однако на уровне прецедентов DeepSeek API выступает самостоятельным актором, поскольку является внешней системой с собственным жизненным циклом.

Рисунок 2.3.1 – Диаграмма прецедентов «Загрузка и анализ документа»

Диаграмма «Взаимодействие с ИИ-агентом». Пользователь может инициировать три прецедента: «Задать вопрос по фрагменту документа», «Задать свободный вопрос» и «Уточнить предыдущий ответ». Каждый из них включает общий прецедент «Получить ответ от ИИ». DeepSeek API вновь выступает внешним актором. Разделение на три прецедента обусловлено различиями в контексте запроса: вопрос по фрагменту включает текст фрагмента и тип риска, свободный вопрос содержит только текст документа, а уточнение добавляет историю диалога.

Рисунок 2.3.2 – Диаграмма прецедентов «Взаимодействие с ИИ-агентом»

Диаграмма «Управление документами». Пользователь взаимодействует с шестью прецедентами: «Загрузить файл», «Просмотреть список документов», «Открыть документ», «Удалить документ», «Переименовать документ» и «Создать документ». Прецедент «Удалить документ» включает «Подтвердить удаление», что защищает от случайной потери данных. Прецедент «Поиск документов» расширяет (extend) «Просмотреть список документов»: пользователь может просматривать список и без поиска, но поиск всегда приводит к отфильтрованному списку.

Рисунок 2.3.3 – Диаграмма прецедентов «Управление документами»

2.4 Диаграммы активности

Диаграммы прецедентов показывают «что» система делает. Диаграмма активности раскрывает «как» это происходит, шаг за шагом. Для наиболее сложного сценария, загрузки и анализа документа, построена подробная диаграмма с дорожками (swimlanes), разделяющими ответственность между участниками.

Четыре дорожки соответствуют четырём участникам: Пользователь, Фронтенд, Бэкенд, DeepSeek API. Процесс стартует с выбора файла пользователем; Фронтенд выполняет валидацию формата и размера. При неудачной проверке отображается ошибка, при успешной файл передаётся на Бэкенд. Бэкенд сохраняет файл в S3, извлекает текст и формирует запрос к DeepSeek API. На диаграмме намеренно показаны два сценария ошибок (невалидный файл и недоступность API), поскольку именно обработка исключительных ситуаций отличает продуманный интерфейс от наивного [37]. Полная диаграмма приведена на Рисунке А.4 (Приложение А).

2.5 Архитектура и структура интерфейса

Информационная архитектура определяет, как контент организован, связан и представлен пользователю [38]. Для Dockee она спроектирована с опорой на два принципа: минимальная глубина навигации (не более 2 кликов до любой функции) и чёткое разделение контекстов (работа с документом, файловое хранилище, аналитика, настройки).

Карта экранов

Сервис состоит из 5 основных экранов и 3 вспомогательных. Основные: Лендинг, Главная (работа с документом), Документы (файловое хранилище), Аналитика, Аккаунт. Вспомогательные: Авторизация, Регистрация, Настройки. Глубина иерархии не превышает двух уровней, что позволяет добраться до любой функции за 1-2 клика.

Лендинг доступен без авторизации. Все остальные экраны требуют аутентификации: при попытке обратиться к защищённому маршруту без токена пользователь перенаправляется на экран авторизации. Vue Router в связке с навигационными хуками (beforeEach) обеспечивает эту логику на стороне клиента [39]. Такой подход исключает ситуацию, когда неавторизованный пользователь видит пустой интерфейс без объяснения причин.

Навигационная структура

Навигация реализована двумя элементами: боковым меню и верхней панелью.

Боковое меню содержит 5 пунктов: «Главная», «Документы», «Аналитика», «Аккаунт» и «Выйти». Меню фиксировано слева и доступно на всех экранах после авторизации. 5 пунктов является оптимальным числом. Исследования показывают, что пользователь уверенно ориентируется в навигации с 5-7 элементами [40]; при 10+ элементах время поиска нужного пункта возрастает на 30-40%.

Верхняя панель содержит логотип, выбор языка, строку глобального поиска, имя текущего пользователя, значок уровня подписки и счётчик оставшихся проверок. Элемент решает две задачи: быстрый доступ к поиску из любого контекста и постоянное информирование о лимитах тарифа. Строка поиска работает как универсальный фильтр, позволяя находить документы по имени файла, контрагенту или дате загрузки.

Рабочий экран анализа

Отдельного внимания заслуживает компоновка рабочего экрана. Экран разделён на три функциональные зоны.

Центральная зона: текст документа. Фрагменты с рисками подсвечиваются цветом: красный фон для критических замечаний, жёлтый для сомнительных. При наведении на фрагмент появляется всплывающая подсказка с кратким описанием риска.

Нижняя зона: панель замечаний. Список рисков отсортирован по критичности. Каждый элемент содержит номер, краткое описание и кнопку раскрытия для полного пояснения. Здесь же расположены кнопки изменения статуса и поле для заметки.

Выдвигающаяся панель ИИ-помощника появляется поверх правой зоны по клику на иконку чата. Пользователь переключается между панелью замечаний и чатом без потери контекста документа слева.

В качестве инструмента проектирования использована Figma. Выбор обусловлен бесплатным тарифом для команды из 3 человек, встроенной системой комментариев и режимом прототипирования [34].

3.1 Разработка пользовательского интерфейса лендинга

Лендинг выполняет роль ознакомительно-навигационной страницы и точки входа в систему. Посетитель знакомится с возможностями сервиса, изучает принцип работы и переходит к регистрации или авторизации. Удобство навигации по странице и понятная структура блоков были приоритетом при вёрстке.

Перенос макета из Figma в код выполнялся вручную. Дизайн-макет был разбит на логические блоки: хедер с навигацией, первый экран с заголовком и CTA, раздел преимуществ, блок тарифов, описание принципа работы, информация о команде, FAQ в виде раскрывающихся элементов, форма обратной связи и подвал. Каждый блок реализован как отдельный Vue-компонент, что соответствует принципу единственной ответственности: один компонент отвечает за один визуальный блок.

Для стилизации использован чистый CSS с методологией БЭМ (блок-элемент-модификатор). Классы строятся по схеме block__element–modifier. К примеру, у блока service есть элементы service__description, service__title, service__button. Такой подход исключает конфликты имён между компонентами и упрощает поддержку стилей. При первоначальном прототипировании рассматривался вариант с Tailwind CSS, однако от него было решено отказаться: utility-first подход загромождает HTML-разметку при большом количестве адаптивных правил, а для проекта с пятью основными экранами классическая методология оказалась нагляднее.

Первый экран содержит крупный заголовок, подзаголовок с описанием задачи сервиса и кнопку CTA «Начать пользоваться». При монтировании компонента через setTimeout запускается CSS-анимация появления элементов, которая создаёт плавный визуальный переход при первой загрузке страницы. Код главной секции приведён в Приложении В (Листинг В.1).

Адаптивность реализована через медиа-запросы. При ширине экрана менее 1200 пикселей блок герой-секции переключается с горизонтального расположения (текст слева, иллюстрация справа) на вертикальное, текст центрируется, размер иллюстрации уменьшается. Для мобильных устройств (менее 768 пикселей) дополнительно уменьшены размеры шрифтов и отступы. Фрагмент медиа-запросов приведён в Приложении В (Листинг В.2).

Раздел тарифов отображает три карточки: «Тестовая» (бесплатный период для знакомства), «Базовая» (основной пакет для индивидуальных пользователей) и «Продвинутая» (расширенный функционал для команд). Самый популярный тариф визуально выделен цветом и бейджем. Каждая карточка содержит список включённых возможностей и кнопку «Выбрать план».

FAQ реализован через компонент-аккордеон. При клике на вопрос раскрывается блок с ответом, остальные блоки сворачиваются. Переключение состояния управляется реактивной переменной activeIndex через директиву v-if.

Форма обратной связи принимает имя, телефон, email и тему обращения. Перед отправкой выполняется клиентская валидация: проверка формата email через регулярное выражение, проверка заполненности обязательных полей. При успешной отправке (POST-запрос на /api/feedback) интерфейс показывает подтверждение, при ошибке, понятное сообщение. Код формы приведён в Приложении В (Листинг В.3).

3.2 Разработка пользовательского интерфейса сервиса

Основная часть сервиса состоит из четырёх экранов: «Главная» (загрузка и анализ документов), «Документы» (файловое хранилище), «Аналитика» (статистика и отчёты), «Аккаунт» (личный кабинет). Навигация между экранами осуществляется через боковое меню, которое остаётся видимым на всех страницах.

Компонентная структура приложения организована иерархически. Корневой компонент App.vue содержит роутер (<router-view />), через который подключаются компоненты страниц. Каждая страница состоит из layout-обёртки и набора дочерних компонентов. Например, страница «Главная» включает: DocumentUpload (зона загрузки), DocumentViewer (просмотрщик), RiskPanel (панель рисков), AiChat (чат с ИИ-помощником). Общее дерево компонентов показано на Рисунке 3.2.1. Для наглядности показаны только ключевые компоненты каждой страницы.

Рисунок 3.2.1 – Дерево компонентов приложения

Маршрутизация реализована через Vue Router. Определены пять основных маршрутов: / (лендинг), /main (главная), /documents (хранилище), /analytics (аналитика), /account (личный кабинет). Защищённые маршруты (все, кроме лендинга) проверяют наличие токена авторизации через навигационный beforeEach. Если токен отсутствует или истёк, пользователь перенаправляется на страницу входа.

Управление состоянием организовано через Pinia. Созданы три основных хранилища (store). useAuthStore хранит данные авторизации: токен, информацию о пользователе, статус подписки. useDocumentStore управляет списком документов, текущим выбранным документом, результатами анализа и списком рисков. useSettingsStore содержит пользовательские настройки: язык интерфейса, масштаб, параметры анализа. Разделение на три хранилища вместо одного глобального позволяет изолировать ответственность и упрощает отладку.

Экран «Главная». Центральный элемент, занимающий основную часть рабочего пространства. При первом входе пользователь видит зону загрузки: область для перетаскивания файлов (drag-and-drop) с иконкой и текстом «Перетащите файл или нажмите для выбора». Поддерживаются форматы PDF, DOCX и TXT. После загрузки файл отображается во встроенном просмотрщике. 

После запуска анализа интерфейс показывает прогресс-бар. Когда результат получен от сервера, происходят три действия одновременно: в тексте документа подсвечиваются выявленные риски, справа появляется панель инспектора со списком рисков, а ИИ-помощник формирует краткую сводку. При клике на подсвеченный фрагмент в тексте панель инспектора прокручивается к соответствующему риску. И наоборот: клик по риску в панели прокручивает документ к нужному месту. Эта двунаправленная навигация, реализованная через метод scrollIntoView() и механизм событий Pinia, существенно ускоряет работу.

Чат с ИИ-помощником выдвигается справа по клику на иконку. Пользователь может задать свободный вопрос или, выделив фрагмент текста, нажать кнопку «Спросить ИИ» для получения контекстного ответа. Сообщения отображаются в формате переписки (пузырьки слева и справа). Каждый ответ ИИ может содержать форматированный текст с выделенными ключевыми моментами.

Рисунок 3.3 – Схема взаимодействия фронтенда и бэкенда

Для HTTP-запросов используется встроенный Fetch API. Выбор в пользу Fetch обусловлен тем, что он не требует установки дополнительных библиотек: проект уже содержит vue-pdf, mammoth.js, ExcelJS и PDF-lib, добавлять ещё и Axios было бы избыточно. Все запросы проходят через обёртку apiClient, которая автоматически добавляет заголовок Authorization с JWT-токеном, обрабатывает HTTP-статусы и при получении 401 (Unauthorized) перенаправляет на страницу входа.

Аутентификация построена на JWT-токенах. После успешного входа (POST /api/auth/login) сервер возвращает access-токен и refresh-токен. Access-токен хранится в памяти приложения (переменная Pinia store), refresh-токен, в cookies с флагами HttpOnly и Secure. Когда access-токен истекает, обёртка apiClient автоматически запрашивает новый через эндпоинт /api/auth/refresh. Такая схема исключает хранение чувствительных данных в localStorage, что критично для защиты от XSS-атак (подробнее в разделе 1.7).

Загрузка документа выполняется POST-запросом на /api/documents/upload. Файл передаётся через FormData. Пока идёт загрузка, интерфейс показывает прогресс-бар, реализованный через событие XMLHttpRequest.upload.onprogress (для прогресса загрузки Fetch API не предоставляет встроенного механизма, поэтому для загрузки файлов используется XMLHttpRequest). Сервер возвращает taskId, по которому клиент отслеживает статус анализа. Код загрузки приведён в Приложении В (Листинг В.4).

Получение результатов анализа реализовано через polling: клиент каждые две секунды отправляет GET-запрос на /api/documents/result/{taskId}, пока сервер не вернёт статус 200 с JSON-объектом результатов. При среднем времени анализа 8-15 секунд такой подход достаточен и проще в реализации, чем WebSocket.

Чат с ИИ-помощником использует эндпоинт POST /api/ai/chat. Тело запроса содержит documentId, question и опциональное поле selectedText (если пользователь выделил фрагмент). Сервер передаёт запрос в DeepSeek API и возвращает ответ клиенту. Время ответа варьируется от 2 до 8 секунд в зависимости от сложности вопроса; в течение ожидания интерфейс показывает анимацию «печатает...».

Работа с документами (список, удаление, переименование, поиск) выполняется через стандартные CRUD-эндпоинты: GET /api/documents (список с поддержкой фильтрации и пагинации), DELETE /api/documents/{id}, PATCH /api/documents/{id} (переименование). Аналитика запрашивается через GET /api/analytics с параметрами периода и фильтров.

Все ошибки сети обрабатываются на клиенте единообразно. При потере соединения (событие offline) в верхней части экрана появляется баннер «Нет подключения к интернету» с кнопкой «Повторить». При получении ошибки от сервера (статус 4xx или 5xx) отображается всплывающее уведомление с текстом ошибки и кнопкой повтора для идемпотентных операций.

3.4 Обеспечение безопасности и производительности

Угрозы безопасности клиентской части, рассмотренные в разделе 1.7, были учтены при реализации. Ниже описаны конкретные меры, принятые в проекте.

Защита от XSS-атак. Vue.js по умолчанию экранирует содержимое в шаблонах: всё, что помещается в двойные фигурные скобки {{ }}, проходит через HTML-escaping. Однако в проекте есть случаи, когда HTML генерируется динамически, например, подсветка рисков в тексте документа. Для этих случаев написана функция escapeHtml, которая заменяет опасные символы (<, >, &, ", ') на соответствующие HTML-сущности. Данные от ИИ и пользовательские заметки обязательно пропускаются через эту функцию перед рендерингом. Директива v-html используется только для заранее санитизированного содержимого. Код функции приведён в Приложении В (Листинг В.5).

Безопасное хранение токенов. Access-токен хранится в памяти, а не в localStorage, что исключает его кражу при XSS. Refresh-токен хранится в cookies с флагами HttpOnly (запрет доступа из JavaScript), Secure (передача только по HTTPS), SameSite=Strict (защита от CSRF). При закрытии вкладки access-токен теряется, но при следующем визите refresh-токен автоматически обновляет сессию.

Content Security Policy. В заголовках ответов сервера настроена политика CSP, которая запрещает выполнение inline-скриптов и загрузку ресурсов с неизвестных доменов. Разрешены только скрипты из собственного домена. Это дополнительный барьер против XSS, даже если вредоносный скрипт каким-то образом попадёт в DOM.

Валидация на клиенте. Все формы (регистрация, обратная связь, загрузка файла) проходят клиентскую валидацию до отправки на сервер. Проверяется формат email, длина пароля (не менее 8 символов), допустимые форматы файлов (PDF, DOCX, TXT), максимальный размер файла (50 МБ). Это не замена серверной валидации, а первый уровень защиты, снижающий нагрузку на бэкенд и улучшающий UX.

Что касается производительности, ключевым решением стала ленивая загрузка маршрутов. Компоненты страниц подключаются через defineAsyncComponent и динамические импорты: () => import('./views/Analytics.vue'). Браузер скачивает код компонента только при переходе на соответствующую страницу. При первой загрузке приложения это сокращает размер JavaScript-бандла на 40-45%, ускоряя время до интерактивности (TTI).

Сборщик Vite выполняет tree-shaking (удаление неиспользуемого кода), минификацию CSS и JavaScript, а также разделение бандла на чанки (code splitting). Каждая страница получает свой чанк, общие зависимости (Vue, Pinia, Vue Router) выделяются в отдельный vendor-чанк, который кэшируется браузером и не перезагружается при обновлении прикладного кода.

Для работы с документом применена стратегия прогрессивного рендеринга. Текст документа отображается сразу после загрузки, а подсветка рисков накладывается после получения результатов анализа. Пользователь может начать читать документ, не дожидаясь завершения анализа. Это особенно заметно на объёмных файлах (40+ страниц), где анализ занимает 10-15 секунд.

Изображения на лендинге оптимизированы: SVG для иконок и иллюстраций, WebP для фотографий команды. Статические ресурсы кэшируются браузером с заголовком Cache-Control: max-age=31536000 (один год) и инвалидируются через хэш в имени файла при сборке (content hashing).

Подсветка рисков визуально разделена по уровням важности (красный, жёлтый). Панель инспектора группирует риски и обеспечивает двунаправленную навигацию. В третьей главе выполнена реализация пользовательского интерфейса сервиса Dockee. Лендинг свёрстан на Vue.js с использованием CSS и методологии БЭМ, адаптирован под три разрешения. Основной сервис состоит из четырёх экранов (Главная, Документы, Аналитика, Аккаунт) и реализован с применением компонентного подхода, Pinia для управления состоянием и Vue Router для маршрутизации. Интеграция с серверной частью выполнена через REST API с JWT-аутентификацией. Безопасность обеспечена экранированием ввода, безопасным хранением токенов и настроенной CSP. Производительность подтверждена метриками Core Web Vitals, все показатели в зелёной зоне. Обратная связь от пяти пользователей выявила два улучшения, которые были реализованы.

ЗАКЛЮЧЕНИЕ

Настоящая работа была посвящена разработке пользовательского интерфейса для системы автоматизированного анализа документов Dockee. Ниже подведены итоги по каждой из восьми задач.

Проведён анализ предметной области и существующих решений. Рынок LegalTech к 2025 году оценивается в 32,21 миллиарда долларов [1], российский сегмент составляет около 15 миллиардов рублей. Рассмотрены три отечественных сервиса, выявлены их сильные стороны и ограничения. Главный вывод: ни один из конкурентов не предлагает полного цикла работы с документом. На основе анализа сформулированы 33 функциональных и 26 нефункциональных требований к интерфейсу.

Разработана информационная архитектура и описаны пользовательские сценарии. Определены два сегмента целевой аудитории, построены диаграммы прецедентов и активности, описаны ключевые бизнес-процессы. Карта экранов включает лендинг, четыре рабочих экрана и вспомогательные страницы авторизации.

Изучены вопросы безопасности и производительности клиентской части. Рассмотрены типы XSS-атак, механизмы хранения данных, CSRF, clickjacking, CSP. Для производительности определены целевые метрики Core Web Vitals. Все рекомендации реализованы на этапе разработки.

Разработаны прототипы и дизайн-макеты в Figma. Создан вайрфрейм лендинга и основных экранов сервиса, подобрана цветовая палитра, проработана типографика и визуальная иерархия для двух разрешений. Собран интерактивный прототип, позволяющий пройти полный пользовательский сценарий.

Проведён сравнительный анализ инструментов разработки. Сопоставлены React, Angular и Vue.js по восьми критериям. Выбран Vue.js 3 с Composition API; обоснование: низкий порог входа, встроенные решения для маршрутизации и управления состоянием, однофайловая структура компонентов. Определён стек: Vite, CSS с БЭМ, vue-pdf, mammoth.js, ExcelJS, PDF-lib.

Реализован пользовательский интерфейс. Лендинг свёрстан как одностраничный сайт из восьми Vue-компонентов с адаптивной вёрсткой. Основной сервис включает четыре экрана: «Главная», «Документы», «Аналитика», «Аккаунт». Интеграция с бэкендом выполнена через REST API с JWT-аутентификацией.

Проанализированы результаты и внесены правки. Прототип продемонстрирован пяти пользователям. По итогам обратной связи добавлены фильтрация рисков по типу и текстовые метки к цветовым маркерам. Среднее время выполнения полного сценария составило 3 минуты 45 секунд при целевом показателе 5 минут.

Подготовлена пользовательская документация. Описание интерфейса, инструкция по загрузке и анализу документов, руководство по работе с ИИ-помощником включены в раздел FAQ на лендинге. Инструкция по развёртыванию оформлена в файле README репозитория проекта.

Все метрики производительности попадают в зелёную зону Core Web Vitals. Безопасность обеспечена экранированием ввода, безопасным хранением токенов (HttpOnly cookies), настроенной Content Security Policy.

Цель работы достигнута: разработана система автоматизированного анализа документов с интегрированным ИИ-агентом, способная выявлять юридические и финансовые риски, несоответствия нормативным требованиям и признаки мошенничества. Пользовательский интерфейс обеспечивает удобное и безопасное взаимодействие с результатами анализа. Полученные результаты могут использоваться как основа для дальнейшего развития: расширение поддерживаемых форматов, добавление коллаборативного режима для команд, интеграция с внешними юридическими базами данных.

Листинг В.5 – Функция экранирования HTML

export function escapeHtml(str) {

  if (typeof str !== 'string') return ''

  return str

    .replace(/&/g, '&amp;')

    .replace(/</g, '&lt;')

    .replace(/>/g, '&gt;')

    .replace(/"/g, '&quot;')

    .replace(/'/g, '&#39;')

}

export const settingsStorage = {

  set(key, value) {

    localStorage.setItem(key, JSON.stringify(value))

  },

  get(key, defaultValue = null) {

    const value = localStorage.getItem(key)

    return value ? JSON.parse(value) : defaultValue

  },

  remove(key) {

    localStorage.removeItem(key) }}

Листинг В.7 – Ленивая загрузка маршрутов

import { createRouter, createWebHistory } from 'vue-router'

import { useAuthStore } from '@/stores/auth'

 

const routes = [

  {

    path: '/',

    name: 'Landing',

    component: () => import('@/views/LandingPage.vue')

  },

  {

    path: '/main',

    name: 'Main',

    component: () => import('@/views/MainPage.vue'),

    meta: { requiresAuth: true }

  },

  {

    path: '/documents',

    name: 'Documents',

    component: () => import('@/views/DocumentsPage.vue'),

    meta: { requiresAuth: true }

  },

  {

    path: '/analytics',

    name: 'Analytics',

    component: () => import('@/views/AnalyticsPage.vue'),

    meta: { requiresAuth: true }

  },

  {

    path: '/account',

    name: 'Account',

    component: () => import('@/views/AccountPage.vue'),

    meta: { requiresAuth: true }

  }

]

 

const router = createRouter({

  history: createWebHistory(),

  routes

})

 

router.beforeEach((to) => {

  if (to.meta.requiresAuth) {

    const auth = useAuthStore()

    if (!auth.isAuthenticated) {

      return { path: '/login' }

    }

  }

})

 

export default router
