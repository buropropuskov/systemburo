# Рабочий процесс

## Ветки и задача

`dev` — рабочая интеграция, `staging` — зеркало после успешной поставки, `prod` — выпуск. Работать в отдельной ветке от актуального origin/dev, не теряя собственные или чужие незакоммиченные файлы. Для issue применяется `issue/НОМЕР`; для согласованной задачи без issue — отдельная ветка с понятным назначением.

До реализации согласовать результат, границы и приёмку. Issue вести по шаблонам `.github/ISSUE_TEMPLATE`; если публикация задачи отдельно исключена, не создавать её автоматически. PR — в dev; замечания и результаты обязательных проверок сверять по текущему HEAD.

## Коммиты и PR

Формат проверяет `.githooks/commit-msg`: короткое сообщение `type(scope): описание`, например `fix(ui): исправил подпись срока`. Ссылка на issue уместна, если issue существует. Точный набор допустимых типов и ограничения — в хуке, не в копии его регулярного выражения здесь.

Добавлять явный список собственных файлов, перед коммитом читать staged diff и проверять секреты. Описание PR должно содержать результат, объём, выполненные проверки и ограничения; не выдавать запланированный тест за выполненный.

Merge в dev выполняется после зелёных обязательных проверок нужного HEAD и разрешения блокирующих замечаний. Issue закрывается после подтверждённого результата; `Closes` не гарантирует немедленное закрытие при merge в ветку, которая не является default. После merge дождаться Deploy to Staging нужной ревизии и применимой ручной проверки. Production — отдельный согласованный релиз dev → prod; старый обязательный персональный reviewer из прежней инструкции больше не задаётся этим документом.

## Проверки и документация

Команды Go берутся из Makefile и выполняются в Docker проекта. Frontend — из `frontend/package.json`; Playwright — по конфигурации проекта. Объём проверок должен соответствовать изменённому поведению и риску. Не ослаблять тест/порог ради зелёного результата.

Для изменённого API сверять маршрут, DTO, фактический envelope и frontend-вызов; для прав — ещё видимость объекта и deny. Для обновления зависимости пересобирать THIRD-PARTY-NOTICES и проверять совместимость. Изменение схемы/конфигурации поставки требует отдельной оценки последствий.

В каждом PR оценить влияние на технические документы, руководства и обучение. Источник клиентского текста — Markdown в `Документация/`, сборка/факты — [Документация/src/README.md](Документация/src/README.md). Документационный долг фиксировать явно; не закрывать маркер синхронизации до сверки содержания.

Поведение конвейеров и границы доказательств: [docs/ci-cd.md](docs/ci-cd.md). CODEOWNERS — правило автоматического назначения ревью, не передача владения Git-файлами и не доказательство обязательного approve.

### Уязвимость, которую нечем закрыть

Проверка уязвимостей Go запускается не напрямую, а через `scripts/govulncheck_gate.py`. Причина простая: `govulncheck` не умеет ничего откладывать, а уязвимость без выпущенного исправления держала бы проверку красной неделями - и красный чек переставали бы читать вообще. Trivy в соседнем шаге по той же причине запущен с `ignore-unfixed`.

Отсрочка - не выключатель. Запись в `scripts/govulncheck-exceptions.json` живёт до своей даты пересмотра и перестаёт работать, как только у уязвимости появляется исправленная версия: в обоих случаях проверка падает и требует вернуться к записи. Запись про уязвимость, которая больше не находится, тоже роняет проверку - чтобы перечень не зарастал.

Заводить запись можно, когда выполнены оба условия: исправленной версии нет, и у нас есть, что написать в поле `why` про то, почему уязвимое место недостижимо или чем оно закрыто своими силами. «Потом разберёмся» причиной не считается - для этого есть задача, а не отсрочка.

```json
{
  "id": "GO-2026-XXXX",
  "module": "example.com/lib",
  "until": "2026-12-01",
  "why": "чем закрыто у нас и почему этого достаточно"
}
```

## Обновления зависимостей

Обновления приносит dependabot по понедельникам. Безопасные подъёмы (minor, patch) приходят одним PR на экосистему, мажоры - отдельными: мажор в общей группе держал в заложниках безопасную часть, так минорный подъём vite месяц ждал вместе с vitest 4 -> 5.

**PR от бота красный сам по себе - это ожидаемо, а не поломка.** `THIRD-PARTY-NOTICES.md` собирается из репозитория и уходит заказчику, поэтому его сверяют два замка: Go-тест в `internal/legal` и спека `frontend/src/__tests__/thirdPartyNotices.spec.js`. Бот меняет версию в `go.mod` или `package-lock.json`, а перечень пересобрать не может - замки видят расхождение и честно краснеют:

```
версии в перечне разошлись со сборкой: golang.org/x/text: в перечне v0.41.0, в сборке v0.42.0
```

Что делать: перенести подъём версий в свою ветку от свежего `dev`, пересобрать там перечень и открыть обычный PR. PR бота после мержа закрыть со ссылкой на свой. В ветки dependabot не пушим: они принадлежат боту, он их пересоздаёт при следующем обновлении, и дослованный коммит пропадает вместе с веткой.

```bash
git fetch origin
git checkout -b deps/go-minor origin/dev
git cherry-pick <коммит-бота>
make notices          # python3 scripts/gen-third-party-notices.py
git commit -am "build(deps): пересобрал перечень компонентов"
git push -u origin HEAD
```

Автоматизировать это шагом конвейера нельзя: у workflow на PR от бота токен только для чтения, а `pull_request_target` дал бы запись, но потребовал бы запустить `npm ci` и компиляцию Go на коде обновляемых зависимостей - то есть выполнить чужой код с правом записи в репозиторий, ровно там, где и живёт риск подмены пакета. Ручной коммит дешевле этой дыры.

**Мажоры разбираются как задачи, а не как подъём версии.** Перед мержем читать список ломающих правок и проверять то, на что они влияют: среда тестов - полным прогоном, редактор - существующими текстами новостей и руководства. Если работа не на один заход, лучше закрыть PR бота со ссылкой на задачу, чем держать его открытым месяцами.


## Локальная настройка

```bash
git clone git@github.com:buropropuskov/systemburo.git
cd systemburo
make init
cp .env.example .env
# Задать локальные секреты, ключ шифрования и настройки HTTP; не публиковать .env.
make up
```

Повторный seed может изменить существующий пароль; демоданные не добавляют в рабочую БД ради проверки. Установка и сопровождение — [docs/DEPLOYMENT.md](docs/DEPLOYMENT.md).
