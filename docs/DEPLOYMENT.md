# Развёртывание и сопровождение

Сверено с репозиторием 14.10.2026. Подробная инструкция оператора — [руководство сопровождения](../Документация/Руководство%20по%20развёртыванию%20и%20сопровождению/Руководство%20по%20развёртыванию%20и%20сопровождению.md). Здесь — карта команд и границы сред. Примеры не являются разрешением менять production.

## Локальная разработка

Нужны Docker/Compose v2 и настроенный `.env`. Версии образов — Dockerfile/Compose, Go — `go.mod`, frontend CI — Node.js 22. Go в этом проекте запускается через Docker.

```bash
cp .env.example .env
# Задать DATABASE/JWT/ключ шифрования и параметры локального HTTP.
make init
make up
```

Dev Compose использует службы `go-backend`, `frontend`, `db`, `pgadmin`; HTTP backend — localhost:8080, frontend — localhost:8081, pgAdmin — localhost:8082. Внутренний BIND_PORT может отличаться от внешнего порта. Проверка живости: `curl http://localhost:8080/health`; формат ответа сверять с handler, не зашивать неподтверждённый пример.

`make seed` создаёт/обновляет тестового администратора. Повторный запуск может заменить пароль; не выполнять его как безвредную проверку доступности. `seed-demo` дополнительно изменяет много данных. На реальных средах демонабор не нужен.

Для локального frontend вне контейнера: `npm ci`, `npm run dev` в frontend. `npm run serve` не существует. Ключи шифрования обязательны по умолчанию; для локального HTTP проверить CookieSecure, для HTTPS — оставить Secure.

## Staging и production

Compose-файлы накладываются на базовый:

```bash
# Примеры состава конфигурации, не выполнять без подготовки среды:
docker compose -f docker-compose.base.yml -f docker-compose.staging.yml config --quiet
docker compose -f docker-compose.base.yml -f docker-compose.prod.yml config --quiet
```

Тихая валидация не раскрывает подставленные секреты. `make staging-*` и `make deploy-*` используют соответствующие пары файлов. Инициализация окружения — `scripts/init-env.sh`, TLS — `scripts/init-tls.sh`; не устанавливать host certbot поверх контейнерной схемы по старому краткому рецепту.

Staging имеет дополнительный Basic Auth. Его логин не заменяет вход приложения. pgAdmin в staging существует как опциональный профиль tools; утверждение «pgAdmin только в dev» неверно. В production Compose его нет.

Автоматическая поставка описана в [ci-cd.md](ci-cd.md). На время обновления применяется согласованный порядок техработ, после поставки проверяются SHA, нужный API и рабочий сценарий. `/health` подтверждает только свой контракт, не успешную миграцию любого сценария. Доступность старой страницы после обновления не доказывает совместимость её кода с новой версией.

## Файлы, архивы и резервные копии

База, uploads, файловый архив и ключи требуют согласованного резервирования. `ARCHIVE_PATH` и `ENTITY_EXPORT_PATH` должны находиться вне uploads; архив/выгрузки могут содержать открытые ПД. HTTP-доступ к uploads уже защищён, но это не причина размещать там самостоятельные массовые выгрузки.

Для архива age-пара получателя/identity задаётся совместно. Не менять ключи и не форматировать раздел по универсальному примеру. Шифрование диска, шифрование выгрузки и шифрование полей БД защищают разные уровни и не заменяют друг друга.

Штатные команды: `make backup`, `backup-status`, `backup-verify`; для других сред — соответствующие префиксы. Восстановление меняет данные, выполняется только по отдельной процедуре и подтверждению. Сначала проверить комплектность, ключи, дату/версию и восстановимость на изолированной среде; один SQL dump не содержит всех файлов. Результат резервирования может быть успешным с предупреждением о слишком долгом хранении копий — предупреждение нужно разобрать, не считать успешный exit отсутствием замечаний.

## Хранение и наблюдение

Сроки задаёт владелец установки. `APPLICATION_RETENTION_MONTHS=0` отключает автоматическое обезличивание заявок; `AUDIT_RETENTION_MONTHS=0` отключает автоматическую уборку истории сущностей. Это отдельные механизмы. `MAIL_MESSAGE_RETENTION_DAYS=30` относится к очереди почты, не к mailbox получателя. `PD_AUDIT_RETENTION_MONTHS=36` относится к журналу ПД, не ко всем журналам.

Проверять `compose ps`, логи нужной службы, состояние резервных копий и заполнение диска. Не оставлять тестовые контейнеры/сборщики работающими после проверки. При сбое не запускать reset/clean/restore автоматически: определить, что именно нарушено, и сохранить доказательства без токенов и ПД.

## Входящий прокси и лимиты файлов

Backend доверяет адресу внутреннего nginx, а не всем частным сетям. Для staging и production выделена отдельная настраиваемая подсеть: пересечение с занятой сетью нужно устранить выбором свободной подсети, не отключением проверки. При прямом подключении посетителей дополнительный внешний доверенный прокси не нужен. Если перед nginx есть внешний прокси, в `EDGE_TRUSTED_PROXY_CIDRS` указывают только подтверждённые адреса этого узла; входящие заголовки посетителя сами по себе источником доверия не являются. Точные параметры и порядок проверки приведены в полном руководстве сопровождения.

Файлы-черновики ограничены на владельца: по умолчанию 50 файлов и 200 МиБ, включая текущие загрузки. Это отдельная квота от файлов поданной заявки. Неподанные файлы убираются по сроку хранения черновиков; принятые файлы заявки этим механизмом не удаляются. До изменения лимитов сверяют серверную конфигурацию и ограничения формы: сейчас форма допускает 10 файлов, серверный предел заявки по умолчанию — 30.
