# Безопасность приложения

Сверено с кодом 14.10.2026. Это описание технических механизмов, не заключение о соответствии законодательству и не результат полного аудита инфраструктуры.

## Сессии и пароли

Источники: `internal/services/auth_service.go`, `internal/handlers/auth.go`, `internal/config/config.go`.

- Access JWT: по умолчанию 15 минут; хранится в памяти frontend. Refresh: 168 часов; в HttpOnly cookie (`Path=/api`, SameSite=Strict, Secure по конфигурации), в БД — хеш. Refresh не отдаётся в JSON, при продлении ротируется.
- Для staging/production нужен HTTPS и `COOKIE_SECURE=true`. Значение false допустимо для локального HTTP, не является способом исправить вход на публичном стенде.
- Пароли хешируются Argon2id (m=19456, t=2, p=1); параметры чтения старого хеша проверяются. JWT-секреты валидируются конфигурацией, значения не публикуются в примерах.
- Есть ограничения входа по IP и блокировка учётной записи после неверных попыток, с нарастанием времени. Значения и границы — в auth service; старое утверждение «account lockout отсутствует» неверно.
- Бан, неактивность, обязательная смена пароля и согласие на обработку ПД проверяются отдельно. Вход под другим пользователем оставляет собственные ограничения и аудит.

## Права и видимость

Источник — `permission_resolver.go`: неактивность/бан запрещают доступ прежде суперправ; затем super, admin с исключением super-only и личных deny, затем объединение роли/групп и пользовательские overrides. Личный allow обычного пользователя может заменить групповой deny; личный deny запрещает действие. Ключи не образуют неявную иерархию по строковому префиксу.

`RequirePermissionV2` проверяет действие и журналирует отказ. Наличие права на действие не даёт видимость каждой записи: сервис отдельно проверяет заявку, таблицу, организацию и политику ПД. Скрытый frontend-элемент не является защитой API. Бизнес-тип `type_id` не заменяет признак super-admin.

Для чтения/поиска/экспорта действует политика отображения ПД: нельзя фильтровать по скрытой фамилии и тем самым раскрывать наличие записи. Для новых записей истории пересылки получатели проверяются по ID. Старые записи без ID не раскрывают непроверенные имена и не связываются с пользователем по совпадению имени.

При снятии возражения право администратора проверяется до загрузки записи: обычный пользователь не узнаёт о существовании ID по различию 403/404. При частичном обновлении человека непереданные поля не трактуются как попытка изменения ПД; реально запрещённое изменение сохраняет 409. Это разные причины отказа, нельзя унифицировать их снятием проверок.

## Шифрование и хранение

`internal/crypto` использует AES-256-GCM и HMAC для поиска по защищённым полям; hooks моделей выполняют преобразование. Какие поля защищены, проверять по текущим моделям, а не только по паспорту/патенту старого описания.

`REQUIRE_ENCRYPTION=true` по умолчанию: пустой/неподходящий ключ не должен молча перевести установку на открытое хранение. Ключ и резервные копии ключа хранить отдельно с ограничением доступа. Нельзя произвольно заменить ключ в рабочей базе: потребуется согласованное преобразование существующих данных.

Файлы и выгрузки — отдельная поверхность защиты. `/api/uploads` имеет FileAccess, сканы — дополнительную проверку принадлежности. Архив и `ENTITY_EXPORT_PATH` находятся вне загрузок. Выгрузка может содержать открытые ПД даже при зашифрованной БД; доступ к файлам, резервным копиям и age-ключам регулируется отдельно.

Хранение настраивается: `APPLICATION_RETENTION_MONTHS=0` и `AUDIT_RETENTION_MONTHS=0` отключают соответствующую автоматическую обработку; включение меняет сохранность данных и требует решения владельца. При обработке заявок ПД обезличиваются, это не удаление всей заявки. `PD_AUDIT_RETENTION_MONTHS=36`, технические журналы/уведомления/почта имеют собственные сроки. Полный перечень и исключения — руководство сопровождения и `internal/database/retention*.go`.

## Аудит и согласия

`internal/middleware/pd_audit.go` содержит фактический список путей аудита: помимо людей/вложений туда входят поиск, пользователи, кандидаты получателей и массовые выгрузки. Он не равен «все запросы ко всем ПД» и не заменяет доменную историю. Запись выполняется асинхронно с отдельным контекстом и ограничением времени.

Согласия, их редакции, отзыв и блокирующий гейт — отдельные механизмы. Кабинет субъекта ПД и обработка обращений имеют специальные права. Наличие интерфейса не является разрешением выполнять массовое обезличивание или менять установленный срок хранения без согласования.

## Загрузки, экспорт и сеть

- Тип/размер загрузки проверяются; для изображений нормализация ограничивает исходное изображение 25 миллионами пикселей до полного декодирования. Это площадь (ширина × высота), не размер файла в мегабайтах. Применение смотреть в handlers, лимит не означает сжатие любых файлов до 25 МБ.
- Периоды и пагинация валидируются; безопасные выгрузки не должны превращать содержимое ячейки в формулу электронной таблицы.
- Ссылки Web Push проверяются по допустимым узлам; `PUSH_ALLOWED_HOSTS` расширяет разрешённые адреса служб доставки, не является универсальным разрешением произвольного URL.
- Общее ограничение запросов и отдельное ограничение входа имеют разные настройки. In-memory ограничение не является общим распределённым счётчиком нескольких процессов.
- DOMPurify уже установлен и используется; старое требование «сначала установить DOMPurify» устарело. Каждую точку HTML всё равно нужно проверять по реальному пути обработки.

## nginx и CSP

`nginx/nginx.conf` задаёт для script-src self и nonce запроса. HTML проходит подстановку nonce, поэтому внешний прокси отключает upstream-сжатие HTML. Для `/assets/` отдельная обработка передаёт Accept-Encoding и сохраняет сжатие JS/CSS. Не переносить ослабленный CSP Swagger из staging на основной интерфейс.

`nginx/staging.conf` включает дополнительный Basic Auth для стенда; защита учитывается для HTML, API, assets и служебных путей по конкретной location. Basic Auth не заменяет сессию и права приложения. Внешний TLS-терминатор/хостинг также влияет на итоговый HTTPS; содержимое репозитория не доказывает настройки конкретного сервера.

## Проверки безопасности

`security.yml`: Gitleaks по истории, govulncheck через `scripts/govulncheck_gate.py`, production npm audit high+, отдельный информационный аудит dev-зависимостей, Trivy high/critical с ignore-unfixed. Проверки запускаются на push/PR dev/prod и по расписанию. Исключения govulncheck ограничены сроком и условиями; их изменение не заменяет исправление.

Наличие зелёного workflow не доказывает отсутствие всех уязвимостей. Текущая конфигурация веток, секретов/environments, публикация сервисов и firewall не устанавливаются из этого документа. Последние два пункта не входят в согласованный объём проверки.
