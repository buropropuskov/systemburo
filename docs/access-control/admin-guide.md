# Руководство администратора по системе прав

Описание для супер-администратора. Покрывает создание ролей, групп прав, назначение пользователям, журнал отказов и блокировку.

## Концепция

Роль задаёт бизнес-положение пользователя, прямые права и default-группы. Явные группы пользователя дополняют роль; личные разрешения и запреты применяются поверх групп. Каталог и операции доступны по собственным правам, а не по номеру типа учётной записи.

Приоритет: бан/неактивность → запрет; super-admin → полный доступ; admin → доступ кроме super-only и личных deny; обычный пользователь → роль/группы с личными overrides. Личный allow обычного пользователя может перекрыть групповой deny. Не выдавайте super-admin ради одной недостающей операции.

Отдельные права управляют общим сроком вложений, индивидуальным сроком человека/машины и исправлением учёта прохода. Наличие права не возвращает видимость чужой или архивной записи. Текущий каталог — в интерфейсе настройки прав и permission_keys.go.

Обычный администратор не может сбрасывать пароль административной учётной записи или менять её почту: это действие суперадминистратора. Собственный пароль меняется с подтверждением текущего пароля. Маска имени принимающего не скрывает его от действующего администратора, однако отсутствие согласия на обработку данных действует и для административного просмотра.

## Создание роли

1. Боковое меню → Админка → **Роли**.
2. Кнопка **«+ Создать роль»**.
3. Заполните: название (Арендатор), код латиницей (`tenant`, неизменный), описание.
4. Сохранить.
5. Кнопка **«Настроить группы»** на карточке роли — выберите default-группы.

## Создание группы прав

1. Боковое меню → Админка → **Группы прав**.
2. Кнопка **«+ Создать группу»**, введите название.
3. После создания откроется модалка-редактор прав: дерево по namespace (`page.*`, `tab.*`, `entity.*`, `action.*`, `permission.audit.*`). Выберите нужные разрешения в дереве.
4. Поиск по ключу или описанию.
5. Кнопка «Сохранить» применит набор. Резолвер инвалидирует кэш — изменения вступают в силу при следующем polling-цикле (≤30s).

## Назначение пользователю

1. Админка → Пользователи. Выберите пользователя.
2. Кнопка **«Роль и группы прав»** в action bar.
3. В модалке:
   - Дропдаун **«Роль»** — выберите бизнес-роль или «Без роли».
   - Выбор **«Дополнительные группы прав»** — добавляются поверх default-групп роли.
4. Сохранить.

## Составная группа

Если у пользователя 2+ группы — это «Составная» (визуальная метка, отдельной сущности в БД нет).

**«Слить выбранные в новую группу»** — кнопка появляется при ≥2 группах. Действие создаёт новую обычную группу с union прав; у пользователя её записи `user_groups` заменяются на одну новую. Старые группы остаются в системе и могут быть назначены другим юзерам.

## Блокировка пользователя

В модалке «Роль и группы прав» секция «Блокировка»:

- **Заблокировать** — запрещает рабочие действия и отзывает прежние сессии. Для заблокированной учётной записи предусмотрено ограниченное чтение собственного кабинета и своих заявок; чужое и служебное чтение не разрешается. Неактивная архивная учётная запись не получает этот доступ.
- **Нельзя забанить super-admin** (защита).
- **Нельзя забанить себя** (защита).

После бана:
- В навигации все пункты серые/disabled, кроме «Личный кабинет» и «Выйти».
- В ЛК баннер «Учётная запись заблокирована».
- Журнал отказов получает запись с `reason=account_banned` при попытке открыть любую защищённую страницу.

**Разблокировать** — `is_banned=false`. Refresh-токены остаются revoked, юзеру нужно перелогиниться.

## Журнал отказов

Админка → **Журнал отказов**.

Поля записи: ID, дата, пользователь, ресурс (метод+путь), требуемое право, причина (`permission_denied` / `account_banned`), IP.

Фильтры: ID пользователя, подстрока ресурса, причина, период.

Переключатель **Активные / Архив**:
- Активная таблица — последние 3 месяца.
- Архив — старше, доступен для аудита.

Действия:
- **Очистить с фильтрами** — selective DELETE из активной таблицы.
- **Архивировать всё за период** — массовый перенос в архив.

Cron автоматически переносит записи старше 90 дней раз в сутки.

## Восстановление super-admin

Восстановление доступа — отдельная административная операция. Сначала проверить причину отказа: пароль, временную блокировку входа, бан, неактивность, признак super-admin или настройки среды. Повторный seed может заменить существующий пароль и не является безвредной диагностикой. Прямой SQL из старой инструкции не применять автоматически. Использовать согласованную процедуру сопровождения с проверенной резервной копией и аудитом выполненных действий.
