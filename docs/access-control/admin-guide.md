# Руководство администратора по системе прав

Описание для супер-администратора. Покрывает создание ролей, групп прав, назначение пользователям, журнал отказов и блокировку.

## Концепция

Система прав построена на трёх уровнях:

1. **Роль** — кем является пользователь (Арендатор, Охранник, Руководитель). Одна роль на пользователя. Роль не содержит прав напрямую.
2. **Группа прав** — именованный набор разрешений ("Доступ ко всем таблицам", "Управление заявками"). Не привязана к роли жёстко.
3. **Привязка** — каждой роли можно задать набор default-групп, и каждому пользователю — дополнительные группы поверх роли.

Финальные права пользователя:

```
super-admin?  -> все права (bypass)
banned?       -> ноль прав (bypass)
otherwise:
  permissions = (default-groups роли) ∪ (явные группы пользователя)
  поверх: user_permission_overrides (deny здесь побеждает любое allow)
```

## Создание роли

1. Боковое меню → Админка → **Роли**.
2. Кнопка **«+ Создать роль»**.
3. Заполните: название (Арендатор), код латиницей (`tenant`, неизменный), описание.
4. Сохранить.
5. Кнопка **«Настроить группы»** на карточке роли — выберите default-группы.

## Создание группы прав

1. Боковое меню → Админка → **Группы прав**.
2. Кнопка **«+ Создать группу»**, введите название.
3. После создания откроется модалка-редактор прав: дерево по namespace (`page.*`, `tab.*`, `entity.*`, `action.*`, `permission.audit.*`). Чекбоксы.
4. Поиск по ключу или описанию.
5. Кнопка «Сохранить» применит набор. Резолвер инвалидирует кэш — изменения вступают в силу при следующем polling-цикле (≤30s).

## Назначение пользователю

1. Админка → Пользователи. Выберите пользователя.
2. Кнопка **«Роль и группы прав»** в action bar.
3. В модалке:
   - Дропдаун **«Роль»** — выберите бизнес-роль или «Без роли».
   - Чекбоксы **«Дополнительные группы прав»** — добавляются поверх default-групп роли.
4. Сохранить.

## Составная группа

Если у пользователя 2+ группы — это «Составная» (визуальная метка, отдельной сущности в БД нет).

**«Слить выбранные в новую группу»** — кнопка появляется при ≥2 группах. Действие создаёт новую обычную группу с union прав; у пользователя её записи `user_groups` заменяются на одну новую. Старые группы остаются в системе и могут быть назначены другим юзерам.

## Блокировка пользователя

В модалке «Роль и группы прав» секция «Блокировка»:

- **Заблокировать** — `is_banned=true` + revoke всех refresh-токенов. На следующий запрос юзер получит 401, фронт сделает logout.
- **Нельзя забанить super-admin** (защита).
- **Нельзя забанить себя** (защита).

После бана:
- В навигации все пункты серые/disabled, кроме «Личный кабинет» и «Выйти».
- В ЛК баннер «Учётная запись заблокирована».
- Журнал отказов получает запись с `reason=account_banned` при попытке открыть любую защищённую страницу.

**Разблокировать** — `is_banned=false`. Refresh-токены остаются revoked, юзеру нужно перелогиниться.

## Журнал отказов

Админка → **Журнал отказов**.

Поля записи: ID, дата, пользователь, ресурс (метод+путь), требуемое право, причина (`permission_denied` / `account_banned`), IP.

Фильтры: ID пользователя, подстрока ресурса, причина, период.

Переключатель **Активные / Архив**:
- Активная таблица — последние 3 месяца.
- Архив — старше, доступен для аудита.

Действия:
- **Очистить с фильтрами** — selective DELETE из активной таблицы.
- **Архивировать всё за период** — массовый перенос в архив.

Cron автоматически переносит записи старше 90 дней раз в сутки.

## Восстановление super-admin

Если случайно забанили / удалили единственного super-admin:

```bash
make staging-seed PASS=newpass    # пересоздаёт buropropuskov с is_super_admin=true
```

или прямой SQL:

```sql
UPDATE users SET is_super_admin = true, is_banned = false WHERE username = 'buropropuskov';
```
