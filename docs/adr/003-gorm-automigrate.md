# ADR-003: GORM с AutoMigrate

> Актуализация 21.10.2026: Запись описывает исходный выбор GORM, а не инструкцию изменения рабочей БД. Текущий запуск включает дополнительные явные миграции из internal/database/migrate.go; изменение схемы требует отдельной процедуры и проверки. Рекомендация о замене мигратора ниже сама по себе не означает выполненного или утверждённого перехода.

**Статус:** Принято, требует пересмотра для production

## Контекст

Нужен ORM для PostgreSQL. Альтернативы: sqlc (генерация из SQL), sqlx (типизированные запросы), Ent (кодогенерация графов).

Для миграций: файловые миграции (goose, golang-migrate) vs AutoMigrate.

## Решение

GORM с AutoMigrate. Модели определяют схему через struct tags, миграция при старте приложения.

## Последствия

**Плюсы:**
- Быстрый старт — модель = схема, нет отдельных SQL-файлов
- GORM hooks (BeforeSave/AfterFind) — прозрачное шифрование ПД без изменения бизнес-логики
- Preload для решения N+1
- Идемпотентность — безопасно запускать повторно
- Совместимость с Rust-схемой (детекция существующих таблиц)

**Минусы:**
- AutoMigrate не умеет: удалять колонки, переименовывать, менять типы, откатывать
- На production любое изменение модели автоматически меняет схему — опасно
- Нет версионирования миграций

**Рекомендация:** Перед production заменить AutoMigrate на файловые миграции (goose или golang-migrate). AutoMigrate оставить только для dev.
