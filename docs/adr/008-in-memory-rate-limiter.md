# ADR-008: In-memory rate limiter

> Актуализация 14.10.2026: локальный счётчик сохранён, но ключ авторизованного запроса вычисляется хешированием всей строки Bearer, а не общего префикса токена. Есть отдельная защита входа и блокировка учётной записи. Исторические оценки «нулевой latency» не являются измерением. Текущие ограничения — в ../SECURITY.md; исходное решение ниже сохранено.

> Актуализация 21.10.2026: дополнительно действует общий IP-лимит для авторизованных и анонимных запросов; корректный адрес клиента определяется цепочкой доверенных прокси. Оба счётчика локальны одному процессу. Текущие параметры и границы приведены в ../SECURITY.md и ../DEPLOYMENT.md.

**Статус:** Принято, с ограничениями

## Контекст

Нужен rate limiting для защиты от brute force и DoS. Варианты: Redis-based (распределённый), in-memory map (локальный), облачный WAF.

## Решение

In-memory rate limiter на основе `map[string][]int64` с cleanup-горутиной каждые 60 секунд. Ключ: Bearer token prefix (авторизованные) или IP (анонимные).

## Последствия

**Плюсы:**
- Нет внешних зависимостей (Redis не нужен)
- Нулевая latency (обращение к map vs network round-trip к Redis)
- Простой деплой (один контейнер)
- Настраивается через env: RATE_LIMIT_PER_MINUTE, RATE_LIMIT_WINDOW_SEC

**Минусы:**
- Не работает за балансировщиком (каждый инстанс считает отдельно)
- При перезапуске счётчики сбрасываются
- Память растёт с числом уникальных клиентов (mitigated cleanup-горутиной)

**Когда пересмотреть:** При переходе на >1 инстанс бэкенда — заменить на Redis или `golang.org/x/time/rate` с внешним хранилищем.
